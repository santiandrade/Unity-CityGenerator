# The Editor tool — `Packages/com.santiandrade.citygenerator/Editor/`

Detail behind the "The tool" section of the root `CLAUDE.md`. Namespace `CityGenerator.Editor`, `includePlatforms: [Editor]`, references the runtime asmdef and `Unity.InputSystem`. Every type is `internal static` except `CityGeneratorWindow` and the `Editor/UI/` visual-element classes (which need instance state to exist at all).

## `CityGeneratorWindow`

`Tools > City Generator > Open`. Holds the entire configuration in a single `[SerializeField] CityGeneratorSettings settings`, which is why state survives closing/reopening the window within an Editor session; **deliberately not a `ScriptableObject`** (see the discarded decisions in `specs/01-city-generator-tool.md`).

Built with **UI Toolkit** (`CreateGUI`, not `OnGUI`): `Editor/UI/CityGeneratorWindow.uxml` is the structural skeleton (banner, tab bar, scrollable card container per tab, footer) cloned into `rootVisualElement`, styled by `CityGeneratorWindow.uss` plus a theme sheet (`_Dark`/`_Light`, picked by `EditorGUIUtility.isProSkin`) that only redefines `--cg-*` color variables. The footer's `cg-summary-line` label (`~N buildings · N vehicles · N pedestrians · N custom places`) sits above the build/rebuild/reset buttons and is refreshed on every `RefreshDynamicUi` pass regardless of which tab is active, so it's independent of the per-tab card layout above it.

Six tabs:

- **City** — general/ground/plaza/buildings/vegetation/props, plus the Custom Places card (last on the tab) — see `custom-places.md`.
- **Player** — a Player card with `general.playerEnabled` ("Enabled", moved here from General), Player Prefab and Input Actions, both required only when Enabled is on (`general.playerPrefab`/`general.inputActions` still live under `GeneralSettings`/segment `general`, resolved to this card via `RegisterCardPathAlias`); a Player Settings card for movement/`CharacterController`/input action names (everything the Player card used to hold besides Prefab and Input Actions); a Camera card for `ThirdPersonCamera` orbit/collision/field-of-view tuning; a Free Camera card (SPEC 13, `freeCamera.enabled`/`moveSpeed`/`sprintMultiplier`/`rotationSmoothTime`) for `FreeCameraController` — see `runtime-and-traffic.md`. When Enabled is off, no player is spawned even if a Player Prefab is still assigned, and Free Camera is ignored regardless of its own `enabled` — see `CityGeneratorSceneBuilder`/`CityGeneratorContentAssembler` in `runtime-and-traffic.md`.
- **Traffic** — between Player and Pedestrians. A Traffic card for `general.includeTraffic` ("Enabled") and `general.vehicleCount` ("Vehicle Count"), plus the vehicle-density `HelpBox`; a Vehicles card for the weighted vehicle prefab list. Both fields still live under `GeneralSettings`/segment `general` — resolved to this tab/card via `RegisterCardPathAlias`, the same mechanism `general.playerEnabled` uses for the Player tab.
- **Pedestrians** — a Pedestrian Settings card for `general.includePedestrians` ("Enabled") and `general.pedestrianCount` ("Pedestrian Count"), plus the pedestrian-density and isolated-blocks `HelpBox`es (moved from the City tab's General card via `RegisterCardPathAlias`, same mechanism as Traffic above); the weighted pedestrian list; a Custom Pedestrians card (SPEC 12, `CityGeneratorCustomPedestrianList` — see `pedestrians.md`); a Behaviour card for pace/jitter/stop tuning and the animation reference speeds; a Crowd card for `PedestrianManager` separation/avoidance/staggering.
- **Minimap** — `enabled`, `textureResolution`, `viewRadiusMeters`, with two non-blocking `HelpBox`es (resolution above a warning threshold, view radius larger than the grid's covered world size) — see "Minimap" below.
- **Audio** — an Ambience card and a Plazas card, each `enabled` plus an audio clip list — see "Audio" below.

Switched by `CityGeneratorTabBar`, a hand-rolled tab strip (**not** `UnityEngine.UIElements.TabView`) so it can stay themed with `--cg-*` and mark a tab red when a card on it has a validation error; selection persisted in `EditorPrefs`. Every section is built in code as a `CityGeneratorCard` (collapsible, open/closed state persisted per-card in `EditorPrefs`, badge summarising its content, turns red when one of its fields fails validation).

### Binding

Bound the standard UI Toolkit way — `rootVisualElement.Bind(serializedWindow)` plus per-field `PropertyField`s constructed straight from a `SerializedProperty` — except for controls that manage their own `SerializedProperty` reads/writes:

- `CityGeneratorGridPreview` — a `Painter2D` top-down miniature of the grid. In its default `PlazaMultiToggle` mode it doubles as the plaza editor: clicking a block toggles it directly against `general.plazaCells`, a `List<Vector2Int>` of block coordinates, so the picture and the generated scene can never disagree (there is no separate plaza count). In `SingleSelectQuadrant` mode, used per Custom Place entry, clicking picks a single block plus — unless the entry occupies the full block — which quadrant of it was clicked, using the same 0-3 convention as `CityGeneratorBuildingBuilder.SlotOffsets`. In `NodeGraphPicker` mode (SPEC 12, one per Custom Pedestrian entry), it groups a `CityGeneratorPedestrianPreview`'s nodes into clickable line "zones" (a Ring edge, an Interior spoke, a crossing) fit to their own world-space bounding box instead of a block grid — see `pedestrians.md`, "Custom Pedestrians", for the zone derivation, adjacency/connectivity rules, and the shared-preview caching.
- `CityGeneratorPrefabGrid` — thumbnail grid for `buildingPrefabs`/`vegetation.prefabs`.
- `CityGeneratorWeightedPrefabList` — thumbnail + percentage slider + stacked bar + "Normalize to 100%" for `vehicles`/`pedestrians`. Deliberately never rebuilds its rows on a plain percentage edit, only on add/remove/normalize, because tearing down the dragged `Slider` mid-drag would drop its pointer capture and abort the gesture.
- `CityGeneratorCustomPlaceList` — one self-contained row per Custom Place entry.
- `CityGeneratorCustomPedestrianList` — one self-contained row per Custom Pedestrian entry (SPEC 12), mirroring `CityGeneratorCustomPlaceList`; owns the shared `CityGeneratorPedestrianPreview` every row's `NodeGraphPicker` binds to.
- `CityGeneratorAmbienceClipList` / `CityGeneratorPlazaAudioClipList` — one self-contained row per audio clip entry (SPEC 09), same convention.

**Never use `PropertyField` for a row created after the window's one-time `Bind()` call** — it never binds and renders empty. This was a real regression caught and fixed after the initial SPEC 06 implementation; that is why `CityGeneratorCustomPlaceList` rows are built from plain `TextField`/`ObjectField`/`Toggle`/`EnumField` controls.

### Validation and build buttons

`CityGeneratorValidator.ValidateDetailed` (same checks as the original `Validate`, each issue additionally tagged with the settings path that caused it) is re-run on every edit via `TrackSerializedObjectValue`, driving live required-field/card/tab highlighting and disabling both Build buttons until every issue clears — replacing the old blocking `EditorUtility.DisplayDialog` validation-error flow. A field relocated to a card outside its own settings segment (like `general.playerPrefab` living in the Player card) is resolved through an exact-path alias registered alongside the segment-based lookup.

Two buttons:

- **Build City in New Scene**.
- **Re-Build City in Current Scene** — transactional: builds the new city under a temporary root and only destroys the previous one, found via the `CityGeneratorRoot` marker component rather than by name, once generation finishes without throwing (`CityGeneratorSceneBuilder.RebuildInActiveScene`). Camera/player are left alone either way; the Directional Light's base rotation and shadows are too, but its Day/Night Cycle (see below) is reconciled against the current settings — the one deliberate exception to "the light is left untouched", per SPEC 08.
  - **Bug (fixed 2026-09-02): the previous city used to stay exactly where it was — same world-space footprint as the one under construction — for the whole call**, since it's only destroyed *after* `Assemble` succeeds. Two full sets of static colliders (ground, buildings, everything) stacked exactly on top of each other made `PedestrianNetwork.PrunePlacedObstacles`'s downward `Physics.Raycast` ground check intermittently find no hit at all (confirmed directly: roughly every other Rebuild), wrongly marking most/all nodes `Blocked` and silently under-spawning or zeroing out pedestrians — worst on a Custom Pedestrians entry restricted to a small hand-traced route. Fix: the previous `CityGeneratorRoot` is now moved 50,000 units aside *before* `Assemble` runs (mirroring `CityGeneratorMinimapBuilder`'s own isolate-by-moving-the-root pattern for its snapshot capture, with a different offset so the two can never coincide) and only destroyed after success — moved back to its original position in the `catch` block if generation throws, so the "previous city survives a failed rebuild" guarantee still holds.

Both drive an `EditorUtility.DisplayProgressBar` through an optional `onProgress` callback threaded (additively — default `null`) through `CityGeneratorContentAssembler.Assemble` → `CityGeneratorSceneBuilder`, and show the result in an in-window panel (with a "Ping Scene" button) instead of a dialog. "Reset to Defaults" stays a plain button, low-key styled.

The `settings` field is `[SerializeField] internal`, not `private`, so `Assets/Editor/CityGeneratorSetDefaultsWindow.cs` (outside the package) can read it via the package Editor assembly's `InternalsVisibleTo`.

## Pipeline

In order: `CityGeneratorValidator` → `CityGeneratorSceneBuilder` (new scene + directional light + camera + player, saved as the next free `Assets/Scenes/City<N>.unity`) → `CityGeneratorContentAssembler` (the group hierarchy and every builder) → `Grid` → `GroundBuilder` → `CustomPlaceBuilder` → `BuildingBuilder` → `PlazaBuilder` (which calls `AudioBuilder.BuildPlazaAudio` per plaza) → `StreetPropsBuilder` → `TrafficBuilder` → `PedestrianBuilder` → `CustomPedestrianBuilder` (SPEC 12, against the real `PedestrianNetwork`, independent of `includePedestrians`) → `MinimapBuilder` → `AudioBuilder.BuildAmbience`. `CityGeneratorSceneBuilder` then finalises the Minimap snapshot into a PNG asset and instantiates the `MinimapHUD` prefab, once the generated scene's path is known — see "Minimap" below.

## Custom Grid (SPEC 11)

`GeneralSettings.useCustomGrid` (`bool`) is a switch, not a migration: `gridWidth`/`gridHeight` and `customBlockCells` (`List<Vector2Int>`) coexist in `GeneralSettings` always, and whichever one is read depends only on the flag. `CityGeneratorConstants.MinGridSize`/`MaxGridSize` (promoted from what used to be `CityGeneratorWindow` private consts) are the fixed `MaxGridSize x MaxGridSize` canvas Customize mode edits — a custom shape is always edited on this canvas regardless of `gridWidth`/`gridHeight`, and a block's world position (`CityGeneratorGrid.GetBlockCenter(cell, MaxGridSize, MaxGridSize)`) never shifts as the shape grows or shrinks around it.

"Customize" (General Options card, top-right of the grid preview) shows one blocking `EditorUtility.DisplayDialog` — the sole deliberate exception to the tool's "no blocking dialogs" rule, since entering Customize resets `customBlockCells` to a single centre cell and clears `plazaCells`. "Exit Customize" discards the custom shape outright and restores whichever `gridWidth`/`gridHeight` rectangle was active before — re-entering Customize always restarts from one centre cell, never the previous shape.

While `useCustomGrid` is true, a 2-option selector ("Define City Area" / "Define Plazas") switches `CityGeneratorGridPreview` between two of its own modes:

- **`CustomAreaEdit`** (`BindCustomArea`): paints every canvas cell as a real block or a semi-transparent hole. A hole shows "+" only when `CityGeneratorGrid.IsValidAddition` allows it (orthogonally adjacent to the shape); a real block shows "-" only when `CityGeneratorGrid.CanRemoveWithoutSplitting` allows it (removing it keeps the rest as one connected component, and at least one block remains). Both are pure functions with no scene access, so the same rule the UI paints is the only rule that can ever be reached by clicking — there is no separate "island" validation error to design around.
- **Plaza toggling with `SetShapeMask`**: the existing `PlazaMultiToggle`/`SingleSelectQuadrant` modes gained `SetShapeMask(customBlockCellsProperty)`, applicable on top of an existing `Bind`/`BindSingleSelection`: any cell outside the mask paints semi-transparent and ignores clicks. Used by the main preview's "Define Plazas" submode and by every Custom Place entry's own `SingleSelectQuadrant` picker (`CityGeneratorCustomPlaceList.SetShapeMask`) whenever `useCustomGrid` is true, so neither editor lets the user click a hole.

Every builder downstream branches on `useCustomGrid` in `CityGeneratorContentAssembler`, each with its own custom-shape overload built to agree with the others on the same adjacency rules: a street segment is "real" when at least one of its two flanking cells is in `customBlockCells`; an intersection needs a traffic light/zebra crossing when it has **at least 3** real arms (a full 4-way, or a T-intersection — including one sitting on the shape's own border, not just a strictly-interior one). Exactly 2 real arms is either a plain straight-through point (opposite arms, no cross traffic) or a perimeter corner (perpendicular arms, a street bending 90° with only one possible way through) — neither is a real decision point, so neither gets a light or a crossing. `CityGeneratorTrafficBuilder.HasSignalledIntersection` (over `SignalledIntersectionMinArms`, the same count `BuildTrafficLights` loops on) is the one place this rule is evaluated for a whole city; `CityGeneratorValidator` (Traffic Light prefab required) and `CityGeneratorWindow.GetIsolatedBlocksWarning` both call it instead of re-deriving it, which is what they used to do — see CLAUDE.md's invariant. This 3-arm rule was corrected during QA from an earlier, too-strict "all 4 surrounding cells real" rule (which left every border T-intersection unsignalled) and, separately, from an over-generalised "both axes have an arm" rule (which wrongly signalled plain 2-arm corners too) — see the `CarAgent`/`TrafficNetwork` sections in `runtime-and-traffic.md` and the `PedestrianNetwork` section in `pedestrians.md`. The same 3-arm rule was later applied to the **rectangular** (non-custom) grid path too, at the user's explicit request: a classic `gridWidth x gridHeight` city now also gets lights/crossings at its own border T-intersections, not just at strictly-interior 4-ways — a deliberate behaviour change to the tool's non-custom output, not merely a custom-shape consistency fix.

- **`CityGeneratorGrid.BuildBlocks(customBlockCells, plazaCells)`** — the only overload `BuildingBuilder`/`PlazaBuilder`/`StreetPropsBuilder` ever see, since all three already iterate `IReadOnlyList<BlockCell>` rather than looping `gridWidth x gridHeight` themselves; they needed no changes at all.
- **`CityGeneratorGroundBuilder`** — a custom `BuildRoadBase` places one full-`CellPitch` tile per real block (adjacent tiles abut exactly) plus the outer band beyond any edge with no neighbouring block, tiled by `EnumerateBand` (see "The outer contour" below). A custom `BuildRoadMarkings` draws a dash only on a street segment adjacent to a real block (skipped near a zebra crossing via the shared `HasCrossTraffic` 3-arm test), and a zebra crossing only at a 3-real-arm intersection, drawing a stripe only on each arm that's actually real (a T-intersection gets 3 stripes, not 4). The rectangular (non-custom) `BuildDashes`/`BuildZebraCrossings` mirror the identical 3-arm rule via `HasCrossTrafficRect`, extended to the grid's own border. `BuildEmptyBlocks` fills whatever the shape leaves unpaved inside its own bounding rectangle (see "Filling a custom shape's gaps" below).
- **`Runtime/TrafficNetwork.BuildFromBlockCells`** and **`Runtime/PedestrianNetwork.BuildFromBlockCells`** — both Runtime classes keep their own literal copies of `CellPitch`/`MaxGridSize` (same reasoning as their other "own copy" layout numbers: `CityGeneratorConstants` is Editor-only). `TrafficNetwork` still builds the same dense `axesX x axesZ` node array, but `Neighbour` additionally requires the street segment to be shape-adjacent; any intersection touching zero real blocks gets its entries' `IsEntry` forced false, and — since one intersection can touch a real block through one arm while another of its arms leads nowhere — any individual entry with zero of its own exits is also forced `IsEntry = false`, so neither is ever offered as a vehicle spawn point (`BuildVehicles` otherwise treats any `IsEntry` node as spawn-safe regardless of exit count). **`useCustomShape`/the block-cell sets must be `[SerializeField]`** (mirrored into plain `List<Vector2Int>` fields, since a `HashSet` itself isn't serializable) — see `runtime-and-traffic.md`'s `TrafficNetwork.cs` section for the "cars drive across the whole canvas after a domain/scene reload" bug this fixes. `PedestrianNetwork` only builds a ring/interior-cross for a real block; its crossing-arm loop (`BuildCrossings`) runs over every axis intersection (not just strictly-interior ones) and skips any arm whose neighbouring block is out of range or a shape hole, relying on `FindNearestIntersection`'s 14 m cutoff to naturally skip any corner with no real light.
- **`CityGeneratorMinimapBuilder`** — a custom `Build` overload frames the minimum rectangle wrapping the real cells' bounding box instead of the fixed canvas, so a small or corner-hugging shape doesn't get a mostly-empty minimap.
- **`CityGeneratorValidator`** — a `CustomPlaceEntry.blockCell` no longer present in `customBlockCells` is a blocking error (same mechanism as an out-of-range block on a `gridWidth`/`gridHeight` resize), never auto-cleared or relocated. The traffic-light-required check and the minimap view-radius warning both switch to shape-aware bounding-box logic instead of `gridWidth x gridHeight` when `useCustomGrid` is true.
- **`CityGeneratorWindow`'s vehicle/pedestrian density `HelpBox`es** (`GetVehicleDensityWarning`/`GetPedestrianDensityWarning`) also branch on `useCustomGrid`: the vehicle one calls `TrafficNetwork.EstimateValidSpawnNodeCountCustom` (mirroring `BuildFromBlockCells`'s own entry/exit validity rules) instead of the rectangular `EstimateValidSpawnNodeCount`, and the pedestrian one substitutes `customBlockCells.Count` for `gridWidth x gridHeight` in its ring/interior node estimate — both previously stayed pinned to the leftover `gridWidth`/`gridHeight` values regardless of the actual custom shape's size, so the warning never fired (or fired wrongly) as the shape was edited.
- **`CityGeneratorGridPreview`'s `SingleSelectQuadrant` picker** (one per Custom Place entry, via `CityGeneratorCustomPlaceList`) also gained `SetPlazaMask`, overlaying `general.plazaCells` in the same green used by the main preview's plaza editor — a visual reference for where plazas already sit while placing a Custom Place, wired up unconditionally in `CityGeneratorWindow` (not gated on `useCustomGrid`, since plazas exist in both grid modes).

## The outer contour (SPEC 11)

A generated city **always ends in sidewalk, never in bare asphalt**, on both grid modes: `CityGeneratorGroundBuilder.BuildPerimeterSidewalks` lays a `PerimeterSidewalkWidth` (6 m) band on the far side of every perimeter street, so that street has a walkable far side exactly like an interior one. `RoadBaseMargin` is derived from it (`StreetWidth / 2 + PerimeterSidewalkWidth` = 11 m, up from a hardcoded 6 m) and is still "how far the ground reaches past the outermost street axis", so the road base, the Minimap snapshot footprint and the window's size preview all follow automatically.

Both bands are tiled by one shared `EnumerateBand(cells, centreOf, innerRadius, outerRadius)`: the road base's is `[CellPitch/2, CellPitch/2 + RoadBaseMargin]` from a real cell's centre, the sidewalk's is `[CellPitch/2 + StreetWidth/2, CellPitch/2 + RoadBaseMargin]`. It computes the exact set difference between the shape dilated by each radius (Chebyshev, i.e. square rings), worked per **missing** cell: that cell's own 56 m square is cut by the six coordinates either dilation's boundary can fall on, into at most 5×5 sub-rectangles each wholly in or wholly out of the band, which are then merged along X.

Two earlier, more obvious tilings were tried and are wrong — don't go back to either:

- **Per real cell, outwards** (one strip per open edge plus a square corner fill): two perpendicular strips cover the same square at a concave corner, and coplanar tiles at the same Y z-fight.
- **Per missing cell, but per-edge with a fixed square corner**: a square corner fill is the right shape only when the band is as wide as the whole margin. The 6 m sidewalk band needs an **L**-shaped piece at every convex corner — a square leaves a strip of ground bare where the perimeter street ends. `Assets/Tests/EditMode/Generation/PerimeterSidewalkTests.cs` reconstructs the band by brute force and asserts it is gap-free, overlap-free, and never paves over a street.

## Filling a custom shape's gaps (SPEC 11)

A Custom Grid city still comes out as the **plain rectangle of its own bounding box**: `CityGeneratorGroundBuilder.BuildEmptyBlocks` covers every gap of the shape with `GroundSettings.emptyBlockPrefab` ("Empty Block Prefab (custom grids only)", Ground card), placed at `GroundDatumY` exactly like a plaza lawn — it is ground cover, flush with the sidewalk it abuts — and defaulting to the same `Lawn.prefab` the plaza uses. So a shape whose cells span 6 × 8 generates a 6 × 8 city, not a 10 × 10 canvas with holes in it. It is a blocking validation error to leave the field empty while Customize mode is on. The rectangular grid path never calls it: a full rectangle has no gap to fill.

The filled region is the cells' bounding rectangle **grown by `RoadBaseMargin`** — exactly the outer footprint a rectangular grid of the same block count would have, and the same rectangle `CityGeneratorMinimapBuilder` and the validator's View Radius check already frame — **minus the shape dilated by `CellPitch/2 + RoadBaseMargin`**, i.e. everything the road base and the perimeter sidewalk already cover. The fill therefore stops exactly at the outer edge of the perimeter sidewalk rather than covering it, which is what keeps "a generated city always ends in sidewalk" true.

`EnumerateEmptyFill` tiles it per **missing** cell, for the same reason `EnumerateBand` does (a per-real-cell tiling overlaps at concave corners and leaves an unpaved notch at convex ones): a missing cell's 56 m square is cut by the two coordinates the covered dilation's boundary can fall on into at most 3×3 sub-rectangles, each wholly covered or wholly uncovered, clipped to the bounding rectangle and merged along X. The surrounding ring of cells clips on that same coordinate, so it needs no extra cut. `Assets/Tests/EditMode/Generation/EmptyBlockFillTests.cs` reconstructs the fill by brute force and asserts it is gap-free, overlap-free, never on top of paved ground, and never outside the bounding rectangle.

## Builders and utilities

- **`CityGeneratorConstants`** holds the layout numbers (46 m blocks on a 56 m pitch, `GroundDatumY` 0.18, 22 m building slots, lamp/zebra/traffic-light offsets…). Most constants carry a comment explaining *why* that value — several were tuned against real overlap bugs (lamps clearing the plaza lawn, zebra stripes vs. dashed centreline, corner margin so wide prefabs don't collide across a corner). Change them from there, never inline. Player movement/`CharacterController`/camera tuning and pedestrian pace/jitter/stop/crowd tuning used to live here as hardcoded (and, for the pedestrian ones, mostly unreferenced) constants; they are now user-configurable settings (`PlayerSettings`, `CameraSettings`, `PedestrianBehaviourSettings`, `CrowdSettings` in `CityGeneratorSettings.cs`) — don't reintroduce them as constants.
- **Overlap avoidance** is the tool's central mechanism, but only for props, vegetation and Custom Places — buildings and vehicles are deliberately exempt. `CityGeneratorBoundsUtility.GetWorldBounds` combines all child `Renderer` bounds, and `CityGeneratorPlacementEngine` instantiates a candidate and checks its XZ `Rect` against already-placed objects, `DestroyImmediate`ing it if it overlaps. Bounds, not fixed per-category radii, because the prefabs come from the user. `ContentAssembler` threads one growing `obstacles` list through every category in turn — if you add a category, append its result to that list; `obstacles` stays the source of truth. Since SPEC 05 the overlap check queries `CityGeneratorSpatialHash` (a uniform hash keyed by cell, cell size derived from the block size) instead of scanning `obstacles` linearly — the hash is a pure index over `obstacles`, populated alongside it and never a second source of truth (measured -17.2% total generation time on a 10×10 grid; same placement result for a given seed, only the query cost changes).
- **`CityGeneratorPlayerSpawner.FindSpawnPosition`** picks where the player instance lands: inside a plaza block when the city has one (searched in random order across plazas), a random block otherwise, checked against the same growing `obstacles` list (minus ground cover, since standing on lawn/sidewalk is the point) so the player never spawns overlapping a building/prop/vehicle.
- **`CityGeneratorSceneBuilder.ConfigurePlayer`** `AddComponent`s `CharacterController`, `PlayerController` and `PlayerInputAuthority` to whichever prefab is assigned as Player Prefab, if it doesn't already carry them — but then **writes the Player tab's tuning onto the instance unconditionally**, even when the prefab already had its own `CharacterController`/`PlayerController`: the window is the single source of truth, never the prefab asset (which is never touched). This is what lets `DefaultAssets/Prefabs/Characters/` stay clean model+Animator prefabs, and equally lets a user-supplied character work as Player Prefab with zero manual setup. `CreateMainCamera` applies the Camera tab's tuning to the generated `ThirdPersonCamera` the same way (`fieldOfView`, orbit, collision, cursor lock), and adds `FreeCameraController` alongside it (SPEC 13 — see `runtime-and-traffic.md`); only the camera's initial transform stays a hand-tuned fixed value in `CityGeneratorSceneBuilder`.
- **`CityGeneratorBuildingBuilder.BuildBuildings`** picks up to 4 fixed 22 m corner slots per non-plaza block, guaranteeing every assigned building prefab is used at least once. **Which corners are filled is shuffled per block** when `buildingsPerBlock < 4` — a QA-found bug had every block always fill corners `0..buildingsPerBlock-1` in the same order, making partially-built blocks look identical everywhere. Buildings are **not** overlap-checked against each other or against the block edge: an oversized building prefab will visibly clip into its neighbour or spill into the street — accepted as the user's responsibility to size their prefabs to the 22 m slot. Since SPEC 06 it also takes an optional `reservedSlots` set (`(gridX, gridY, slot)`, `slot == -1` meaning the whole block) produced by `CityGeneratorCustomPlaceBuilder`: a reserved corner is excluded from that block's random corner order, a reserved whole block is skipped entirely, and an empty set (the default) reproduces the exact old behaviour.
- **Densities** mean "fraction of valid candidate points filled", not an absolute count — including `lampDensity` (1 = all 3 candidate points per block side).
- **Static flags**: `CityGeneratorContentAssembler` applies `BatchingStatic | OccluderStatic | OccludeeStatic` to every generated group **except `Vehicles`/`Pedestrians`**, so each generated city is batched and ready for a lightmap/occlusion bake with no manual pass — this includes the `CustomPlaces` group, since a Custom Place never moves at runtime. `CarAgent`/`PedestrianAgent` move their instances by transform every frame, which is why both are excluded.
- **Seeding**: `general.useCustomSeed` + `general.seed` make generation reproducible; `Assemble` uses `new System.Random(seed)` when enabled, unseeded otherwise. Every builder receives that one `System.Random` **by parameter** — none of them touch `UnityEngine.Random`, so seeding it is enough to make placement and prefab choice fully deterministic (`CarAgent`'s runtime driving still uses `UnityEngine.Random`, unrelated to generation). Which blocks are plazas is **not** part of this: `CityGeneratorGrid.BuildBlocks` takes `general.plazaCells` directly and never touches `random` — it used to draw a random subset here (`ChoosePlazaIndices`), which is why the grid preview couldn't reliably match the generated scene.
- **No `Global Volume`** is generated — removed on purpose (commit `a094fef`) to keep the tool render-pipeline-agnostic.

## Vehicle spawning and the `Vehicle` layer

`CityGeneratorTrafficBuilder.BuildVehicles` calls `EnsureVehicleLayerExists` before spawning anything: if the project has no `Vehicle` layer yet, it creates one itself by writing directly to `ProjectSettings/TagManager.asset` via `SerializedObject`, using the first free slot from `CityGeneratorConstants.FirstUserLayerIndex` (8) up, and logs that it did so. Requiring the user to create this layer by hand was a recurring point of confusion during SPEC 02 verification. Only if every slot 8-31 is already taken does it fall back to warning instead — in that case every instance's `CarAgent.vehicleMask` is left at `0` (Nothing) rather than matching whatever layer the instance happens to share with unrelated scene geometry, so vehicles simply stop detecting each other (they still stop for lights and unsignalled-crossing priority) until a slot frees up.

`CarAgent` and the `Vehicle` layer are added **to the scene instances only**, never to the user's prefab asset, and outer-edge exit nodes are skipped when spawning (a car there has nothing ahead and `CarAgent` disables itself).

When the layer does exist, `BuildVehicles` sets `CarAgent.vehicleMask` to `1 << instance.layer` per instance via `SerializedObject` — **do not rely on the mask baked into a vehicle prefab's own serialized data**: it only happens to work when `Vehicle` sits at the same layer index the prefab was authored against, and silently makes the forward sensor blind to every other vehicle otherwise (found during SPEC 02 verification: the demo prefabs' baked `vehicleMask` and `m_Layer` both happened to reference index 8, which is why the bug went unnoticed).

`CityGeneratorConstants.VehicleDensityWarningThreshold` (a fraction of the spawn nodes) is surfaced only as a live `HelpBox` in the window while editing `vehicleCount` — `BuildVehicles` itself no longer logs a console warning past that threshold, since the inspector already told the user before they clicked generate. The threshold is empirical: measured on a 5×5 grid, traffic at 38% of nodes flowed and at 76% gridlocked from the first frame.

`CityGeneratorDistributionUtility.DistributePercentages` (a generic largest-remainder distributor) is shared between `BuildVehicles` and `BuildPedestrians` rather than duplicated per category.

## Defaults

- **`CityGeneratorDefaultAssets.ApplyTo`** fills a fresh `CityGeneratorSettings` with the package's own demo prefabs (buildings, vegetation, vehicles and pedestrians with their percentages, ground, plaza prefabs and layout, a Custom Places demo entry, props, player, input actions, audio clips), loaded from hardcoded `Packages/com.santiandrade.citygenerator/DefaultAssets/...` paths, so the window opens ready for a one-click first generation instead of empty required fields. **It is generated code — read the current defaults there, never from this document.** Those paths resolve in any project that installs the package, so this is ordinary portable code. It cannot run from a field initializer on `CityGeneratorSettings` (Unity forbids `AssetDatabase` calls during `EditorWindow` deserialization); it is invoked from `CityGeneratorWindow.OnEnable()`, gated by a serialized `defaultsInitialized` flag so it runs once per window instance, and again from "Reset to Defaults".
- **`CityGeneratorDefaultAssetsWriter.SaveCurrentAsDefault`** is the other direction: given an open window's `settings`, it regenerates `CityGeneratorDefaultAssets.cs`'s `ApplyTo` body wholesale (asset lists can change length between calls, which a targeted text edit can't express as cleanly as a full rewrite) and patches the scalar field initializers in `CityGeneratorSettings.cs` in place via `Regex` (safe because every scalar field name — `gridWidth`, `vehicleCount`, `density`… — is unique within that file). Both are plain `File.WriteAllText` calls against the package's own source under `Packages/`, followed by `AssetDatabase.Refresh()`. Kept in its own file rather than folded into `CityGeneratorDefaultAssets` because it overwrites that file's contents — it must never need to regenerate itself. A prefab assigned from outside `DefaultAssets/` still gets written into the new default (the command never blocks on it), but the result only resolves in this project; flagged with a console warning per offending field rather than silently accepted. The `[MenuItem("Tools/City Generator/Set Current Selection As Default")]` entry point that calls it lives outside the package, in `Assets/Editor/CityGeneratorSetDefaultsWindow.cs`. `minimap`'s scalars are deliberately excluded (they come from `MinimapSettings.Default()`, not inline field initializers, so the regex wouldn't match them anyway; the shipped default is the intended one).

## Day/Night Cycle

- **`DayNightSettings`** (`Editor/CityGeneratorSettings.cs`) — the "Day/Night Cycle" card of the City tab (`enabled`, `startHour`, `speedMultiplier`, `lightColorOverTime`, `lightIntensityOverTime`) drives `CityGeneratorSceneBuilder.CreateDirectionalLight`/`RebuildInActiveScene` → `ConfigureDayNightCycle`, which adds/updates a `Runtime.DayNightCycle` on the generated "Directional Light" and projects those fields onto it — the same projection pattern `MinimapSettings` uses for `MinimapHUD`.
- **The component is always attached, never removed**: `dayNight.enabled` is written onto the `Behaviour`'s own `enabled` flag, so a disabled cycle stays put at Start Hour (Unity skips `Update` on a disabled Behaviour) instead of the light falling back to a static default orientation. Turning the cycle off used to skip `ApplySun` entirely, which is exactly that bug (fixed in 2.4.1) — `ApplySun(startHour)` is now called unconditionally.
- **Editor preview without Play**: the builder calls `DayNightCycle.ApplySun(startHour)` directly, once, right after adding/updating the component. `DayNightCycle` has no `[ExecuteAlways]` behaviour of its own — deliberately, to avoid animating in Editor refreshes — so this one explicit call is the only way the light previews oriented/colored for `startHour` outside Play Mode.
- **Rotation**: `ApplySun` only ever changes pitch (X axis), via `pitch = hourOfDay / 24f * 360f - 90f`; yaw/roll come from a base rotation `DayNightCycle` captures once in `Awake`. The builder overrides that capture on **every** build/re-build via `DayNightCycle.SetBaseRotation(Quaternion.Euler(0, CityGeneratorSceneBuilder.DirectionalLightYaw, 0))`, so the yaw is always `-110°` (roll `0°`) even on a light that already existed with a different baked-in yaw. The minimap is drawn with world `+Z` up and world `+X` right, i.e. minimap-right is East, so a yaw of `-90°` would put sunrise (hour 6) due East and sunset (hour 18) due West; `-110°` tilts that axis 20° — sunrise east-north-east, sunset west-south-west — still reading correctly against the HUD while keeping shadows off the exact street axis of an all-parallel grid. (It was `-90°` in 2.4.1 and `-30°`, uncorrected on Re-Build, before that.) `CreateDirectionalLight` gives a fresh light `Euler(50, -110, 0)`; `UpdateDirectionalLight` leaves an existing light's position and shadows alone but still corrects its yaw.
- **Play Mode**: `DayNightCycle.Update()` (only runs while playing, since there's no `[ExecuteAlways]`) advances `currentHour` by `Time.deltaTime * speedMultiplier / 3600f` per frame and calls `ApplySun` — so `speedMultiplier = 1` means one simulated hour per one real hour, and both `lightColorOverTime`/`lightIntensityOverTime` are sampled at `t = hourOfDay / 24f`, completing one full gradient/curve cycle per 24 simulated hours regardless of `speedMultiplier`.
- **Re-Build**: `CityGeneratorSceneBuilder.UpdateDirectionalLight` locates the light by name ("Directional Light", same fragile-by-name pattern the Minimap HUD lookup already accepts), recreating it via `CreateDirectionalLight` if it's missing, then runs the same `ConfigureDayNightCycle` — adding the component if absent, updating its fields and its `enabled` flag, and forcing the yaw — without moving the light or touching its shadows.

## Audio (SPEC 09)

`CityGeneratorAudioBuilder` turns the Audio tab's `AudioSettings` into plain `AudioSource`s, in two independent halves, both applied on Build and Re-Build:

- **`BuildAmbience`** — one 2D (`spatialBlend = 0`), looping, `playOnAwake` `AudioSource` per `AmbienceClipEntry`, as a direct child of `cityRoot`. Called last in `CityGeneratorContentAssembler.Assemble`.
- **`BuildPlazaAudio`** — one 3D (`spatialBlend = 1`) looping source per `PlazaAudioClipEntry`, placed at each generated plaza's centre inside that block's own group, with the entry's `minDistance`/`maxDistance` rolloff. Called from `CityGeneratorPlazaBuilder` per plaza, so a city with no plaza block gets none.

Both hang off geometry the pipeline rebuilds wholesale on every Build/Re-Build, so unlike the Directional Light's Day/Night Cycle there is **no reconcile-an-existing-instance path** here — the previous city's sources go away with the previous city root. Each half is skipped entirely when its own `enabled` is off, and an entry with no clip assigned is skipped rather than producing a silent source.

## Minimap

`CityGeneratorMinimapBuilder.Build`, called from `CityGeneratorContentAssembler.Assemble` when `minimap.enabled`, computes the grid's world bounding box (`gridWidth`/`gridHeight` × `CellPitch` + `RoadBaseMargin`, same footprint as the road base slab — or, when `useCustomGrid`, the bounding box of the real cells in `customBlockCells` instead, via a separate `Build` overload — see "Custom Grid" above), captures a top-down orthographic snapshot into an **in-memory** `Texture2D`, and fills a `MinimapData` component (added to the city root, alongside `CityGeneratorRoot`) with it, the bounding box, and the `PointOfInterestEntry` list `CityGeneratorCustomPlaceBuilder` projects from every Custom Place with `isPointOfInterest == true`.

- **Two-phase asset**: the snapshot stays in-memory (not yet a saved asset) because at this point in the pipeline the final scene path isn't known — a brand-new scene is only saved after `Assemble` returns. `CityGeneratorMinimapBuilder.SaveSnapshotAsset` finalises it into a PNG inside the scene's own per-scene folder (`<SceneFolder>/<SceneName>/<SceneName>_Minimap.png` — the same folder Unity itself creates next to the scene for things like baked lighting data, created via `AssetDatabase.CreateFolder` if missing; same path/GUID on every Re-Build) once `CityGeneratorSceneBuilder` knows the scene path, for both `BuildAndSaveScene` and `RebuildInActiveScene`.
- **Excluding vehicles/pedestrians from the snapshot**: `Build` temporarily deactivates the `Vehicles`/`Pedestrians` groups around the `Camera.Render()` call, restoring them in a `finally`. A `Camera.cullingMask` excluding the `Vehicle`/`Pedestrian` layers was tried first and does **not** work — that layer is assigned only to each instance's root proxy collider (see the collider invariant in `runtime-and-traffic.md`), never cascaded onto the child mesh `Renderer`s that actually draw the car/pedestrian, which stay on whatever layer the prefab's meshes were authored with (typically `Default`). Verified with a same-scene hidden/shown capture diff during QA: the `cullingMask` approach produced zero pixel difference against an unrestricted render.
- **Neutralising the lighting for the snapshot**: lighting is *not* scoped by the isolation offset below — a Directional Light lights the city wherever it sits, so a snapshot taken on a city generated at hour 2 came out night-dark and unreadable. `Build` therefore disables every enabled directional light currently in memory (this city's own, mid-cycle, or one left over from a previous city during a Re-Build), adds a temporary `HideAndDontSave` white light at `Euler(50, DirectionalLightYaw, 0)` (it reads `CityGeneratorSceneBuilder.DirectionalLightYaw` rather than copying the number, so the two can't drift apart) with intensity 1 and no shadows for the `Camera.Render()` call, and restores everything in a `finally`. Unlike a same-call `SetActive` on an already-rendered GameObject (see below), toggling a preexisting `Light`'s `enabled`/color/intensity *does* take effect on a manual `Render()` in the same call — confirmed with a direct repro.
- **Isolating the capture from everything else loaded**: `Camera.Render()` isn't scene-scoped — it draws every currently loaded scene within its frustum, not just `cityRoot`'s own, and (during a Re-Build) the previous city's root is still fully active at capture time too, since `RebuildInActiveScene` only destroys it after `Assemble` returns. `Build` isolates the capture by moving `cityRoot` itself to a far offset (`SnapshotIsolationOffsetX`, 50,000 units) before rendering and back after, rather than hiding/moving anything preexisting. Two more natural-looking approaches were tried and discarded, both confirmed by direct repro: `Camera.scene` (Unity's own mechanism for exactly this, used internally by Prefab Mode) silently fails to filter when the target scene hasn't been saved yet, which `cityRoot`'s scene always is at this point; and deactivating (or re-layering) every other root/scene *looked* correct in casual QA but still leaked real vehicles in a fraction of positions on closer inspection — a manual `Camera.Render()` simply doesn't pick up a same-call `SetActive`/layer/position change made to a GameObject Unity has already rendered at least once before (isolated with a minimal red-cube repro: hide-then-render-in-one-script-call shows the cube, hide-in-one-call-then-render-in-a-later-call correctly shows background). `cityRoot` is always freshly created for the call, so it's never been rendered before, and moving it is exactly as reliable as hiding `vehiclesGroup`/`pedestriansGroup` (also freshly created, a few lines above) already was.
- **`CityGeneratorSceneBuilder`** instantiates the `MinimapHUD` prefab (`DefaultAssets/Prefabs/MinimapHUD.prefab`, a fixed package path like `ThumbnailPath`, not a settings field) when `minimap.enabled`, writing `viewRadiusMeters` onto its `MinimapHUD.viewRadiusMeters` via `SerializedObject` — same pattern as `CreateMainCamera` applying the Camera tab to `ThirdPersonCamera`. On a Re-Build, the previous `Minimap HUD` instance (found by name, since it isn't under the swapped city root) is destroyed first.
- **`Runtime/MinimapHUD.cs`** (UGUI: `Canvas` Screen-Space Overlay + a circle-masked `RawImage`) reads `MinimapData` at `Start` and drives everything off its `worldOrigin`/`worldSize`/`pointsOfInterest` — it never recalculates them. Each `LateUpdate`: windows the snapshot texture via `RawImage.uvRect` (offset/scaled from the player's XZ position and `viewRadiusMeters`, so the map itself never rotates — north stays up), rotates the player marker to the player's yaw, and repositions/toggles the pooled POI marker clones (one generic pin sprite, reused for every POI) that fall within `viewRadiusMeters`.
- **Out-of-bounds window**: the `uvRect` above is deliberately *not* clamped to [0, 1] — keeping the player exactly at the HUD's centre matters more than staying inside the snapshot, so within `viewRadiusMeters` of a city edge the window necessarily reaches past it. That remainder is handled in the material, not the HUD: the map `RawImage` uses `DefaultAssets/Materials/MinimapWindow.mat` (`DefaultAssets/Shaders/MinimapWindow.shader`, a copy of `UI/Default` — stencil properties included, since the image is masked by the HUD's circular `Mask` — with one change: fragments whose UV falls outside [0, 1] are painted `_OutOfBoundsColor` instead of sampling the texture). That colour is kept equal to the capture camera's `backgroundColor`, so beyond the city reads as a continuation of the snapshot's own background. Reverting the image to the stock UI material brings the bug back: the PNG is imported with `wrapMode = Clamp`, so Unity smears its outermost row/column of pixels across the rest of the minimap.
