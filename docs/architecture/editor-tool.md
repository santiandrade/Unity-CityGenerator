# The Editor tool — `Packages/com.santiandrade.citygenerator/Editor/`

Detail behind the "The tool" section of the root `CLAUDE.md`. Namespace `CityGenerator.Editor`, `includePlatforms: [Editor]`, references the runtime asmdef and `Unity.InputSystem`. Every type is `internal static` except `CityGeneratorWindow` and the `Editor/UI/` visual-element classes (which need instance state to exist at all).

## `CityGeneratorWindow`

`Tools > City Generator > Open`. Holds the entire configuration in a single `[SerializeField] CityGeneratorSettings settings`, which is why state survives closing/reopening the window within an Editor session; **deliberately not a `ScriptableObject`** (see the discarded decisions in `specs/01-city-generator-tool.md`).

Built with **UI Toolkit** (`CreateGUI`, not `OnGUI`): `Editor/UI/CityGeneratorWindow.uxml` is the structural skeleton (banner, tab bar, scrollable card container per tab, footer) cloned into `rootVisualElement`, styled by `CityGeneratorWindow.uss` plus a theme sheet (`_Dark`/`_Light`, picked by `EditorGUIUtility.isProSkin`) that only redefines `--cg-*` color variables.

Three tabs:

- **City** — general/ground/plaza/buildings/vegetation/vehicles/props, plus the Custom Places card (last on the tab) — see `custom-places.md`.
- **Player** — Player Prefab + Input Actions (moved here from General), a Player card for movement/`CharacterController`/input action names, a Camera card for `ThirdPersonCamera` orbit/collision/field-of-view tuning.
- **Pedestrians** — the weighted pedestrian list, a Behaviour card for pace/jitter/stop tuning and the animation reference speeds, a Crowd card for `PedestrianManager` separation/avoidance/staggering.

Switched by `CityGeneratorTabBar`, a hand-rolled tab strip (**not** `UnityEngine.UIElements.TabView`) so it can stay themed with `--cg-*` and mark a tab red when a card on it has a validation error; selection persisted in `EditorPrefs`. Every section is built in code as a `CityGeneratorCard` (collapsible, open/closed state persisted per-card in `EditorPrefs`, badge summarising its content, turns red when one of its fields fails validation).

### Binding

Bound the standard UI Toolkit way — `rootVisualElement.Bind(serializedWindow)` plus per-field `PropertyField`s constructed straight from a `SerializedProperty` — except for controls that manage their own `SerializedProperty` reads/writes:

- `CityGeneratorGridPreview` — a `Painter2D` top-down miniature of the grid. In its default `PlazaMultiToggle` mode it doubles as the plaza editor: clicking a block toggles it directly against `general.plazaCells`, a `List<Vector2Int>` of block coordinates, so the picture and the generated scene can never disagree (there is no separate plaza count). In `SingleSelectQuadrant` mode, used per Custom Place entry, clicking picks a single block plus — unless the entry occupies the full block — which quadrant of it was clicked, using the same 0-3 convention as `CityGeneratorBuildingBuilder.SlotOffsets`.
- `CityGeneratorPrefabGrid` — thumbnail grid for `buildingPrefabs`/`vegetation.prefabs`.
- `CityGeneratorWeightedPrefabList` — thumbnail + percentage slider + stacked bar + "Normalize to 100%" for `vehicles`/`pedestrians`. Deliberately never rebuilds its rows on a plain percentage edit, only on add/remove/normalize, because tearing down the dragged `Slider` mid-drag would drop its pointer capture and abort the gesture.
- `CityGeneratorCustomPlaceList` — one self-contained row per Custom Place entry.

**Never use `PropertyField` for a row created after the window's one-time `Bind()` call** — it never binds and renders empty. This was a real regression caught and fixed after the initial SPEC 06 implementation; that is why `CityGeneratorCustomPlaceList` rows are built from plain `TextField`/`ObjectField`/`Toggle`/`EnumField` controls.

### Validation and build buttons

`CityGeneratorValidator.ValidateDetailed` (same checks as the original `Validate`, each issue additionally tagged with the settings path that caused it) is re-run on every edit via `TrackSerializedObjectValue`, driving live required-field/card/tab highlighting and disabling both Build buttons until every issue clears — replacing the old blocking `EditorUtility.DisplayDialog` validation-error flow. A field relocated to a card outside its own settings segment (like `general.playerPrefab` living in the Player card) is resolved through an exact-path alias registered alongside the segment-based lookup.

Two buttons:

- **Build City in New Scene**.
- **Re-Build City in Current Scene** — transactional: builds the new city under a temporary root and only destroys the previous one, found via the `CityGeneratorRoot` marker component rather than by name, once generation finishes without throwing (`CityGeneratorSceneBuilder.RebuildInActiveScene`). Light/camera/player are left alone either way.

Both drive an `EditorUtility.DisplayProgressBar` through an optional `onProgress` callback threaded (additively — default `null`) through `CityGeneratorContentAssembler.Assemble` → `CityGeneratorSceneBuilder`, and show the result in an in-window panel (with a "Ping Scene" button) instead of a dialog. "Reset to Defaults" stays a plain button, low-key styled.

The `settings` field is `[SerializeField] internal`, not `private`, so `Assets/Editor/CityGeneratorSetDefaultsWindow.cs` (outside the package) can read it via the package Editor assembly's `InternalsVisibleTo`.

## Pipeline

In order: `CityGeneratorValidator` → `CityGeneratorSceneBuilder` (new scene + directional light + camera + player, saved as the next free `Assets/Scenes/City<N>.unity`) → `CityGeneratorContentAssembler` (the group hierarchy and every builder) → `Grid` → `GroundBuilder` → `CustomPlaceBuilder` → `BuildingBuilder` → `PlazaBuilder` → `StreetPropsBuilder` → `TrafficBuilder`.

## Builders and utilities

- **`CityGeneratorConstants`** holds the layout numbers (46 m blocks on a 56 m pitch, `GroundDatumY` 0.18, 22 m building slots, lamp/zebra/traffic-light offsets…). Most constants carry a comment explaining *why* that value — several were tuned against real overlap bugs (lamps clearing the plaza lawn, zebra stripes vs. dashed centreline, corner margin so wide prefabs don't collide across a corner). Change them from there, never inline. Player movement/`CharacterController`/camera tuning and pedestrian pace/jitter/stop/crowd tuning used to live here as hardcoded (and, for the pedestrian ones, mostly unreferenced) constants; they are now user-configurable settings (`PlayerSettings`, `CameraSettings`, `PedestrianBehaviourSettings`, `CrowdSettings` in `CityGeneratorSettings.cs`) — don't reintroduce them as constants.
- **Overlap avoidance** is the tool's central mechanism, but only for props, vegetation and Custom Places — buildings and vehicles are deliberately exempt. `CityGeneratorBoundsUtility.GetWorldBounds` combines all child `Renderer` bounds, and `CityGeneratorPlacementEngine` instantiates a candidate and checks its XZ `Rect` against already-placed objects, `DestroyImmediate`ing it if it overlaps. Bounds, not fixed per-category radii, because the prefabs come from the user. `ContentAssembler` threads one growing `obstacles` list through every category in turn — if you add a category, append its result to that list; `obstacles` stays the source of truth. Since SPEC 05 the overlap check queries `CityGeneratorSpatialHash` (a uniform hash keyed by cell, cell size derived from the block size) instead of scanning `obstacles` linearly — the hash is a pure index over `obstacles`, populated alongside it and never a second source of truth (measured -17.2% total generation time on a 10×10 grid; same placement result for a given seed, only the query cost changes).
- **`CityGeneratorPlayerSpawner.FindSpawnPosition`** picks where the player instance lands: inside a plaza block when the city has one (searched in random order across plazas), a random block otherwise, checked against the same growing `obstacles` list (minus ground cover, since standing on lawn/sidewalk is the point) so the player never spawns overlapping a building/prop/vehicle.
- **`CityGeneratorSceneBuilder.ConfigurePlayer`** `AddComponent`s `CharacterController`, `PlayerController` and `PlayerInputAuthority` to whichever prefab is assigned as Player Prefab, if it doesn't already carry them — but then **writes the Player tab's tuning onto the instance unconditionally**, even when the prefab already had its own `CharacterController`/`PlayerController`: the window is the single source of truth, never the prefab asset (which is never touched). This is what lets `DefaultAssets/Prefabs/Characters/` stay 12 clean model+Animator prefabs, and equally lets a user-supplied character work as Player Prefab with zero manual setup. `CreateMainCamera` applies the Camera tab's tuning to the generated `ThirdPersonCamera` the same way (`fieldOfView`, orbit, collision, cursor lock); only the camera's initial transform stays a hand-tuned fixed value: position `(36, 28, -36)`, rotation `Euler(27, -45, 0)`, `fieldOfView` 45.
- **`CityGeneratorBuildingBuilder.BuildBuildings`** picks up to 4 fixed 22 m corner slots per non-plaza block, guaranteeing every assigned building prefab is used at least once. **Which corners are filled is shuffled per block** when `buildingsPerBlock < 4` — a QA-found bug had every block always fill corners `0..buildingsPerBlock-1` in the same order, making partially-built blocks look identical everywhere. Buildings are **not** overlap-checked against each other or against the block edge: an oversized building prefab will visibly clip into its neighbour or spill into the street — accepted as the user's responsibility to size their prefabs to the 22 m slot. Since SPEC 06 it also takes an optional `reservedSlots` set (`(gridX, gridY, slot)`, `slot == -1` meaning the whole block) produced by `CityGeneratorCustomPlaceBuilder`: a reserved corner is excluded from that block's random corner order, a reserved whole block is skipped entirely, and an empty set (the default) reproduces the exact old behaviour.
- **Densities** mean "fraction of valid candidate points filled", not an absolute count — including `lampDensity` (1 = all 3 candidate points per block side).
- **Static flags**: `CityGeneratorContentAssembler` applies `BatchingStatic | OccluderStatic | OccludeeStatic` to every generated group **except `Vehicles`/`Pedestrians`**, so each generated city is batched and ready for a lightmap/occlusion bake with no manual pass — this includes the `CustomPlaces` group, since a Custom Place never moves at runtime. `CarAgent`/`PedestrianAgent` move their instances by transform every frame, which is why both are excluded.
- **Seeding**: `general.useCustomSeed` (off by default) + `general.seed` make generation reproducible; `Assemble` uses `new System.Random(seed)` when enabled, unseeded otherwise. Every builder receives that one `System.Random` **by parameter** — none of them touch `UnityEngine.Random`, so seeding it is enough to make placement and prefab choice fully deterministic (`CarAgent`'s runtime driving still uses `UnityEngine.Random`, unrelated to generation). Which blocks are plazas is **not** part of this: `CityGeneratorGrid.BuildBlocks` takes `general.plazaCells` directly and never touches `random` — it used to draw a random subset here (`ChoosePlazaIndices`), which is why the grid preview couldn't reliably match the generated scene.
- **No `Global Volume`** is generated — removed on purpose (commit `a094fef`) to keep the tool render-pipeline-agnostic.

## Vehicle spawning and the `Vehicle` layer

`CityGeneratorTrafficBuilder.BuildVehicles` calls `EnsureVehicleLayerExists` before spawning anything: if the project has no `Vehicle` layer yet, it creates one itself by writing directly to `ProjectSettings/TagManager.asset` via `SerializedObject`, using the first free slot from `CityGeneratorConstants.FirstUserLayerIndex` (8) up, and logs that it did so. Requiring the user to create this layer by hand was a recurring point of confusion during SPEC 02 verification. Only if every slot 8-31 is already taken does it fall back to warning instead — in that case every instance's `CarAgent.vehicleMask` is left at `0` (Nothing) rather than matching whatever layer the instance happens to share with unrelated scene geometry, so vehicles simply stop detecting each other (they still stop for lights and unsignalled-crossing priority) until a slot frees up.

`CarAgent` and the `Vehicle` layer are added **to the scene instances only**, never to the user's prefab asset, and outer-edge exit nodes are skipped when spawning (a car there has nothing ahead and `CarAgent` disables itself).

When the layer does exist, `BuildVehicles` sets `CarAgent.vehicleMask` to `1 << instance.layer` per instance via `SerializedObject` — **do not rely on the mask baked into a vehicle prefab's own serialized data**: it only happens to work when `Vehicle` sits at the same layer index the prefab was authored against, and silently makes the forward sensor blind to every other vehicle otherwise (found during SPEC 02 verification: the demo prefabs' baked `vehicleMask` and `m_Layer` both happened to reference index 8, which is why the bug went unnoticed).

`CityGeneratorConstants.VehicleDensityWarningThreshold` (0.4 of spawn nodes) is surfaced only as a live `HelpBox` in the window while editing `vehicleCount` — `BuildVehicles` itself no longer logs a console warning past that threshold, since the inspector already told the user before they clicked generate. Measured on a 5×5 grid: 38% of nodes flowed, 76% gridlocked from the first frame.

`CityGeneratorDistributionUtility.DistributePercentages` (a generic largest-remainder distributor) is shared between `BuildVehicles` and `BuildPedestrians` rather than duplicated per category.

## Defaults

- **`CityGeneratorDefaultAssets.ApplyTo`** fills a fresh `CityGeneratorSettings` with the package's own demo prefabs (buildings, vegetation, vehicles and pedestrians with their percentages, ground, plaza prefabs and layout (`plazaCells`), a Custom Places demo entry — a whole-block `Hospital`, `isPointOfInterest = true`, at block `(3, 3)` — props, player, input actions), loaded from hardcoded `Packages/com.santiandrade.citygenerator/DefaultAssets/...` paths, so the window opens ready for a one-click first generation instead of empty required fields. Those paths resolve in any project that installs the package, so this is ordinary portable code. It cannot run from a field initializer on `CityGeneratorSettings` (Unity forbids `AssetDatabase` calls during `EditorWindow` deserialization); it is invoked from `CityGeneratorWindow.OnEnable()`, gated by a serialized `defaultsInitialized` flag so it runs once per window instance, and again from "Reset to Defaults".
- **`CityGeneratorDefaultAssetsWriter.SaveCurrentAsDefault`** is the other direction: given an open window's `settings`, it regenerates `CityGeneratorDefaultAssets.cs`'s `ApplyTo` body wholesale (asset lists can change length between calls, which a targeted text edit can't express as cleanly as a full rewrite) and patches the scalar field initializers in `CityGeneratorSettings.cs` in place via `Regex` (safe because every scalar field name — `gridWidth`, `vehicleCount`, `density`… — is unique within that file). Both are plain `File.WriteAllText` calls against the package's own source under `Packages/`, followed by `AssetDatabase.Refresh()`. Kept in its own file rather than folded into `CityGeneratorDefaultAssets` because it overwrites that file's contents — it must never need to regenerate itself. A prefab assigned from outside `DefaultAssets/` still gets written into the new default (the command never blocks on it), but the result only resolves in this project; flagged with a console warning per offending field rather than silently accepted. The `[MenuItem("Tools/City Generator/Set Current Selection As Default")]` entry point that calls it lives outside the package, in `Assets/Editor/CityGeneratorSetDefaultsWindow.cs`.
