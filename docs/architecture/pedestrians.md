# Pedestrian system

Detail behind the "Pedestrian system" bullet of the root `CLAUDE.md`. Added by `specs/03-pedestrian-network.md`, structurally mirroring the vehicle traffic system (`runtime-and-traffic.md`) throughout.

## `PedestrianNetwork.cs`

An **undirected** graph (unlike `TrafficNetwork`'s directed one: a pedestrian can walk either way along every edge), rebuilt in `Awake`/`Build()` from the same street axes.

- Every block gets an 8-node ring (4 corners + 4 side midpoints) sitting in the gap between the building slot edge and street furniture.
- Every intersection with a real `TrafficLightIntersection` nearby (any with at least 3 real street arms — a full 4-way, or a T-intersection including along the grid/shape's own border; a perimeter corner with exactly 2 perpendicular arms never gets one, since a car arriving there has only one possible way through) additionally gets, per real arm, a curb → crossing → curb chain linking two ring corners across the street, with the crossing node matched **by geometry** (nearest `TrafficLightIntersection`, same convention as `TrafficNetwork`'s light matching, within a 14 m cutoff) so `CanCross` can read the real light state via `TrafficNetwork.AxisState`/`IsAxisGreen` (`TrafficLightIntersection.EastWestState`/`NorthSouthState`). `BuildCrossings` is called for every axis intersection (not just strictly interior ones) but skips any arm whose neighbouring block is out of range or a Custom Grid shape hole (`BlockExists`), and the 14 m cutoff means an unsignalled corner simply finds no match — widening the loop can't add a crossing where there's no real light.
- `CanCross` only allows stepping onto the road on **Red**, not just "not green" — Amber still has cars moving through.
- `FindPath` is a zero-allocation BFS into caller-supplied buffers (shortest by hop count, since every edge is unweighted).
- A city with **no signalled intersection at all** (`CityGeneratorTrafficBuilder.HasSignalledIntersection`) gets no crossings, so every block's ring is isolated — surfaced as a non-blocking `HelpBox` in `CityGeneratorWindow` (`GetIsolatedBlocksWarning`), same convention as the vehicle density warning. Note this is *not* the case for a `gridWidth == 1`/`gridHeight == 1` grid: it has no strictly interior intersection, but SPEC 11's border T-intersections are signalled and do get crossings (a measured 1x2 city: 6 lights, 6 `Crossing` nodes, one single connected component). The warning tested the old `gridWidth > 1 && gridHeight > 1` rule until that was unified.
- `Build()` wipes `nodes` from scratch every call (Awake in Play, or an explicit re-bake) and rebuilds four node kinds: `Ring`, `Curb`, `Crossing`, and (SPEC 10) `Interior` — nothing else the generator adds to this graph after `Build()` returns. SPEC 06 removed the one thing that used to (the Point of Interest machinery); see below.
- **The perimeter walkway** (SPEC 11, `BuildBorderWalkway`) covers the sidewalk band that closes the city at its outer contour — see [editor-tool](editor-tool.md), "The outer contour". Without it, that sidewalk would exist but be unwalkable, and the outward crosswalk already painted at every border T-intersection would lead nowhere. It is tiled from the **missing** cells around the city, mirroring the ground band's own decomposition: each contributes a 3-node strip towards every real neighbour it has, stitched into one contour by position (a dictionary keyed to a decimetre), so an inner corner shares one node between its two strips and an outer corner gets its own node joining the two strips that pass it. Nodes are `Ring`: pedestrians spawn on and walk to the perimeter like any other sidewalk.
- **Border crosswalks**: `BuildCrossings` used to skip any arm whose block was off the grid or a Custom Grid hole. It now skips only an arm with **no** block on **either** side; a side with no block resolves to the nearest perimeter walkway node instead of a ring corner (`FindBorderNodeNear`, within `perimeterLinkRadius`). Since a crosswalk arm still needs a matched `TrafficLightIntersection`, this adds one only at a real 3-arm border T-intersection — exactly where the zebra stripes were already painted. Build order matters: `BuildBorderWalkway` runs **before** the crossings pass.
- The perimeter walkway is a single connected contour but is only tied into the block network through those border crosswalks, so a city with no signalled intersection at all (a 1×1 grid, a single-cell custom shape) leaves it as its own connected component. That degrades exactly like the pre-existing isolated-ring case: `PickRandomDestination(requiredComponent)` keeps a pedestrian drawing destinations it can actually reach.
- SPEC 10 (`Interior`): every normal block **without** a full-block Custom Place (`BlockCell.isPlaza == false` and no `reservedSlots` entry with `slot == -1`) gets a 5-node `Interior` cross (block centre + 4 arm midpoints), connected to that block's own 4 `Ring` midpoint nodes — a shortcut through the block's interior, not a full walkable area. A plaza block (`BlockCell.isPlaza == true`) or a block with a full-block Custom Place gets neither — pedestrians stay confined to the ring around them. Per-block flags (`blockIsPlaza`/`blockIsFullyReserved`, flattened `[bi, bj] -> bool` arrays) are computed by `CityGeneratorPedestrianBuilder.AddNetworkComponent` from `BlockCell`/`reservedSlots` (both Editor-only types `PedestrianNetwork.Build()` must not reference directly) and written via `SerializedObject`, mirroring every other field `AddNetworkComponent`/`AddManagerComponent` wire in.
- A block's `Interior` nodes tie into its `Ring` midpoints at exactly the same hop-count a same-block `Ring`-only route already has (e.g. the south and north midpoints are 4 hops apart either way around the ring, and also 4 hops via the interior cross), so `FindPath`'s BFS — which resolves same-length ties in favour of whichever edge was built first, always the ring — would never actually route a pedestrian through it **as an intermediate waypoint**: detouring into an Interior pocket and back out always costs more hops than continuing along the street/ring grid, so BFS only ever enters one when it's the trip's actual endpoint. `PlanNewDestination` (below) is what decides that endpoint, and is where SPEC 10's fixes live.

**SPEC 16 — coordinates relative to the root, and hierarchy-scoped matching.** `BlockCentre`/`BlockCentreOutside` and the corner/arm points built by `BuildBlockRing`/`BuildInteriorCross`/`BuildBorderWalkway`/`BuildCrossings` are all projected through `transform.TransformPoint` before becoming a node's `Position`, exactly like `TrafficNetwork` (only translation of the root is supported/verified — see the user manual). `Build()` resolves both its `TrafficLightIntersection` matches and its fallback `TrafficNetwork` reference (used by `CanCross`) scoped to its own `GetComponentInParent<CityGeneratorRoot>()` hierarchy (`FindIntersectionsInScope`/`FindTrafficNetworkInScope`), falling back to a scene-wide search only when there is no `CityGeneratorRoot` ancestor. Without this, two cities placed at the exact same world position — or simply close enough for the 14 m cutoff to overlap — could match a crossing to the wrong city's traffic light, or worse, silently share one city's `TrafficNetwork` for `CanCross` on both.

SPEC 05 added two performance structures, both recalculated inside `Build()`:

- **Connected components** (`nodeComponent`, a flood fill over the finished ring/crossing edges, one entry per node, read via `ComponentOf`) — `PedestrianAgent.PlanNewDestination` filters candidates to the origin's component before attempting a route, so an isolated single-block ring never wastes a BFS on an unreachable node.
- A **short-lived BFS tree cache** (`cameFromCache`, keyed by origin node, invalidated on every `Build()`) so several pedestrians planning from nearby origins in the same frame window don't each repeat the same BFS.

## Obstacle pruning

Pedestrian obstacle avoidance is **purely physics-based, on `Collider` alone** — an obstacle with no `Collider` anywhere in its hierarchy is invisible to it and every node stays walkable through/on top of it. This is a deliberate invariant (see "History" below), not an oversight: a `Collider` is what any object uses to declare "I am physically here," so pedestrian routing treats exactly that as the source of truth, nothing else, one path, no fallback.

Two facets of the same check, both `PedestrianNetwork.PrunePlacedObstacles` (`Physics.CheckSphere` at each node's position against `obstacleMask`, plus a downward raycast to require actual ground beneath it):

1. Runs automatically at the end of every `Build()`/`BuildFromBlockCells()` call, including the one `CityGeneratorPedestrianBuilder`/`CityGeneratorContentAssembler` make right after placing every other category (buildings, props, traffic lights, Custom Places) — so by the time it runs, every real obstacle already has its final `Collider` in the scene, generation-time and Play-mode-time agree, and there is no separate "generation-time" pass to keep in sync with it.
2. The same method exposed as `[ContextMenu("Prune Placed Obstacles")]` / `Tools > City Generator > Rebuild Pedestrian Network` for an explicit re-bake without entering Play (e.g. after hand-editing the scene).

It iterates `network.NodeCount` generically, so `Interior` nodes (SPEC 10) get exactly the same pruning as `Ring`/`Curb`/`Crossing` with no pipeline changes — a quarter-slot Custom Place blocks any node that lands on it, provided it has a `Collider`.

**Consequence for content authors**: a Custom Place, custom pedestrian prefab, or any demo asset that should block pedestrian routes **must** have a `Collider` somewhere in its hierarchy. A purely visual object (no `Collider,` e.g. flat decals, a decorative mesh with no gameplay purpose) is correctly treated as walkable-through — if that's wrong for a specific asset, the fix is to add a `Collider` to it, not to change this system.

### History: the removed rect-based "level 1" (fixed 2026-09-02)

There used to be a second, coarser pass (`CityGeneratorPedestrianBuilder.PruneNodesAgainstObstacles`) that ran once at generation time, before the physics pass existed as a safety net for a `Collider`-less obstacle (which physics structurally can't see): it checked every obstacle's XZ rect (`ObstacleCache.GetRect`, the *full renderer bounds* of the obstacle's whole hierarchy — the right measure for spacing buildings apart at placement time) via a plain `Rect.Contains(point)`.

Found via SPEC 12 QA: that rect is far wider than an object's solid footprint whenever anything sticks out visually without being solid (a balcony, a canopy, a sign arm, a lawn/vegetation patch with no `Collider` at all) — checking every obstacle against it, on top of the precise physics check, blocked sidewalk nodes nowhere near anything solid. In one generated city ~35% of all nodes came back `Blocked` from this rect check alone, while a fresh `PrunePlacedObstacles()` pass against the exact same scene found zero real overlaps. It barely showed with normal pedestrians (spread across hundreds of nodes, a handful going missing is invisible), but a Custom Pedestrians entry restricted to a small hand-traced route (as few as 8 `Ring` nodes) could have *every one* of its nodes wrongly blocked at once, silently spawning 0 instances for that entry — and non-deterministically, since `General > Use Custom Seed` off means which obstacle lands where (and whether its rect happens to reach a given node) changes on every rebuild.

First fix attempt: keep the rect check but only for obstacles with no `Collider` (the one case physics can't see), skipping it for anything that has one. Given the project's own demo vegetation is itself `Collider`-less by design, this narrower check still over-blocked identically — so the maintainer's call was to drop the rect-based safety net entirely rather than special-case it further: an obstacle with no `Collider` is now simply never treated as a pedestrian obstacle, full stop — pushing the "add a `Collider` if you want this to block pedestrians" responsibility onto content authors instead of the generator guessing from render bounds.

This rect-based over-blocking was real and worth fixing on its own, but it turned out **not** to be what was causing the specific symptom that surfaced it (a Custom Pedestrians entry with a small route intermittently spawning 0 instances on "Re-Build City in Current Scene", roughly every other rebuild): after removing the rect check entirely, the exact same intermittent failure kept reproducing. The actual cause was unrelated to obstacle detection at all — see [editor-tool](editor-tool.md)'s "Re-Build City in Current Scene" bullet: the previous city stayed in the same world-space footprint as the one under construction for the whole rebuild, and two stacked sets of colliders made the ground raycast below intermittently fail. Both fixes stand on their own merits; neither is a substitute for the other.

## `PedestrianAgent.cs`

Walks the graph destination to destination, moving by transform (no `CharacterController`/`Rigidbody`, mirroring `CarAgent`), driving the same `Speed`/`Grounded` Animator parameters `PlayerController` uses so it shares `CharacterAnimator.controller`'s Locomotion blend tree unmodified.

Every `Animator.SetFloat`/`SetBool` call is guarded by a `hasAnimatorController` flag cached in `Awake` — a pedestrian prefab with no `Animator`, or an `Animator` with no controller assigned, still walks fine, but calling `SetFloat`/`SetBool` on it would otherwise spam a console warning every frame.

Waits at a curb (`WaitingToCross` state) until `CanCross` clears. `PlanNewDestination` rolls several random candidate destinations and tries them **farthest-first** (by straight-line distance from the pedestrian's current position), not just the single farthest one — a grid-corner block with only one link to the rest of the network would otherwise almost always draw an unreachable "farthest" candidate and idle forever.

SPEC 10: any drawn `Interior` candidate is tried **first, in draw order** (no distance ranking) instead of competing in that same farthest-first sort — a point on the boundary of any spatially localized area is, by definition, at least as far from any approach direction as a point at its centre, so ranking it by raw distance meant a chosen destination inside one was almost never actually deep inside it, only ever its outer edge. `Ring` candidates are unaffected, still sorted farthest-first exactly as before.

Every serialized field on it (`walkReferenceSpeed`/`runReferenceSpeed`, `paceFraction`, `runnerChance`, jitter, stop durations…) is written unconditionally onto each generated instance by `CityGeneratorPedestrianBuilder.BuildPedestrians` from `CityGeneratorSettings.pedestrianBehaviour` (Pedestrians tab, Behaviour card) — the script's own field initializers only matter for a `PedestrianAgent` used standalone.

Since SPEC 05, `FindPath`'s output buffers are rented from `PedestrianManager`'s `PedestrianPathBufferPool` for the duration of planning rather than kept as a permanent per-agent array sized to the whole graph, and the agent's first `PlanNewDestination` after spawn is deferred by `PedestrianManager`'s staggering instead of firing in `Start`.

## Custom Pedestrians (SPEC 12)

A distinct budget from the general `pedestrianCount`: each `CustomPedestrianEntry` (title, prefab, count, `selectedNodeIndices`) confines its spawned `PedestrianAgent`s to a hand-traced subgraph instead of letting them roam the whole city.

- **Restriction mechanism**: `PedestrianNetwork.PickRandomDestination`/`FindPath` gained an optional `IReadOnlyList<int> allowedNodes` parameter (default `null`, identical behaviour to before this spec). A restricted `FindPath` call bypasses the shared `cameFromCache` entirely (`ComputeRestrictedCameFrom`) — that cache is keyed by origin alone and shared across every agent, so a route restricted to one entry's subgraph is never a valid cache entry for anyone else. `PedestrianAgent` carries the subset as `[SerializeField] private List<int> allowedNodes` (must be `[SerializeField]`, same reasoning as `PedestrianNetwork.useCustomShape` — a plain field is wiped to `null` by the domain reload that precedes entering Play mode, silently turning every Custom Pedestrian back into an unrestricted one) and passes it through in `PlanNewDestination`; when set, the connected-component filter (`ComponentOf`) is skipped too, since it reflects the whole graph's topology, not the restricted subset's — the subset is validated to already be one connected component before it's ever assigned.
- **Gotcha — Unity never leaves a `[SerializeField] List<T>` null**: every normal (non-Custom) pedestrian's `allowedNodes` deserializes as an *empty* `List<int>`, not a `null` reference, even though it's never assigned — confirmed directly via the MCP inspector (`arrayLength: 0`, not a null object reference). `PlanNewDestination` therefore never compares `allowedNodes == null` directly; it first collapses null-or-empty to a local `null` (`restriction`) and uses that everywhere, or every normal pedestrian in the scene would call `PickRandomDestination`/`FindPath` with an empty (rather than absent) restriction and never find a destination — this shipped broken once (SPEC 12's initial merge) and stalled every pedestrian, custom or not.
- **`CityGeneratorPedestrianPreview.cs`** (Editor): builds a disposable, `HideFlags.HideAndDontSave` preview of the pedestrian graph for the *current* settings, so the picker can show real node positions/adjacency before the city is ever generated. Reuses the real generation code — `CityGeneratorTrafficBuilder.BuildTrafficLights` (placement only, no vehicles) plus `PedestrianNetwork.Build()`/`BuildFromBlockCells()` — rather than a parallel reimplementation, so the picker's graph can only diverge from a real generation if the pipeline itself changes the order it calls those pieces in. `CityGeneratorCustomPlaceBuilder.ResolveReservedSlots` (extracted from `BuildCustomPlaces`, same `TryResolveEntry` resolution) supplies which blocks are fully reserved without instantiating any real Custom Place prefab into the throwaway preview. `Fingerprint()` (node count + a rounded-position hash) and the static `ComputeSettingsSignature(CityGeneratorSettings)` are the two cache keys the UI layer uses (see below); without a Traffic Light Prefab assigned yet, the preview simply has no `Curb`/`Crossing` nodes, matching what a real generation without one would produce.
- **Picker UI — zones, not raw nodes (2026-09-02 redesign)**: `CityGeneratorGridPreviewMode.NodeGraphPicker` (`CityGeneratorGridPreview.BindNodeGraph`) no longer draws one clickable point per real node — a normal block's 8 Ring + 5 Interior nodes, plus Curb/Crossing at every signalled arm, made individual nodes too small and too dense to click reliably once a city had more than a couple of blocks. Instead it groups the preview's graph into clickable **zones**, each a polyline fit to the same world-space bounding box, derived purely from node `Kind`/degree (never from block bookkeeping the picker has no access to, so it works identically for the rectangular grid and Custom Grid): a **Ring edge** is any single real edge between two `Ring` nodes (2 nodes/zone — 8 per normal block ring, plus however many the perimeter walkway strips add); an **Interior spoke** is a spoke-centre node (`Interior`, 4 `Interior` neighbours) paired with one arm and that arm's non-centre neighbour (3 nodes/zone — 4 per block with an Interior cross, none for a plaza/full-block-reserved block); a **crossing** is a `Crossing` node (2 `Curb` neighbours) expanded one more hop each side to the two `Ring` nodes it connects (5 nodes/zone — one per signalled crossing arm, none without a Traffic Light Prefab assigned). A zone counts as *selected* only when every one of its underlying nodes is in `selectedNodeIndices`; a click adds a zone only if the selection is empty or the zone shares at least one node with it (zones only ever touch at a shared real node, so this is exactly the old "direct neighbour" rule generalized), and a click on a selected zone removes its nodes *except* any still owned by another zone that stays fully selected, then runs the same `KeepLargestConnectedComponent` flood fill as before. `selectedNodeIndices` itself is unchanged — still raw node indices — so `CityGeneratorCustomPedestrianBuilder`/`CityGeneratorValidator`/runtime code never know zones exist; this is purely a `CityGeneratorGridPreview` presentation concern. `CityGeneratorCustomPedestrianList` (mirrors `CityGeneratorCustomPlaceList`) owns one shared preview instance across every row, rebuilt only when `ComputeSettingsSignature` actually changes (building it runs real generation code, so this cache is load-bearing, not an optimization to skip) — `CityGeneratorWindow.OnDisable`/`ResetToDefaults` dispose it so the hidden preview `GameObject` never leaks.
- **Invalidation**: every entry also carries `graphFingerprint` (an `int`, the preview's `Fingerprint()` value as of the last time its selection was edited). `BindNodeGraph` compares it against the current preview's fingerprint every time a row is (re)bound (i.e. on essentially every settings change, since `CityGeneratorCustomPedestrianList.RefreshPreview` runs from `CityGeneratorWindow.RefreshDynamicUi`) and clears a mismatched, non-empty selection immediately rather than only "on next picker open" — strictly safer than the minimum the spec called for, since it can never silently generate over the wrong nodes. `CityGeneratorValidator.ValidateCustomPedestrians` then reports the now-empty selection through the same "needs at least 2 connected nodes" blocking issue every other incomplete entry gets.
- **`CityGeneratorCustomPedestrianBuilder.cs`** (Editor): runs in `CityGeneratorContentAssembler` after the *real* `PedestrianNetwork` (never the preview) is built and pruned, independent of `includePedestrians`/`pedestrianCount` — mirrors `CustomPlaceEntry` not being gated by any general toggle. Spawns `count` copies per valid entry across that entry's `Ring` nodes (same criterion as a normal pedestrian spawn), configures each `PedestrianAgent` with the same `pedestrianBehaviour` fields `BuildPedestrians` writes, and calls `PedestrianAgent.SetAllowedNodes`. Ensures a `PedestrianManager` exists (creating one via `AddManagerComponent` if `includePedestrians` was off) since Custom Pedestrians register with it exactly like any other agent.
- **Validation**: `CityGeneratorValidator.ValidateCustomPedestrians` — title, prefab, `count >= 1`, at least 2 selected nodes, and (via a flood fill over the real graph, reusing the caller's already-current preview when one is passed in — `CityGeneratorWindow` passes `CityGeneratorCustomPedestrianList.CurrentPreview` — to avoid building a second one on every keystroke) that the selection is a single connected component.

## `PedestrianPathBufferPool.cs` (SPEC 05)

A plain pool of `int[]` buffers sized to `PedestrianNetwork.NodeCount`, constructed by `PedestrianManager` in `OnEnable`. Exists because the old per-agent permanent buffer was O(pedestrians × nodes) of memory; now that initial planning is staggered across frames, only a small subset of agents is planning at any one instant, so a shared pool sized to the graph is enough. `PedestrianAgent.PlanNewDestination` calls `Rent`/`Return` around its `FindPath` calls.

## `PedestrianManager.cs`

Ticks every registered `PedestrianAgent` from one central `Update` (`Register`/`Unregister`, called from each agent's `OnEnable`/`OnDisable`), same convention as `TrafficManager`/`CarAgent` (not a scene-global singleton either — `PedestrianAgent` resolves it via `network.Manager`), with the same far-from-camera decision-logic staggering above `staggerMinAgentCount`.

On top of that it rebuilds a coarse spatial grid every frame and applies a small local separation nudge between nearby agents, plus a stronger player-avoidance nudge — the only peer-interaction mechanic implemented so far (a `PedestrianState.Interacting` value exists on the enum but is never entered, reserved for a future spec). `PedestrianAgent` has **no jam/gridlock mechanics of its own** — crowding only ever shows as this separation nudge, never a stuck agent — which is why `CityGeneratorConstants.PedestrianCountWarningThreshold` is deliberately much higher than the vehicle one. Pedestrians still only ever spawn on `Ring` nodes, but since SPEC 10 the threshold is measured against the network's **total** node count (`PedestrianNetwork.NodeCount`/`CityGeneratorWindow`'s validation-time estimate of it) rather than just the `Ring` count — `Ring` alone stopped representing the block's real walkable capacity once `Interior` nodes exist. `CityGeneratorPedestrianBuilder.AddManagerComponent` configures every field on the generated instance from `CityGeneratorSettings.crowd` (Pedestrians tab, Crowd card).

SPEC 05 changes: it owns the `PedestrianPathBufferPool`; it staggers each agent's first `PlanNewDestination` by spawn index across several frames instead of firing every agent's initial plan in the same `Start`; its separation pass processes each nearby agent pair once instead of twice (once per side) and skips a pair entirely when neither side is "active" this frame under the existing sensor staggering; and it rebuilds `PedestrianRoadProximityGrid` once per frame, passing in the resolved player `Transform` separately since the player isn't a `PedestrianAgent`.

## `PedestrianRoadProximityGrid.cs` (SPEC 05)

A uniform spatial grid of registered `PedestrianAgent` positions, rebuilt once per frame by `PedestrianManager` and queried by `CarAgent.pedestrianMask` sensing (above `staggerMinAgentCount` pedestrians) instead of `SphereCastNonAlloc`. The **player** is not a `PedestrianAgent` (it's the manually-driven player instance, sharing the `Pedestrian` layer) so it can't be bucketed like one; `PedestrianManager` passes the resolved player `Transform` into `Rebuild` separately, and the grid tracks it via `TryGetPlayerPosition`, checked alongside the bucketed query so cars keep braking for the player once this grid takes over from the `SphereCast` fallback.

## Generation and layers

`CityGeneratorPedestrianBuilder` mirrors `CityGeneratorTrafficBuilder`: the `PedestrianNetwork` graph is always built and pruned against the shared `obstacles` list, **independent of `includePedestrians`**, so its crossings stay wired to the real traffic lights even when no NPCs are spawned; NPC instances are only placed when `includePedestrians` is on.

Vehicles brake for pedestrians (and for the player) via `CarAgent.pedestrianMask` and a second, independent forward sensor (`PedestrianAheadClearance`) feeding the same `StopReason.VehicleAhead` braking branch — no dedicated state. `EnsurePedestrianLayerAndAssignMask` creates the `Pedestrian` layer the same fail-closed way `EnsureVehicleLayerExists` creates `Vehicle` (first free slot from `FirstUserLayerIndex`, warns and leaves the mask at `0` if none is free) and sets `pedestrianMask` per vehicle instance, exactly like `vehicleMask`. It is called whenever vehicles exist (not gated on `includePedestrians`), since `CityGeneratorSceneBuilder` puts the **player** on this same `Pedestrian` layer and vehicles must detect it either way.

`PedestrianAgent` itself never gets pushed back by its own collider since it moves by setting `transform.position` directly. The `DefaultAssets/Prefabs/Characters/` prefabs double as the default pedestrian list, evenly weighted, and are the same prefabs offered as Player Prefab.

## Animator culling mode — a rigid-rig prefab needs `Always Animate`

`CityGeneratorPedestrianBuilder.ApplyAnimatorCullingMode` (called from both `BuildPedestrians` and `CityGeneratorCustomPedestrianBuilder`) sets each instance's `Animator.cullingMode` based on whether it has a `SkinnedMeshRenderer` anywhere in its hierarchy: `Cull Completely` when it does, `Always Animate` when it doesn't. `Cull Completely` decides whether to keep simulating the state machine from a visibility check that's built around `SkinnedMeshRenderer`; a rig assembled from plain per-part `MeshRenderer`s instead (each limb its own rigid mesh, e.g. `DefaultAssets/Prefabs/Pets/`) never gets flagged visible under it, so its Animator permanently freezes at whatever pose it had when spawned — `SetFloat`/`SetBool` keep writing every frame with no console warning, only the state time itself never advances. This shipped broken once (the Pets prefabs sat at `Cull Completely`, inherited from the human `Characters/` convention, until the freeze was diagnosed live via `Animator.GetCurrentAnimatorStateInfo(0).normalizedTime` staying constant across frames). **A new pedestrian prefab whose model isn't skinned needs this function to see it get `Always Animate` — don't hardcode `Cull Completely` for pedestrians again.**

A second, independent gotcha hits the same symptom from the model-import side: an FBX's auto-generated take-based clips (`ModelImporter.clipAnimations` empty in the `.meta`, so Unity splits by take name with **`Loop Time` off by default**) leave the state's `normalizedTime` climbing forever while the sampled pose clamps to the clip's last frame after one pass — a walk cycle under a second looks statically frozen almost all the time, indistinguishable at a glance from the culling freeze above but requiring a completely different fix (`ModelImporterClipAnimation.loopTime`/`loopPose`, not `Animator.cullingMode`). `DefaultAssets/Prefabs/Characters/` doesn't hit this because its FBX importers were already reconfigured to loop `idle`/`walk`/`sprint`/`fall`/`crouch`/`static` (`demo-content.md`); a newly-added FBX (again, `Pets/`) needs the same treatment explicitly — check `AnimationClip.isLooping` (or `UnityEditor.AnimationUtility.GetAnimationClipSettings(clip).loopTime`) on every clip a Locomotion blend tree references before assuming a "not animating" report is the culling bug above.

## Points of Interest — removed

Benches and the plaza centerpiece (`PlazaSettings.benchPrefab`/`centerpiecePrefab`) are plain visual props placed by `CityGeneratorPlazaBuilder`, exactly like a lamp or a bin — **not** wired into `PedestrianNetwork` in any way.

They used to register `PointOfInterest` nodes that pedestrians would occasionally walk to and linger at; SPEC 06 removed that entire mechanism (node kind, descriptor, register/connect methods, and `PedestrianBehaviourSettings.poiStopDurationMin`/`Max`) at the user's request, to decouple POIs from pedestrians ahead of the minimap/POI system SPEC 07 built on Custom Places instead (`CustomPlaceEntry.isPointOfInterest` → the Minimap HUD — see `custom-places.md` and `editor-tool.md`'s "Minimap" section). **Don't reintroduce a pedestrian-side POI stop without a new spec.**
