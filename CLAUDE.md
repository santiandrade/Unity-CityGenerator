# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a Unity project (`Test AI`) using Unity Editor version `6000.5.8f1` and the Universal Render Pipeline (URP). It started from Unity's default 3D template and a library of FBX model assets under `Assets/Models`. It now has a single scene, `Assets/Scenes/City.unity`, holding a city with working traffic, plus the playable third-person character walking around it.

The scene used to be a loose sea of ~1000 ProBuilder objects; it has since been **fully converted to prefab instances**. Every piece of geometry in `City.unity` is now an instance of a prefab under `Assets/Prefabs/` — the scene itself only contains 27 plain GameObjects (the city root, its 11 group empties, the 8 `Block_*` empties, the 4 intersection empties, camera, light and volume) and no `MeshFilter`/`MeshCollider` of its own.

**The project's current focus is the City Generator tool** (branch `spec-01-city-generator-tool`, 15 commits ahead of `main`, not yet merged): an Editor window that generalises the hand-built `City.unity` into a procedural generator, distributable as a standalone package. Implementation and manual QA are both complete. `City.unity` is now the *reference city* the generator reproduces — see "The City Generator tool" below. Its spec lives in `specs/01-city-generator-tool.md` (written in Spanish, driven by a `/spec-*` workflow configured by `specs/.spec-config.yml`); read it before touching the tool, it records the decisions taken **and explicitly discarded**, including several found and fixed during manual QA after the initial implementation.

The repository is initialized (branch `main`, remote-less history starting at `Initial commit: Unity SmallCityDemo project`).

## Structure

- `Assets/Scenes/City.unity` — **the only scene committed so far** (it was named `City3` while being built, and the earlier `SampleScene` has been deleted); the generator writes further ones as `Assets/Scenes/City<N>.unity`. Roots: `City` (the city root; the `City3` name is gone from the scene too), a `Player` instance of `Assets/Prefabs/Characters/Player.prefab`, `Main Camera` (has `ThirdPersonCamera`), `Directional Light`, and `Global Volume`. There is no `Plane` ground any more — the character stands on the city's own road and sidewalk geometry, which is what carries the colliders.
- Build Settings now list `Assets/Scenes/City.unity` as the only (enabled) scene — the stale `SampleScene` entry has been removed, so builds and `SceneManager.LoadScene` work.
- `Assets/Prefabs/` is organised by category: `Buildings/`, `Characters/` (`Player.prefab`), `Floors/` (the ground/road/marking slabs), `Props/`, `Vegetation/` (`Tree.prefab`) and `Vehicles/`. Note `Player.prefab` moved from the `Prefabs/` root into `Prefabs/Characters/`.
- `Assets/Prefabs/Characters/Player.prefab` — the playable character. Built on `character-male-d.fbx`, with `CharacterController` (radius 0.2, height 0.72, center (0, 0.36, 0) — sized to the model's actual bounds, not Unity's 2 m default), `Animator` (uses `PlayerAnimator.controller` and the FBX's own Avatar), and `CityGenerator.Runtime.PlayerController`.
- `Assets/CityGenerator/Runtime/PlayerController.cs` — walk/run/jump via the new Input System (`InputSystem_Actions.inputactions`, `Player` action map: `Move`, `Sprint`, `Jump`). Movement direction is relative to the camera. Drives the Animator's `Speed`, `Grounded`, `Jump`, `VerticalSpeed` parameters.
- `Assets/CityGenerator/Runtime/ThirdPersonCamera.cs` — Mario-64-style orbit camera. Reads `Look` from the same action map. Only the target-follow *position* is smoothed (`SmoothDamp`); rotation is recomputed every frame as `LookRotation` from the camera's actual (possibly lagging) position to the pivot, so camera position and where it looks can never desync — do not reintroduce separate smoothing on `transform.rotation`, that was tried and caused visible motion sickness. Pivot offset from the target is configurable via `verticalOffset` and `horizontalOffset` (the latter applied along the orbit's local right axis, i.e. an over-the-shoulder offset), not a single `Vector3` offset. Has camera-vs-environment `SphereCast` collision.

### The city (the `City` root in `City.unity`)

- Layout is unchanged from when it was built with ProBuilder primitives via `Unity_RunCommand` editor scripts: a 56 m grid, street axes at x/z ∈ {-84, -28, 28, 84}, nine 46 m blocks centred on {-56, 0, 56}, city extent ±90. Grouped as `Roads`, `Sidewalks`, `RoadMarkings`, `Buildings`, `TrafficLights`, `StreetLights`, `Plaza`, `Trees`, `Props`, `Vehicles`, `TrafficNetwork`. Block tops sit at y = 0.18 (sidewalk thickness), which is the ground datum every prop is placed on. The centre block is a plaza (lawns, fountain, benches).
- **The geometry is now 345 prefab instances, not loose meshes** (346 counting the `Player` at the scene root). Exact census, by group:
  - `Roads` — a single `Road_Base` instance of `Floors/RoadBase.prefab`, one 180 × 0.1 × 180 asphalt slab at y = -0.05 covering the whole city (it replaced the per-street road strips).
  - `Sidewalks` — 9 `Sidewalk_r_c` instances of `Floors/RoadSidewalk.prefab`, one 46 × 0.18 × 46 slab per block at y = 0.09 (so its top is the y = 0.18 datum).
  - `RoadMarkings` — 96 `Dash_H|V_*` (`Floors/RoadDash.prefab`) and 80 `Zebra_*` (`Floors/RoadZebra.prefab`), all at y = 0.012, with no collider.
  - `Buildings` — 8 `Block_*` groups, 32 building instances (see below).
  - `Plaza` — 4 `Lawn_*` (`Floors/Lawn.prefab`, 19 × 0.12 × 19), 4 `Bench_*` and one `Fountain`.
  - `Trees` — 44 instances of `Vegetation/Tree.prefab` (32 `Tree_Street_*`, 12 `Tree_Plaza_*`).
  - `StreetLights` — 32 `Lamp_H|V_*` instances of `Props/Lamp.prefab`.
  - `TrafficLights` — 4 `Intersection_±28_±28` empties, 4 `TrafficLight_*` instances each.
  - `Props` — 4 `Bin_*` and 4 `BusStop_*`.
  - `Vehicles` — 18 car instances (see below).
- The floor/prop prefabs are still ProBuilder-authored (they keep their `ProBuilderMesh` component), so **each instance stores its regenerated mesh as a scene-local override**: `City.unity` holds ~637 embedded `pb_Mesh*` assets referenced through `propertyPath: m_Mesh` modifications on the prefab instances. That is expected — do not "clean up" those meshes, and expect the scene file to churn when ProBuilder rebuilds them.
- Colliders were deliberately simplified: `RoadBase`, `RoadSidewalk`, `Lawn`, `Bench` (2), `Lamp` (3) and `TrafficLight` (4) use `BoxCollider`s; only `Tree` keeps `MeshCollider`s (2, trunk and crown). Road markings (`RoadDash`, `RoadZebra`) have no collider at all.
- New props since the greybox pass: `Props/Bin.prefab` (Body + Lid, `MetalDark`), `Props/BusStop.prefab` (Roof, BackPanel, two posts, and a **nested `Bench.prefab` instance** — editing `Bench` changes bus stops too) and `Props/Fountain.prefab`, which is the only imported-model prop: its body is the mesh and embedded materials of `Assets/Models/Props/Fountain by Poly.glb` (glTFast import), at root scale 0.65, with three ProBuilder `Water` discs added on top.
- The `Buildings` group: its 8 `Block_*` groups hold 32 instances of the modelled prefabs in `Assets/Prefabs/Buildings/` (`Building-A`, `-F`, `-I`, `-M`, `-Skyscraper-C`, `-Skyscraper-E`), replacing the original ProBuilder greybox blocks. One instance per 22 m slot inside each block (positions unchanged, y = 0.18), prefab picked at random with every prefab guaranteed at least once, and a random 90° yaw. The prefabs are authored at root scale 10 with the pivot at the base and their own collider, so they are dropped in as-is; the widest footprint (~13.9 m) still clears the 22 m slot spacing.
- `Assets/CityGenerator/Runtime/TrafficLight.cs` / `.../TrafficLightIntersection.cs` — the traffic lights. `TrafficLight` swaps lamp materials (`LightRed`/`LightAmber`/`LightGreen`/`LightOff`) to show its state; `TrafficLightIntersection` runs the coroutine that alternates green between its `eastWest` and `northSouth` groups with amber and all-red phases. The four inner intersections each have 4 lights, wired up by editor script through `SerializedObject` (the fields are private `[SerializeField]`), with a `startOffset` per intersection so neighbours are not in sync.
- `Assets/CityGenerator/Runtime/TrafficNetwork.cs` / `.../CarAgent.cs` — the traffic. `TrafficNetwork` (on `City/TrafficNetwork`) *generates* the lane graph in `Awake` from the same layout as the geometry (`laneOffset` 2.6 — the nodes are computed, not serialized). The axes are **two independent arrays**, `axesX` and `axesZ` (both defaulting to the reference city's `{-84,-28,28,84}`, i.e. 128 nodes), so grids need not be square; `SetAxes` + the public `Build()` let the generator set the layout, place all traffic lights, and only then build the graph (`Build` matches lights by scanning the scene, so order matters). `EnsureBuilt` covers accessors called before `Awake`. Per intersection and direction there is an *entry* node (the inner corner of the crossing: where the turn is chosen and where the light applies) and an *exit* node; turning right needs no intermediate node because one direction's entry coincides geometrically with the exit of the direction to its right. Lights are matched by geometry, not by name: each entry gets the `TrafficLight` facing it head-on (`Dot(light.forward, direction) < -0.9`), which leaves the 12 outer intersections unsignalled. `CarAgent` follows the graph picking turns at random (`straightWeight` favours going straight), brakes progressively for red/amber and for the car ahead, and takes corners with `RotateTowards` plus a speed cut, not by interpolating positions. Two rules matter: once past the stop line a car keeps going even if the light changes (so it never freezes inside a crossing), and at unsignalled crossings priority is an exclusive per-intersection reservation (`TryReserve`/`Release`, with a timeout) because the forward sensor cannot see cross traffic.
- That reservation once deadlocked every car into a standstill queue for over five minutes, and its current shape *is* the fix — do not revert any of the three pieces: (1) the owner does **not** refresh its timestamp when re-claiming the reservation (if it does, a car blocked next to the crossing holds it forever just by asking every frame, and the timeout never expires); (2) priority is claimed only within `claimDistance` of the stop line, slowing down beforehand like a give-way, never from far off — reserving before you can actually cross blocks everyone else; (3) `ReleaseReservationWhileBlocked` drops it when its owner is stopped by another car and has not entered the crossing yet, which is what breaks the "A waits for the priority B holds, B waits for A to move" cycle. `CurrentStopReason`/`StoppedTime`/`DistanceTravelled` exist to diagnose jams.
- Route weighting (`RouteWeight`/`Ring`, with `interiorBias` and `borderPenalty`) exists because without it all traffic ends up circling the perimeter: on a border street, going straight is the only non-turning exit, and with the raw straight weight that was ~71% likely at every crossing. The weights cancel that bias towards the interior; measured, traffic settles around 9/9 between perimeter and interior.
- Layer `Vehicle` (slot 8) — used by the cars; `CarAgent`'s forward sensor (`SphereCastNonAlloc`) queries only that layer. In that sensor, hits are discarded **by identity** (`other == this`), never by distance: a zero-distance hit is both the car's own collider and the car already bumper-to-bumper ahead, and filtering by distance made cars fail to see each other and drive inside one another on corners. Cars carry a single `BoxCollider` on the root rather than their pieces' `MeshCollider`s: they move by transform with no `Rigidbody`, and the collider exists only so they can detect each other.
- The `Vehicles` group no longer holds ProBuilder greybox cars — traffic is 18 instances of four modelled prefabs in `Assets/Prefabs/Vehicles/` (`SedanSportCar.prefab`, `TaxiCar.prefab`, `DeliveryCar.prefab`, `PoliceCar.prefab`), mixed across the grid rather than clustered by type: 7 `Taxi_*`, 4 `Police_*`, 5 `Delivery_*`, 2 `Sedan_*`. Each prefab already had its own `BoxCollider` sized to its mesh; layer `Vehicle`, `CarAgent` and `vehicleMask` were added on top by editor script (`PrefabUtility.LoadPrefabContents`/`SaveAsPrefabAsset`, not hand-edited YAML) — reuse that pattern for further vehicle prefabs. `CarAgent.network` is left unassigned on the prefabs; `Start()` falls back to `FindFirstObjectByType<TrafficNetwork>()`, which is fine since the scene only ever has one.
- Each type has distinct `CarAgent` tuning so the mixed traffic doesn't all drive identically (prefab defaults; each scene instance additionally has a ±6% random jitter on `maxSpeed` for per-car variety): `Delivery` is the slowest and worst-accelerating (`maxSpeed` 6.5, `acceleration` 3, `braking` 9, `turnSpeed` 160°/s, `cornerSpeedFactor` 0.32 — reads as a heavy truck, sluggish into corners); `Police` sits at a patrol pace with the snappiest acceleration for its speed (`maxSpeed` 9, `acceleration` 7.5, `braking` 15, `turnSpeed` 230°/s, `cornerSpeedFactor` 0.45 — the original default tuning); `Taxi` is a bit faster than `Police` but accelerates worse (`maxSpeed` 10.2, `acceleration` 4.5, `braking` 13, `turnSpeed` 215°/s, `cornerSpeedFactor` 0.42); `Sedan` is the fastest and hardest-accelerating of all (`maxSpeed` 12.8, `acceleration` 9.5, `braking` 17, `turnSpeed` 260°/s, `cornerSpeedFactor` 0.5).
- `Assets/Materials/City/` — the flat-colour URP/Lit palette for the city (`Asphalt`, `Sidewalk`, `Concrete`, `RoadLine`, `Crosswalk`, `Grass`, the `Building*`/`Roof*`/`Glass*`/`Window*` facade set, `TreeTrunk`/`TreeLeaves`, `MetalDark` for street furniture, `Car*` bodies, plus the emissive `LightRed`/`LightAmber`/`LightGreen`/`LightOff`/`LampWarm` lamp materials). Created by editor script, not by hand. The only geometry that does *not* use this palette is the fountain, which keeps the materials embedded in its `.glb`.

### The City Generator tool (`Assets/CityGenerator/`)

- The folder is the whole distributable package: `Runtime/` (the six gameplay MonoBehaviours, namespace `CityGenerator.Runtime`) and `Editor/` (the tool itself, namespace `CityGenerator.Editor`, every type `internal static` except the window). There are **no `.asmdef` files** — everything still compiles into `Assembly-CSharp`/`Assembly-CSharp-Editor`, so `Editor/` is only an editor assembly by virtue of Unity's magic folder name.
- `CityGeneratorWindow` — `Tools > City Generator`. Holds the entire configuration in a single `[SerializeField] CityGeneratorSettings settings`, which is why state survives closing/reopening the window within an Editor session; **deliberately not a `ScriptableObject`** (see the spec's discarded decisions). Three buttons: "Build City in New Scene", "Re-Build City in Current Scene" (destroys the `City` root and regenerates it, leaving light/camera/player/volume alone) and "Reset to Defaults". Two UI quirks are load-bearing and commented in place: `labelWidth` is scaled from `position.width` because the auto width clips the long labels, and required fields draw their red asterisk as a `Rect` overlay inside the label column because a trailing `GUILayout` control gets pushed off-screen on a narrow window. The asterisk is also **conditional**: `DrawRequiredField`'s `isRequired` parameter hides it for fields only required under another setting (e.g. `lawnPrefab` only when `plazaCount > 0`), so it disappears once that condition stops applying.
- `CityGeneratorDefaultAssets.ApplyTo` fills a fresh `CityGeneratorSettings` with this project's own reference-city prefabs (all 21 of them — buildings, vegetation, vehicles with their percentages, ground, plaza, props, player), so the window opens ready for a one-click first generation instead of empty required fields. It is the **one deliberately non-portable file** in the tool — isolated on purpose so it can be swapped or deleted when packaging the tool for another project. It cannot run from a field initializer on `CityGeneratorSettings` (Unity forbids `AssetDatabase` calls during `EditorWindow` deserialization — throws "not allowed to be called from a ScriptableObject constructor"); it is invoked instead from `CityGeneratorWindow.OnEnable()`, gated by a serialized `defaultsInitialized` flag so it only runs once per window instance, and again from "Reset to Defaults".
- Pipeline, in order: `CityGeneratorSceneBuilder` (scene + light + camera + player) → `CityGeneratorContentAssembler` (the group hierarchy and every builder) → `Grid` → `GroundBuilder` → `BuildingBuilder` → `PlazaBuilder` → `StreetPropsBuilder` → `TrafficBuilder`. `CityGeneratorValidator` runs first and blocks generation with a dialog + console errors.
- `CityGeneratorConstants` holds the layout numbers extracted from the reference city (46 m blocks on a 56 m pitch, `GroundDatumY` 0.18, 22 m building slots…). Most constants carry a comment explaining *why* that value — several were tuned against real overlap bugs (lamps clearing the plaza lawn, zebra stripes vs. dashed centreline, corner margin so wide prefabs don't collide across a corner). Change them from there, never inline.
- **Overlap avoidance is the tool's central mechanism, but only for props and vegetation** — buildings and vehicles are deliberately exempt (see below). `CityGeneratorBoundsUtility.GetWorldBounds` combines all child `Renderer` bounds, and `CityGeneratorPlacementEngine` instantiates a candidate, checks its XZ `Rect` against every already-placed object, and `DestroyImmediate`s it if it overlaps. Bounds, not fixed per-category radii, because the prefabs come from the user. `ContentAssembler` threads one growing `obstacles` list through every category in turn — if you add a category, append its result to that list.
- `CityGeneratorBuildingBuilder.BuildBuildings` picks up to 4 fixed 22 m corner slots per non-plaza block, guaranteeing every assigned building prefab is used at least once. **Which corners are actually filled is shuffled per block** when `buildingsPerBlock < 4` — a QA-found bug had every block always fill corners `0..buildingsPerBlock-1` in the same order (e.g. always corner 0 with a count of 1), making partially-built blocks look identical everywhere. Buildings are **not** overlap-checked against each other or against the block edge: an oversized building prefab will visibly clip into its neighbour or spill past the block into the street — accepted as the user's responsibility to size their building prefabs to the 22 m slot, same as any other user-supplied prefab.
- Densities mean "fraction of valid candidate points filled", not an absolute count. Lamps are the exception: `PlaceAll`, fixed at 3 per block side, no density.
- `CityGeneratorTrafficBuilder` adds `CarAgent` and the `Vehicle` layer **to the scene instances only** — never to the user's prefab asset (this is why the reference city's `PrefabUtility.LoadPrefabContents` pattern is *not* reused here). It also warns instead of failing when the project has no `Vehicle` layer, and skips outer-edge exit nodes when spawning (a car there has nothing ahead and `CarAgent` disables itself). Vehicles are never overlap-checked against buildings either, but that's structurally moot: `CarAgent`'s forward sensor only queries the `Vehicle` layer, so a car can't "see" a building even if one encroached on its lane — the real safety margin is the street/lane geometry, not a bounds check.
- `general.useCustomSeed` (bool, off by default) + `general.seed` (int) make generation reproducible on demand: `Assemble` uses `new System.Random(seed)` when enabled, or an unseeded `new System.Random()` otherwise (same as before the field existed). Every builder receives that one `System.Random` instance by parameter — none of them touch `UnityEngine.Random`, so seeding it is enough to make position/prefab-choice generation fully deterministic (`CarAgent`'s own runtime driving behaviour still uses `UnityEngine.Random`, unrelated to generation).
- The generated `Main Camera`'s transform is a **hand-tuned fixed value**, not Unity's defaults: position `(36, 28, -36)`, rotation `Euler(27, -45, 0)`, `Camera.fieldOfView` 45. Verified by eye in `City.unity` before being hardcoded into `CityGeneratorSceneBuilder.CreateMainCamera`.
- Remaining known gap vs. the spec: `CityGeneratorSceneBuilder` hardcodes `Assets/InputSystem_Actions.inputactions`, which will silently resolve to null in another project (`ThirdPersonCamera` ends up without `inputActions`, no error). Should be fixed before packaging the tool for distribution. The `globalVolumeProfile` setting and the generated `Global Volume` were removed on purpose (commit `a094fef`) to keep the tool render-pipeline-agnostic — `City.unity` keeps its own volume, unrelated to the tool.

### Shared assets

- `Assets/Animations/PlayerAnimator.controller` — created via `UnityEditor.Animations.AnimatorController` (editor script), not hand-authored YAML. Base layer: `Locomotion` (1D blend tree on `Speed`, blending `idle`→`walk`→`sprint`), `Jump`, `Fall`, with trigger/bool-driven transitions between them.
- `Assets/Models/Characters/character-male-d.fbx` — the model backing `Player`. Its importer was reconfigured (via editor script, not by hand-editing the `.meta`) to `animationType: Generic` with an Avatar created from the model itself (was `avatarSetup: 0` / no Avatar originally), and `idle`/`walk`/`sprint`/`fall`/`crouch`/`static` clips set to loop (the FBX's default `clipAnimations` import with `loopTime: false`). The FBX contains 32 animation takes total (combat, wheelchair, emotes, etc.) beyond the ones currently wired into the controller — reuse the same reimport pattern if more are needed.
- `Assets/Models/Props/Fountain by Poly.glb` — the only non-FBX model in the project, imported by the glTFast `ScriptedImporter` (`com.unity.cloud.gltfast`) with its own embedded meshes and materials. Backs `Prefabs/Props/Fountain.prefab`. Drop further downloaded `.glb`/`.gltf` props here.
- Other `Assets/Models/Characters/*.fbx` (other character variants) and `Assets/Models/Pets/*.fbx` — same Generic/no-Avatar import state as `character-male-d.fbx` originally had; not yet reimported or referenced by any prefab/script.
- `Assets/Settings/` — URP pipeline assets (separate PC and Mobile renderer/pipeline configs) and the default volume profile.
- `Assets/InputSystem_Actions.inputactions` — the project's only input asset (`generateWrapperCode: 0`, so there's no generated C# class; scripts look up the `Player` action map and actions by name via a serialized `InputActionAsset` reference). Project uses the new Input System exclusively (`activeInputHandler: 1` in ProjectSettings) — `UnityEngine.Input` will throw at runtime.
- `Packages/manifest.json` — package dependencies (URP 17.5.0, Input System 1.20.0, ProBuilder 6.1.2, glTFast 6.19.0, AI Navigation 2.0.14, Timeline, Visual Scripting, Unity AI Assistant, etc.). No Cinemachine — the camera is hand-rolled by design. AI Navigation is installed but **unused so far**: there is no `NavMeshSurface` in the scene and `NavMeshSettings.m_NavMeshData` is null, so nothing is baked.
- The many `Unity.*.csproj` files and `.sln` at the root are IDE-generated project files (regenerated by Unity/Rider automatically); do not hand-edit them.

## Working in this project

- There is no CLI build/test/lint pipeline set up — this project is edited and run through the Unity Editor (or Rider/Visual Studio via the generated `.sln`).
- When adding scripts, place runtime code in `Assets/CityGenerator/Runtime` and editor code in `Assets/CityGenerator/Editor` (there is no `Assets/Scripts` any more), following standard Unity C# conventions (MonoBehaviour components, `.meta` files are auto-generated by the Editor — don't create or edit them manually).
- Structural, hard-to-hand-author assets (AnimatorControllers, ModelImporter reconfiguration, prefab creation, the whole city) were built via one-off editor scripts run through the Unity MCP tooling (`Unity_RunCommand`), not by writing `.controller`/`.meta` YAML directly — prefer that same approach for similar changes.
- Nothing in C# refers to the scene, the city root, or the materials folder by name (material references are serialized by GUID), so the `City3` → `City` renames needed no code changes. Watch for it anyway when writing new editor scripts: the ones used to build the city looked the root up with `GameObject.Find("City3")` — that name no longer exists anywhere, use `GameObject.Find("City")`.
- When adding more city content, **create a prefab and instance it** rather than dropping loose ProBuilder objects into the scene — that is the shape the whole scene now has, and it is what made the scene file shrink by roughly two thirds. Build the prefab with `PrefabUtility.SaveAsPrefabAsset` from an editor script and place instances with `PrefabUtility.InstantiatePrefab`; edit existing prefabs with `PrefabUtility.LoadPrefabContents`/`SaveAsPrefabAsset`, never by hand-editing the `.prefab` YAML.
- Prefer `BoxCollider`s over `MeshCollider`s on new props and floors, matching the existing prefabs; leave purely decorative geometry (markings, glass, small details) with no collider.
- FBX characters/pets other than `character-male-d` still have `animationType: Generic` with no Avatar and un-looped clips; before animating any of them, reimport following the same pattern used for `character-male-d.fbx`.
- Unity here does not pick up new/edited scripts on its own while the Editor is in the background: creating a `.cs` and then calling `AssetDatabase.Refresh()` leaves `Assembly-CSharp` stale (the type is missing from `AppDomain`, and `Unity_RunCommand` fails to compile against it). Force it with `UnityEditor.Compilation.CompilationPipeline.RequestScriptCompilation()`, then wait — the domain reload makes the MCP briefly report "Unity not detected", and only after it the new types resolve. Check `Unity_ReadConsole` for compile errors when a type still fails to appear.
- ProBuilder 6.1.2 is installed and is the intended way to build level geometry. From an editor script, generate shapes with `UnityEngine.ProBuilder.ShapeGenerator.*`, then call `ToMesh()`, `Refresh()` and `UnityEditor.ProBuilder.EditorMeshUtility.Optimize(pb)` so the mesh is cached in the scene — `UnityEditor.ProBuilder.EditorUtility.InitObject` is `internal` in this version and cannot be used. Watch two gotchas in `Unity_RunCommand` scripts: `EditorUtility` is ambiguous once `UnityEditor.ProBuilder` is imported (qualify it as `UnityEditor.EditorUtility`), and `Object.GetInstanceID()` is obsolete in this Unity version (`GetEntityId()`).
- The namespaces are `CityGenerator.Runtime` (`PlayerController`, `ThirdPersonCamera`, `TrafficLight`, `TrafficLightIntersection`, `TrafficNetwork`, `CarAgent`) and `CityGenerator.Editor` (the tool); extend those rather than introducing a new one. The old `TestAI` namespace is gone — no code or asset refers to it any more (the move needed no scene/prefab fixes because Unity serializes script references by GUID, and the `.meta` files travelled with the files).
- The tool must stay **portable to any Unity project**: no dependency on this project's prefabs, materials, layers or assets, and no mutation of the user's assets. Anything project-specific belongs in the reference city, not in `Assets/CityGenerator/`.
