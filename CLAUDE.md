# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a Unity project (`City Generator`, Unity `6000.5.8f1`, URP) whose **only reason to exist is to develop, test and distribute the City Generator tool** — an Editor window that procedurally generates a city (roads, sidewalks, markings, buildings, plazas, street furniture, traffic lights, autonomous traffic and pedestrians) into a new or existing scene.

The tool lives in the embedded package `Packages/com.santiandrade.citygenerator/` and that package **is** the deliverable: it is what a user installs into their own Unity project via **Package Manager > Install package from git URL**. This project consumes the tool the same way — as an installed package, not as loose code in `Assets/` — so a portability break shows up here first, not in the user's project. See the root `README.md` (English) / `README.es.md` (Spanish) for the install URL, the update procedure and full user-facing documentation. Everything else in the repo exists to support the package, in one of three roles:

- **Demo content**, inside the package at `Packages/com.santiandrade.citygenerator/DefaultAssets/` — the sample prefabs the tool ships with so it works out of the box, loaded by `CityGeneratorDefaultAssets`. It travels with the package to any project that installs it; only the models actually referenced by a demo prefab live here (see "Demo content" below for how that's decided).
- **Orphan models** (`Assets/Models/`) — FBX/glb library entries from the same asset packs as the demo models that no demo prefab currently uses. Kept in this repo on purpose for future use, but deliberately **not** part of the package, so installing it doesn't drag along unused models.
- **Test scene** (`Assets/Scenes/City.unity`) — a **disposable** scene generated by the tool, kept only to eyeball the output. It is regenerated freely and carries no hand-made work worth preserving. Never treat it as a source of truth, and never hand-edit it to fix something the tool should be doing.

The tool's behaviour is considered **done and correct**: reproduce it, don't redesign it. Its original spec lives in `specs/01-city-generator-tool.md` (Spanish, driven by a `/spec-*` workflow configured by `specs/.spec-config.yml`); read it before touching the tool's generation logic — it records the decisions taken **and explicitly discarded**, several of them found during manual QA. `specs/02-unity-package-distribution.md` is the spec for the package/distribution work described in this file (embedding, demo content movement, README, versioning, release tooling) — it does not touch generation behaviour. `specs/03-pedestrian-network.md` is the spec for the autonomous pedestrian system (see "Pedestrian system" below). `specs/04-critical-architecture-fixes.md` is the spec for the v2.0.0 critical-fixes-and-architecture round (transactional rebuild, pedestrian POI persistence, hierarchical collider detection, `Include Traffic`/traffic-light validation, non-singleton managers, single Input System authority) — its changes are folded into the sections below. `specs/05-performance-and-tests.md` is the spec for the v2.1.0 performance-and-test-suite round (the `Assets/Tests/` suite described below, `CityGeneratorSpatialHash`, `TrafficLaneOccupancy`, `PedestrianRoadProximityGrid`, `PedestrianNetwork` connected components/BFS caching, `PedestrianPathBufferPool`) — it records the measured baseline/delta numbers for each change and is the reference for why those structures exist. `specs/06-custom-places.md` is the spec for Custom Places (see "Custom Places" below) and, in parallel, the full removal of the pedestrian network's Point of Interest machinery — a user-driven decision to decouple POIs from pedestrians ahead of a future minimap/POI system built on Custom Places; `PedestrianNetwork`/`PedestrianAgent`/`CityGeneratorPedestrianBuilder` no longer contain any POI code, and benches/the plaza centerpiece are plain visual props with no pedestrian-graph wiring. `docs/technical-review.md` is the standing technical review (performance, code quality, ECS analysis) with the pending findings; `docs/technical-review-2026-08-25.md` is the external review whose critical/architectural findings SPEC 04 addressed and whose performance findings (items 6-9) SPEC 05 addressed — its remaining medium/low-priority items (demo content, docs, `CityGeneratorWindow` splitting) stay open for future specs.

Historical note: the layout the tool reproduces was originally a hand-built city made of ProBuilder primitives. That hand-made city no longer exists (commit `ff13e28`, "Removed old city"). The numbers extracted from it survive as `CityGeneratorConstants`.

## Structure

### The tool — `Packages/com.santiandrade.citygenerator/` (the installable package)

An embedded Unity package (`package.json`, `name` `com.santiandrade.citygenerator`, `unity` `6000.0`, dependencies `com.unity.inputsystem` and `com.unity.cloud.gltfast`). Two assemblies, each with its own `.asmdef`:

- `Runtime/CityGenerator.Runtime.asmdef` — namespace `CityGenerator.Runtime`, references `Unity.InputSystem`.
- `Editor/CityGenerator.Editor.asmdef` — namespace `CityGenerator.Editor`, `includePlatforms: [Editor]`, references the runtime asmdef and `Unity.InputSystem`. Every type in it is `internal static` except the window and the `Editor/UI/` visual-element classes below (which need instance state to exist at all).

**`CityGeneratorWindow`** — `Tools > City Generator > Open`. Holds the entire configuration in a single `[SerializeField] CityGeneratorSettings settings`, which is why state survives closing/reopening the window within an Editor session; **deliberately not a `ScriptableObject`** (see the spec's discarded decisions). The window is built with **UI Toolkit** (`CreateGUI`, not `OnGUI`): `Editor/UI/CityGeneratorWindow.uxml` is the structural skeleton (banner, tab bar, scrollable card container per tab, footer) cloned into `rootVisualElement`, styled by `CityGeneratorWindow.uss` plus a theme sheet (`_Dark`/`_Light`, picked by `EditorGUIUtility.isProSkin`) that only redefines `--cg-*` color variables. Cards are grouped into four tabs — **City** (general/ground/plaza/buildings/vegetation/vehicles/props), **Player** (Player Prefab + Input Actions, moved here from General; a Player card for movement/`CharacterController`/input action names; a Camera card for `ThirdPersonCamera` orbit/collision/field-of-view tuning), **Pedestrians** (the weighted pedestrian list; a Behaviour card for pace/jitter/stop tuning and the animation reference speeds; a Crowd card for `PedestrianManager` separation/avoidance/staggering) and **Custom Places** (see "Custom Places" below) — switched by `CityGeneratorTabBar` (a hand-rolled tab strip, not `UnityEngine.UIElements.TabView`, so it can stay themed with `--cg-*` and mark a tab red when a card on it has a validation error; selection persisted in `EditorPrefs`). Every section is built in code as a `CityGeneratorCard` (collapsible, open/closed state persisted per-card in `EditorPrefs`, badge summarising its content, turns red when one of its fields fails validation). Bound the standard UI Toolkit way — `rootVisualElement.Bind(serializedWindow)` plus per-field `PropertyField`s constructed straight from a `SerializedProperty` — except for controls that manage their own `SerializedProperty` reads/writes: `CityGeneratorGridPreview` (a `Painter2D` top-down miniature of the grid; in its default `PlazaMultiToggle` mode it doubles as the plaza editor — clicking a block toggles it directly against `general.plazaCells`, a `List<Vector2Int>` of block coordinates, so the picture and the generated scene can never disagree; there is no separate plaza count — and in `SingleSelectQuadrant` mode, used per Custom Place entry, clicking picks a single block plus, unless the entry occupies the full block, which quadrant of it was clicked, using the same 0-3 convention as `CityGeneratorBuildingBuilder.SlotOffsets`), `CityGeneratorPrefabGrid` (thumbnail grid for `buildingPrefabs`/`vegetation.prefabs`), `CityGeneratorWeightedPrefabList` (thumbnail + percentage slider + stacked bar + "Normalize to 100%" for `vehicles`/`pedestrians` — deliberately never rebuilds its rows on a plain percentage edit, only on add/remove/normalize, because tearing down the dragged `Slider` mid-drag would drop its pointer capture and abort the gesture) and `CityGeneratorCustomPlaceList` (one self-contained row per Custom Place entry: title/prefab/toggles/facing built from plain `TextField`/`ObjectField`/`Toggle`/`EnumField` controls, **not** `PropertyField`, plus the entry's own `CityGeneratorGridPreview` in `SingleSelectQuadrant` mode — a `PropertyField` constructed after the window's one-time `Bind()` call, which is when every row here is actually created, never binds and renders empty; this was a real regression caught and fixed after the initial SPEC 06 implementation, so don't reintroduce `PropertyField` for a dynamically-added row anywhere in this window). `CityGeneratorValidator.ValidateDetailed` (same checks as the original `Validate`, each issue additionally tagged with the settings path that caused it) is re-run on every edit via `TrackSerializedObjectValue`, driving live required-field/card/tab highlighting (a field relocated to a card outside its own settings segment, like `general.playerPrefab` living in the Player card, is resolved through an exact-path alias registered alongside the segment-based lookup) and disabling both Build buttons until every issue clears — replacing the old blocking `EditorUtility.DisplayDialog` validation-error flow. Two buttons — "Build City in New Scene" and "Re-Build City in Current Scene" (transactional: builds the new city under a temporary root and only destroys the previous one, found via the `CityGeneratorRoot` marker component rather than by name, once generation finishes without throwing — see `CityGeneratorSceneBuilder.RebuildInActiveScene` below; light/camera/player are left alone either way) — drive an `EditorUtility.DisplayProgressBar` through an optional `onProgress` callback threaded (additively — default `null`) through `CityGeneratorContentAssembler.Assemble` → `CityGeneratorSceneBuilder`, and show the result in an in-window panel (with a "Ping Scene" button) instead of a dialog; "Reset to Defaults" stays a plain button, low-key styled. The `settings` field is `[SerializeField] internal`, not `private`, so `Assets/Editor/CityGeneratorSetDefaultsWindow.cs` (outside the package, see "Versioning and releasing" below) can read it via the package Editor assembly's `InternalsVisibleTo`.

**Pipeline**, in order: `CityGeneratorValidator` (runs first, blocks generation with a dialog + console errors) → `CityGeneratorSceneBuilder` (new scene + directional light + camera + player, saved as the next free `Assets/Scenes/City<N>.unity`) → `CityGeneratorContentAssembler` (the group hierarchy and every builder) → `Grid` → `GroundBuilder` → `CustomPlaceBuilder` → `BuildingBuilder` → `PlazaBuilder` → `StreetPropsBuilder` → `TrafficBuilder`.

- `CityGeneratorConstants` holds the layout numbers (46 m blocks on a 56 m pitch, `GroundDatumY` 0.18, 22 m building slots, lamp/zebra/traffic-light offsets…). Most constants carry a comment explaining *why* that value — several were tuned against real overlap bugs (lamps clearing the plaza lawn, zebra stripes vs. dashed centreline, corner margin so wide prefabs don't collide across a corner). Change them from there, never inline. Player movement/`CharacterController`/camera tuning and pedestrian pace/jitter/stop/crowd tuning used to live here as hardcoded (and, for the pedestrian ones, mostly unreferenced) constants; they are now user-configurable settings (`PlayerSettings`, `CameraSettings`, `PedestrianBehaviourSettings`, `CrowdSettings` in `CityGeneratorSettings.cs`, edited from the Player/Pedestrians tabs) — don't reintroduce them as constants.
- **Overlap avoidance is the tool's central mechanism, but only for props and vegetation** — buildings and vehicles are deliberately exempt. `CityGeneratorBoundsUtility.GetWorldBounds` combines all child `Renderer` bounds, and `CityGeneratorPlacementEngine` instantiates a candidate and checks its XZ `Rect` against already-placed objects, `DestroyImmediate`ing it if it overlaps. Bounds, not fixed per-category radii, because the prefabs come from the user. `ContentAssembler` threads one growing `obstacles` list through every category in turn — if you add a category, append its result to that list; `obstacles` stays the source of truth. Since SPEC 05, the overlap check itself queries `CityGeneratorSpatialHash` (a uniform hash keyed by cell, cell size derived from `CityGeneratorConstants`'s block size) instead of scanning `obstacles` linearly — the hash is a pure index over `obstacles`, populated alongside it and never a second source of truth (measured -17.2% total generation time on a 10×10 grid; same placement result for a given seed, only the query cost changes).
- `CityGeneratorPlayerSpawner.FindSpawnPosition` picks where the player instance lands: inside a plaza block when the city has one (searched in random order across plazas), a random block otherwise, checked against the same growing `obstacles` list (minus ground cover, since standing on lawn/sidewalk is the point) so the player never spawns overlapping a building/prop/vehicle. `CityGeneratorSceneBuilder.ConfigurePlayer` `AddComponent`s `CharacterController`, `PlayerController` and `PlayerInputAuthority` (see "Runtime components" below) to whichever prefab is assigned as Player Prefab, if it doesn't already carry them — but then **writes the Player tab's tuning onto the instance unconditionally**, even when the prefab already had its own `CharacterController`/`PlayerController`: the window is the single source of truth, never the prefab asset (which is never touched). This is what lets `DefaultAssets/Prefabs/Characters/` stay 12 clean model+Animator prefabs instead of each needing its own baked movement setup, and equally lets a user-supplied character work as Player Prefab with zero manual setup while still picking up whatever tuning is set in the window. `CreateMainCamera` applies the Camera tab's tuning to the generated `ThirdPersonCamera` the same way (`fieldOfView`, orbit, collision, cursor lock); only the camera's initial transform stays the hand-tuned fixed value described below.
- `CityGeneratorBuildingBuilder.BuildBuildings` picks up to 4 fixed 22 m corner slots per non-plaza block, guaranteeing every assigned building prefab is used at least once. **Which corners are filled is shuffled per block** when `buildingsPerBlock < 4` — a QA-found bug had every block always fill corners `0..buildingsPerBlock-1` in the same order, making partially-built blocks look identical everywhere. Buildings are **not** overlap-checked against each other or against the block edge: an oversized building prefab will visibly clip into its neighbour or spill into the street — accepted as the user's responsibility to size their prefabs to the 22 m slot, same as any other user-supplied prefab. Since SPEC 06 it also takes an optional `reservedSlots` set (`(gridX, gridY, slot)`, `slot == -1` meaning the whole block) produced by `CityGeneratorCustomPlaceBuilder`: a reserved corner is excluded from that block's random corner order, and a reserved whole block is skipped entirely — an empty set (the default) reproduces the exact old behaviour.
- `CityGeneratorCustomPlaceBuilder.BuildCustomPlaces` (SPEC 06) instantiates every valid `CustomPlaceEntry` — title, prefab and an assigned position that resolves to a real, non-plaza block, checked defensively here even though `CityGeneratorValidator` already blocks Build on anything invalid — at its exact block centre (`occupiesFullBlock`) or corner offset (reusing `CityGeneratorBuildingBuilder.SlotOffsets`' 0-3 index, never a separate corner enum) and fixed `facing` rotation (90° steps, never randomised, unlike a normal building's random `Quaternion.Euler(0, 90*random.Next(4), 0)`). Runs before `BuildingBuilder` in the pipeline and returns the reserved-slots set that builder excludes (see above), plus its own instances, which the assembler prepends to the shared `obstacles` list — a Custom Place participates in overlap avoidance like props/vegetation, unlike a normal building.
- Densities mean "fraction of valid candidate points filled", not an absolute count — including `lampDensity` (1 = all 3 candidate points per block side).
- `CityGeneratorContentAssembler` applies `BatchingStatic | OccluderStatic | OccludeeStatic` to every generated group **except `Vehicles`/`Pedestrians`**, so each generated city is batched and ready for a lightmap/occlusion bake with no manual pass — this includes the `CustomPlaces` group (SPEC 06), since a Custom Place never moves at runtime. `CarAgent`/`PedestrianAgent` move their instances by transform every frame, which is why both are excluded.
- `CityGeneratorTrafficBuilder.BuildVehicles` calls `EnsureVehicleLayerExists` before spawning anything: if the project has no `Vehicle` layer yet, it creates one itself by writing directly to `ProjectSettings/TagManager.asset` via `SerializedObject`, using the first free slot from `CityGeneratorConstants.FirstUserLayerIndex` (8) up, and logs that it did so. Requiring the user to create this layer by hand was a recurring point of confusion during SPEC 02 verification. Only if every slot 8-31 is already taken does it fall back to warning instead — in that case every instance's `CarAgent.vehicleMask` is left at `0` (Nothing) rather than matching whatever layer the instance happens to share with unrelated scene geometry, so vehicles simply stop detecting each other (they still stop for lights and unsignalled-crossing priority) until a slot frees up. `CarAgent` and the `Vehicle` layer are added **to the scene instances only**, never to the user's prefab asset, and outer-edge exit nodes are skipped when spawning (a car there has nothing ahead and `CarAgent` disables itself). When the layer does exist, `BuildVehicles` sets `CarAgent.vehicleMask` to `1 << instance.layer` per instance via `SerializedObject` — **do not rely on the mask baked into a vehicle prefab's own serialized data**: it only happens to work when `Vehicle` sits at the same layer index the prefab was authored against, and silently makes the forward sensor blind to every other vehicle otherwise (found during SPEC 02 verification: the demo prefabs' baked `vehicleMask` and `m_Layer` both happened to reference index 8, which is why the bug went unnoticed). `CityGeneratorConstants.VehicleDensityWarningThreshold` (0.4 of spawn nodes) is surfaced only as a live `HelpBox` in `CityGeneratorWindow` while editing `vehicleCount` — `BuildVehicles` itself no longer logs a console warning past that threshold, since the inspector already told the user before they clicked generate; measured on a 5×5 grid, 38% of nodes flowed, 76% gridlocked from the first frame.
- `CityGeneratorPedestrianBuilder` builds the pedestrian network and NPCs, mirroring `CityGeneratorTrafficBuilder`: the `PedestrianNetwork` graph (see "Pedestrian system" below) is always built and pruned against the shared `obstacles` list, independent of `includePedestrians`, so its crossings stay wired to the real traffic lights even when no NPCs are spawned; NPC instances are only placed when `includePedestrians` is on. `CityGeneratorDistributionUtility.DistributePercentages` (a generic largest-remainder distributor) is shared between `BuildVehicles` and `BuildPedestrians` rather than duplicated per category. `EnsurePedestrianLayerAndAssignMask` is called whenever vehicles exist (not gated on `includePedestrians`), since `CityGeneratorSceneBuilder` puts the player on the same `Pedestrian` layer and vehicles must detect it either way.
- `general.useCustomSeed` (off by default) + `general.seed` make generation reproducible: `Assemble` uses `new System.Random(seed)` when enabled, unseeded otherwise. Every builder receives that one `System.Random` **by parameter** — none of them touch `UnityEngine.Random`, so seeding it is enough to make placement and prefab choice fully deterministic (`CarAgent`'s runtime driving still uses `UnityEngine.Random`, unrelated to generation). Which blocks are plazas is **not** part of this: `CityGeneratorGrid.BuildBlocks` takes `general.plazaCells` directly and never touches `random` — it used to draw a random subset here (`ChoosePlazaIndices`), which is why the grid preview couldn't reliably match the generated scene; now the preview edits `plazaCells` directly (see `CityGeneratorGridPreview` above), so they can't disagree.
- The generated `Main Camera`'s transform is a **hand-tuned fixed value**, not Unity's defaults: position `(36, 28, -36)`, rotation `Euler(27, -45, 0)`, `fieldOfView` 45.
- No `Global Volume` is generated — removed on purpose (commit `a094fef`) to keep the tool render-pipeline-agnostic.
- `CityGeneratorDefaultAssets.ApplyTo` fills a fresh `CityGeneratorSettings` with the package's own demo prefabs (buildings, vegetation, vehicles and pedestrians with their percentages, ground, plaza prefabs and layout (`plazaCells`), props, player, input actions), loaded from hardcoded `Packages/com.santiandrade.citygenerator/DefaultAssets/...` paths, so the window opens ready for a one-click first generation instead of empty required fields. Since SPEC 02 those paths resolve in any project that installs the package (the demo content ships inside it), so this file is no longer the one non-portable file in the tool — it's ordinary portable code, just tied to the bundled demo assets rather than to generation logic. It cannot run from a field initializer on `CityGeneratorSettings` (Unity forbids `AssetDatabase` calls during `EditorWindow` deserialization); it is invoked from `CityGeneratorWindow.OnEnable()`, gated by a serialized `defaultsInitialized` flag so it runs once per window instance, and again from "Reset to Defaults".
- `CityGeneratorDefaultAssetsWriter.SaveCurrentAsDefault` is the other direction: given an open window's `settings`, it regenerates `CityGeneratorDefaultAssets.cs`'s `ApplyTo` body wholesale (asset lists can change length between calls, e.g. after swapping in new building or vehicle prefabs, which a targeted text edit can't express as cleanly as a full rewrite) and patches the scalar field initializers in `CityGeneratorSettings.cs` in place via `Regex` (safe because every scalar field name — `gridWidth`, `vehicleCount`, `density`, etc. — is unique within that file). Both are plain `File.WriteAllText` calls against the package's own source under `Packages/`, followed by `AssetDatabase.Refresh()`. Kept in its own file rather than folded into `CityGeneratorDefaultAssets` because it overwrites that file's contents — it must never need to regenerate itself. A prefab assigned from outside `DefaultAssets/` still gets written into the new default (the command never blocks on it), but the result only resolves in this project; flagged with a console warning per offending field rather than silently accepted. This method itself stays in the package (it rewrites the package's own source, which is its job), but the `[MenuItem("Tools/City Generator/Set Current Selection As Default")]` entry point that calls it lives outside the package, in `Assets/Editor/CityGeneratorSetDefaultsWindow.cs` — see "Versioning and releasing" below for why.

### Runtime components — `Packages/com.santiandrade.citygenerator/Runtime/`

These ship with the tool and are what a generated city runs on.

- `PlayerInputAuthority.cs` — the single component allowed to call `Enable()`/`Disable()` on the Player action map (`OnEnable`/`OnDisable`), added to the Player instance by `CityGeneratorSceneBuilder.ConfigurePlayer` alongside `CharacterController`/`PlayerController`. `PlayerController` and `ThirdPersonCamera` only ever read actions already enabled by this component — previously each called `Enable()`/`Disable()` on the same shared map from its own `OnEnable`/`OnDisable`, so disabling either one alone cut input to the other too.
- `PlayerController.cs` — walk/run/jump via the new Input System (`Player` action map: `Move`, `Sprint`, `Jump`). Movement is camera-relative. Drives the Animator's `Speed`, `Grounded`, `Jump`, `VerticalSpeed`. `[RequireComponent(typeof(CharacterController))]`, but neither it nor `CharacterController` are baked into the demo character prefabs — see `CityGeneratorSceneBuilder.ConfigurePlayer` below. Does not `Enable()`/`Disable()` the action map itself — see `PlayerInputAuthority` above.
- `ThirdPersonCamera.cs` — Mario-64-style orbit camera, reads `Look` from the same map (does not `Enable()`/`Disable()` it — see `PlayerInputAuthority` above). Only the target-follow *position* is smoothed (`SmoothDamp`); rotation is recomputed every frame as `LookRotation` from the camera's actual (possibly lagging) position to the pivot, so position and aim can never desync — **do not reintroduce separate smoothing on `transform.rotation`**, that was tried and caused visible motion sickness. Pivot offset is `verticalOffset` + `horizontalOffset` (the latter along the orbit's local right axis, i.e. over-the-shoulder), not a single `Vector3`. Has camera-vs-environment `SphereCast` collision. `OnDisable` restores cursor lock state/visibility (previously absent, so leaving Play or disabling this component left the cursor stranded locked/hidden).
- `TrafficLight.cs` / `TrafficLightIntersection.cs` — `TrafficLight` swaps lamp materials (`LightRed`/`LightAmber`/`LightGreen`/`LightOff`) to show its state; `TrafficLightIntersection` runs the coroutine alternating green between its `eastWest` and `northSouth` groups with amber and all-red phases, with a per-intersection `startOffset` so neighbours are not in sync.
- `TrafficNetwork.cs` — *generates* the lane graph in `Awake` from the same layout as the geometry (`laneOffset` 2.6; nodes are computed, not serialized). The axes are **two independent arrays**, `axesX` and `axesZ`, so grids need not be square; `SetAxes` + the public `Build()` let the generator set the layout, place all traffic lights, and only then build the graph (`Build` matches lights by scanning the scene, so order matters). `EnsureBuilt` covers accessors called before `Awake`. Per intersection and direction there is an *entry* node (the inner corner of the crossing: where the turn is chosen and where the light applies) and an *exit* node; turning right needs no intermediate node because one direction's entry coincides geometrically with the exit of the direction to its right. Lights are matched **by geometry, not by name**: each entry gets the `TrafficLight` facing it head-on (`Dot(light.forward, direction) < -0.9`), which leaves outer intersections unsignalled. Exposes `LaneOccupancy`/`RoadProximity` (see `TrafficLaneOccupancy`/`PedestrianRoadProximityGrid` below), both on the same GameObject as `Manager`. `Physics.SyncTransforms()` (needed because the project runs with `m_AutoSyncTransforms: 0` and `CarAgent` moves by transform then raycasts in the same frame) moved to `TrafficManager.Update` in SPEC 05 — see below; `TrafficNetwork` itself no longer calls it.
- `CarAgent.cs` — follows the graph picking turns at random (`straightWeight` favours going straight), brakes progressively for red/amber and for the car ahead, and takes corners with `RotateTowards` plus a speed cut, not by interpolating positions. Falls back to `FindAnyObjectByType<TrafficNetwork>()` in `OnEnable`/`Start` if `network` wasn't injected by the generator, since a scene only ever has one. Ticked by `TrafficManager` rather than through its own `Update` — see below; resolves its manager via `network.Manager` (falling back to `FindAnyObjectByType<TrafficManager>()`, then auto-creating one, for standalone use outside the generator) and registers with it in `OnEnable` — idempotent, since `TrafficManager.agents` is a `HashSet`, so a re-enabled agent that was never explicitly unregistered doesn't end up ticked twice. Four rules are load-bearing:
  1. Once past the stop line a car keeps going even if the light changes, so it never freezes inside a crossing.
  2. At unsignalled crossings priority is an exclusive per-intersection reservation (`TryReserve`/`Release`, with a timeout), because the forward sensor cannot see cross traffic. **That reservation once deadlocked every car for over five minutes and its current shape *is* the fix — do not revert any of its three pieces**: (a) the owner does *not* refresh its timestamp when re-claiming (if it does, a blocked car holds the reservation forever just by asking every frame and the timeout never expires); (b) priority is claimed only within `claimDistance` of the stop line, slowing down beforehand like a give-way, never from far off; (c) `ReleaseReservationWhileBlocked` drops it when its owner is stopped by another car and has not entered the crossing, breaking the "A waits for the priority B holds, B waits for A to move" cycle. `CurrentStopReason`/`StoppedTime`/`DistanceTravelled` exist to diagnose jams.
  3. In the forward sensor (filtered by `vehicleMask` — set per-instance by `CityGeneratorTrafficBuilder` to match the layer it actually placed the vehicle on, not a value baked into the prefab) hits are discarded **by identity** (`other == this`), never by distance: a zero-distance hit is both the car's own collider *and* the car already bumper-to-bumper ahead, and filtering by distance made cars fail to see each other and drive inside one another on corners. SPEC 05 changed the "car ahead" check to first query `TrafficNetwork.LaneOccupancy.TryGetCarAhead` (a per-lane-segment occupancy index `CarAgent` reports itself in/out of via `Enter`/`Leave` — resolves "car ahead in the same segment" with no physics query) and only fall back to the physics sensor (now an `OverlapSphere` centred on the car's own position, not a `SphereCast` from an offset point ahead — closes a blind spot where a long vehicle a couple of metres ahead could go undetected) when the lane index has no answer (free lane, end of segment, inside a crossing). The pedestrian side of the sensor (`pedestrianMask`) is untouched by the lane index; above `staggerMinAgentCount` pedestrians it queries `TrafficNetwork.RoadProximity` (`PedestrianRoadProximityGrid`) instead of `SphereCastNonAlloc`.
  4. Route weighting (`RouteWeight`/`Ring`, with `interiorBias` and `borderPenalty`) exists because without it all traffic circles the perimeter: on a border street, going straight is the only non-turning exit, ~71% likely at every crossing with the raw straight weight. Measured with the weights, traffic settles around 9/9 perimeter/interior.
- `TrafficManager.cs` — ticks every registered `CarAgent` from a single `Update` (`Register`/`Unregister`, called from each car's `OnEnable`/`OnDisable`) instead of each car paying its own Update marshalling cost (technical review, A.7). Not a scene-global singleton (no `static Instance`, removed in SPEC 04): `CityGeneratorTrafficBuilder.AddManagerComponent` adds it to the `TrafficNetwork` GameObject only when `includeTraffic` is on, and wires it into `TrafficNetwork.Manager` (same GameObject) so `CarAgent` resolves it through the network rather than a global; a `CarAgent` used outside the generator falls back to finding or auto-creating one, so it still drives standalone. This is what lets multiple generated cities coexist in the same scene without their managers fighting over which one ticks which cars. Below `staggerMinAgentCount` (60 by default) every car's forward sensor runs every frame, identical to the old per-car `Update` — **do not lower this without re-verifying the default 80-car demo still behaves the same**. Above it, cars farther than `staggerDistance` from `Camera.main` only run their `SphereCast` 1 of every `staggerFrames` frames, reusing the previous clearance in between. Since SPEC 05, also calls `Physics.SyncTransforms()` once per frame after ticking every agent (moved here from `TrafficNetwork`), and only when `agents.Count > 0` — a scene with traffic disabled or with every `CarAgent` unregistered no longer pays for it.
- `TrafficLaneOccupancy.cs` (SPEC 05) — a per-directed-edge (`(fromNode, toNode)`) occupancy index of the `CarAgent`s currently in that lane segment, ordered by `DistanceTravelled`. `CarAgent` reports itself via `Enter`/`Leave` as it moves between graph nodes; `TryGetCarAhead` resolves "car immediately ahead in the same segment" without a physics query. Lives on the same GameObject as `TrafficNetwork.Manager`, exposed as `TrafficNetwork.LaneOccupancy`. Deliberately scoped to *only* the same-segment-car-ahead case — crossings, obstacles and pedestrians still go through the physics sensor, keeping this index decoupled from `CarAgent`'s pedestrian-braking rule (see rule 3 above).
- `PedestrianRoadProximityGrid.cs` (SPEC 05) — a uniform spatial grid of registered `PedestrianAgent` positions, rebuilt once per frame by `PedestrianManager` and queried by `CarAgent.pedestrianMask` sensing (above `staggerMinAgentCount` pedestrians) instead of `SphereCastNonAlloc`. The **player** is not a `PedestrianAgent` (it's the manually-driven player instance, sharing the `Pedestrian` layer — see "Pedestrian system" below) so it can't be bucketed like one; `PedestrianManager` passes the resolved player `Transform` into `Rebuild` separately, and the grid tracks it via `TryGetPlayerPosition`, checked alongside the bucketed query so cars keep braking for the player once this grid takes over from the `SphereCast` fallback.
- `CityGeneratorRoot.cs` — an empty `[DisallowMultipleComponent]` marker `MonoBehaviour` added to the root of every generated city (first thing `CityGeneratorContentAssembler.Assemble` does, before any builder runs). Lives in `Runtime/` (not `Editor/`) so it also exists in player builds. Lets `CityGeneratorSceneBuilder.RebuildInActiveScene` find the previous city by component instead of by GameObject name (which the user may have renamed, or which an unrelated object might coincidentally share) — see the transactional rebuild described above.

### Pedestrian system

Added by `specs/03-pedestrian-network.md`, structurally mirroring the vehicle traffic system throughout.

- `PedestrianNetwork.cs` — an **undirected** graph (unlike `TrafficNetwork`'s directed one: a pedestrian can walk either way along every edge), rebuilt in `Awake`/`Build()` from the same street axes. Every block gets an 8-node ring (4 corners + 4 side midpoints) sitting in the gap between the building slot edge and street furniture; every interior intersection additionally gets, per arm, a curb → crossing → curb chain linking two ring corners across the street, with the crossing node matched **by geometry** (nearest `TrafficLightIntersection`, same convention as `TrafficNetwork`'s light matching) so `CanCross` can read the real light state via `TrafficNetwork.AxisState`/`IsAxisGreen` (`TrafficLightIntersection.EastWestState`/`NorthSouthState`). `CanCross` only allows stepping onto the road on **Red**, not just "not green" — Amber still has cars moving through. `FindPath` is a zero-allocation BFS into caller-supplied buffers (shortest by hop count, since every edge is unweighted). A grid with `gridWidth == 1` or `gridHeight == 1` has no interior intersections, so every block's ring is isolated — surfaced as a non-blocking `HelpBox` in `CityGeneratorWindow`, same convention as the vehicle density warning. `Build()` wipes `nodes` from scratch every call (Awake in Play, or an explicit re-bake) and rebuilds only `Ring`/`Curb`/`Crossing` nodes — there is no fourth node kind and nothing else the generator adds to this graph after `Build()` returns (see "Custom Places" below for why: SPEC 06 removed the one thing that used to, the pedestrian network's Point of Interest machinery).
  - SPEC 05 added two performance structures, both recalculated inside `Build()`: **connected components** (`nodeComponent`, a flood fill over the finished ring/crossing edges, one entry per node, read via `ComponentOf`) — `PedestrianAgent.PlanNewDestination` filters candidates to the origin's component before attempting a route, so an isolated single-block ring (the `gridWidth == 1`/`gridHeight == 1` case above) never wastes a BFS on an unreachable node; and a **short-lived BFS tree cache** (`cameFromCache`, keyed by origin node, invalidated on every `Build()`) so several pedestrians planning from nearby origins in the same frame window don't each repeat the same BFS.
- Three levels of obstacle pruning, from cheapest/coarsest to most thorough, matching the vehicle system's own generation-time-only check but going further: (1) `CityGeneratorPedestrianBuilder.PruneNodesAgainstObstacles` at generation time, against the same shared `obstacles` list every other category uses; (2) `PedestrianNetwork.PrunePlacedObstacles`, a `Physics.CheckSphere`-based auto-repair pass that runs every `Awake` (so it also catches a building moved/added by hand after generation); (3) the same method exposed as `[ContextMenu("Prune Placed Obstacles")]` / `Tools > City Generator > Rebuild Pedestrian Network` for an explicit re-bake without entering Play. Level 2/3 can't detect a user prefab with **no `Collider` anywhere in its hierarchy** — it still gets avoided at generation time via level 1.
- `PedestrianAgent.cs` — walks the graph destination to destination, moving by transform (no `CharacterController`/`Rigidbody`, mirroring `CarAgent`), driving the same `Speed`/`Grounded` Animator parameters `PlayerController` uses so it shares `CharacterAnimator.controller`'s Locomotion blend tree unmodified. Every `Animator.SetFloat`/`SetBool` call is guarded by a `hasAnimatorController` flag cached in `Awake` — a pedestrian prefab with no `Animator`, or an `Animator` with no controller assigned, still walks fine, but calling `SetFloat`/`SetBool` on it would otherwise spam a console warning every frame. Waits at a curb (`WaitingToCross` state) until `CanCross` clears. `PlanNewDestination` rolls several random candidate destinations and tries them **farthest-first**, not just the single farthest one — a grid-corner block with only one link to the rest of the network would otherwise almost always draw an unreachable "farthest" candidate and idle forever. Every serialized field on it (`walkReferenceSpeed`/`runReferenceSpeed`, `paceFraction`, `runnerChance`, jitter, stop durations…) is written unconditionally onto each generated instance by `CityGeneratorPedestrianBuilder.BuildPedestrians` from `CityGeneratorSettings.pedestrianBehaviour` (Pedestrians tab, Behaviour card) — the script's own field initializers only matter for a `PedestrianAgent` used standalone, outside the generator. Since SPEC 05, `FindPath`'s output buffers are rented from `PedestrianManager`'s `PedestrianPathBufferPool` (below) for the duration of planning rather than kept as a permanent per-agent array sized to the whole graph, and the agent's first `PlanNewDestination` after spawn is deferred by `PedestrianManager`'s staggering (below) instead of firing in `Start`.
- `PedestrianPathBufferPool.cs` (SPEC 05) — a plain pool of `int[]` buffers sized to `PedestrianNetwork.NodeCount`, constructed by `PedestrianManager` in `OnEnable`. Exists because the old per-agent permanent buffer was O(pedestrians × nodes) of memory; now that initial planning is staggered across frames (below), only a small subset of agents is actually planning at any one instant, so a shared pool sized to the graph is enough. `PedestrianAgent.PlanNewDestination` calls `Rent`/`Return` around its `FindPath` calls.
- `PedestrianManager.cs` — ticks every registered `PedestrianAgent` from one central `Update` (`Register`/`Unregister`, called from each agent's `OnEnable`/`OnDisable`), same convention as `TrafficManager`/`CarAgent` (not a scene-global singleton either — `PedestrianAgent` resolves it via `network.Manager`), with the same far-from-camera decision-logic staggering above `staggerMinAgentCount`. On top of that it rebuilds a coarse spatial grid every frame and applies a small local separation nudge between nearby agents, plus a stronger player-avoidance nudge — the only peer-interaction mechanic implemented so far (a `PedestrianState.Interacting` value exists on the enum but is never entered, reserved for a future spec). `PedestrianAgent` has **no jam/gridlock mechanics of its own** — crowding only ever shows as this separation nudge, never a stuck agent — so `CityGeneratorConstants.PedestrianCountWarningThreshold` (0.7 of ring nodes) is much higher than the vehicle one (0.4). `CityGeneratorPedestrianBuilder.AddManagerComponent` configures every field on the generated instance from `CityGeneratorSettings.crowd` (Pedestrians tab, Crowd card). SPEC 05 changes: it owns the `PedestrianPathBufferPool` above and staggers each agent's first `PlanNewDestination` by spawn index across several frames instead of firing every agent's initial plan in the same `Start`; its separation pass now processes each nearby agent pair once instead of twice (once per side) and skips a pair entirely when neither side is "active" this frame under the existing sensor staggering; and it rebuilds `PedestrianRoadProximityGrid` (see above) once per frame, passing in the resolved player `Transform` separately since the player isn't a `PedestrianAgent`.
- Vehicles brake for pedestrians (and for the player) via `CarAgent.pedestrianMask` and a second, independent forward `SphereCastNonAlloc` (`PedestrianAheadClearance`) feeding the same `StopReason.VehicleAhead` braking branch — no dedicated state. `CityGeneratorPedestrianBuilder.EnsurePedestrianLayerAndAssignMask` creates the `Pedestrian` layer the same fail-closed way `EnsureVehicleLayerExists` creates `Vehicle` (first free slot from `FirstUserLayerIndex`, warns and leaves the mask at `0` if none is free) and sets `pedestrianMask` per vehicle instance, exactly like `vehicleMask`. `CityGeneratorSceneBuilder` puts the **player** on this same `Pedestrian` layer too, so vehicles brake for the player regardless of whether `includePedestrians` is on.
- `CityGeneratorColliderUtility.EnsureNonTriggerCollider` (`Editor/`) is the shared collider policy for both generated vehicle and pedestrian instances: the instance **root** always ends up with exactly one dedicated, non-trigger "proxy" collider used exclusively for `CarAgent`'s/`PedestrianAgent`'s own sensor detection — reusing one already on the root (forced non-trigger) if present, or adding a `BoxCollider` sized from the combined `Renderer` bounds otherwise. **A collider that only exists deeper in the prefab's hierarchy is left completely untouched** (not even its `isTrigger`) — that was the SPEC 04 fix: previously such a collider was found via `GetComponentsInChildren` and had `isTrigger` forced off, but its *layer* was never touched, so it still went undetected by a sensor's layer-filtered `SphereCast`/`Physics.CheckSphere` (a collider's layer comes from its own GameObject, not its parent's). The layer the builders assign (`Vehicle`/`Pedestrian`) is applied only to the proxy's own GameObject (the instance root), returned by `EnsureNonTriggerCollider` for that purpose — never propagated to children, so a nested collider keeps whatever layer/`isTrigger` the user's prefab gave it, free to serve its own purpose (typically physical collision against the player's `CharacterController`). Reusing a root collider when present (rather than unconditionally adding a second one) matters because `CarAgent.OnEnable` does `GetComponent<Collider>()` (root-only, singular) to register itself for the bumper-to-bumper identity check — every demo vehicle prefab already carries its own root `BoxCollider`. Called from both `CityGeneratorTrafficBuilder.BuildVehicles` and `CityGeneratorPedestrianBuilder.BuildPedestrians`, never touching the prefab asset. `PedestrianAgent` itself never gets pushed back by its own collider since it moves by setting `transform.position` directly. The 12 `DefaultAssets/Prefabs/Characters/` prefabs double as the default pedestrian list (~8.33% each), same prefabs also selectable as Player Prefab.
- Benches and the plaza centerpiece (`PlazaSettings.benchPrefab`/`centerpiecePrefab`) are plain visual props placed by `CityGeneratorPlazaBuilder`, exactly like a lamp or a bin — **not** wired into `PedestrianNetwork` in any way. They used to register `PointOfInterest` nodes that pedestrians would occasionally walk to and linger at; SPEC 06 removed that entire mechanism (node kind, descriptor, register/connect methods, and `PedestrianBehaviourSettings.poiStopDurationMin`/`Max`) at the user's request, to decouple POIs from pedestrians ahead of a future minimap/POI system built on Custom Places (see below) — don't reintroduce a pedestrian-side POI stop without a new spec.

### Custom Places

Added by `specs/06-custom-places.md`. A `CustomPlaceEntry` (`Editor/CityGeneratorSettings.cs`: title, prefab, `isPointOfInterest`, `occupiesFullBlock`, `blockCell`, `cornerSlot`, `facing`, `positionAssigned`) is a manually-placed, deliberately non-random alternative to a building: the user picks its block (and, unless it occupies the whole block, one of the 4 corner slots) from a per-entry `CityGeneratorGridPreview` in `SingleSelectQuadrant` mode, and a fixed 90°-step `facing` — never the random rotation a normal building gets. `CityGeneratorCustomPlaceBuilder.BuildCustomPlaces` instantiates every valid entry before `CityGeneratorBuildingBuilder` runs (see the pipeline above), returning the set of slots it reserves so the building builder excludes them from that block's random distribution; its instances join the shared `obstacles` list, so a Custom Place — unlike a normal building, deliberately exempt from overlap-checking — does participate in prop/vegetation overlap avoidance.

- `positionAssigned` distinguishes "never placed yet" from a legitimate `(0, 0)` selection; `CityGeneratorValidator.ValidateDetailed` blocks generation on a missing title/prefab, no position assigned, a `blockCell` outside the grid or pointing at a plaza block, and a slot conflict between two entries (same corner, or either entry occupying the whole block) — same "explicit blocking error, never silently resolved by list order" convention as every other list in the tool.
- `cornerSlot` reuses `CityGeneratorBuildingBuilder.SlotOffsets`' 0-3 index rather than a separate corner enum, so the picker, `CityGeneratorCustomPlaceBuilder` and `CityGeneratorBuildingBuilder` all agree on one geometric source of truth.
- `isPointOfInterest` is saved and shown in the UI but has **no functional effect yet** — a deliberate placeholder for a future minimap/POI system that will be built on top of Custom Places (see "Pedestrian system" above for why the *old* POI mechanism was removed instead of reused).
- `CityGeneratorCustomPlaceList` (`Editor/UI/`) is the list editor for the Custom Places tab: each row is self-contained (own title/prefab/toggle/facing controls plus its own grid preview), same convention as `CityGeneratorWeightedPrefabList`'s rows. Its fields are plain `TextField`/`ObjectField`/`Toggle`/`EnumField` controls, not `PropertyField` — see the `CityGeneratorWindow` note above for why a `PropertyField` on a row created this late never binds.
- A Custom Place is never allowed on a plaza block (same rule as normal buildings: a block is either a plaza or buildable, no mixed case), and a quarter-block entry coexists with up to 3 random buildings in the same block's other corners — only `occupiesFullBlock` clears the whole block.

### Demo content — `Packages/com.santiandrade.citygenerator/DefaultAssets/`

Ships inside the package (moved there by SPEC 02 so it's portable to any project that installs it), loaded by `CityGeneratorDefaultAssets` from hardcoded `DefaultAssets/...` paths. Unity treats package content as read-only in the consuming project — to edit a demo prefab, copy it into your own `Assets/` first.

- `DefaultAssets/Prefabs/` — by category: `Buildings/` (16 modelled prefabs — `Building-A` through `Building-M` plus `Building-Skyscraper-A` through `-E` — root scale 10, pivot at base, own collider; widest footprint ~13.9 m, clearing the 22 m slot), `Characters/` (12 selectable Player Prefab candidates, doubling as the default pedestrian list — `Character-Male-A` through `-F`, `Character-Female-A` through `-F` — each a clean model+Animator prefab with no movement component baked in; the default Player Prefab is `Character-Male-D`), `Floors/` (`RoadBase`, `RoadSidewalk`, `RoadDash`, `RoadZebra`, `Lawn` — ProBuilder-authored slabs), `Props/` (`Bench`, `Bin`, `Lamp`, `TrafficLight`, and `Fountain`, the only imported-model prop, built on `DefaultAssets/Models/Props/Fountain by Poly.glb` via glTFast), `Vegetation/Tree.prefab`, `Vehicles/` (15 prefabs: `Ambulance`, `Delivery-Flat`, `DeliveryCar`, `Firetruck`, `Garbage-Truck`, `Hatchback-Sports`, `PoliceCar`, `Sedan`, `SedanSportCar`, `Suv`, `Suv-Luxury`, `TaxiCar`, `Truck`, `Truck-Flat`, `Van`).
- Colliders are deliberately simple: `BoxCollider`s on floors, benches, lamps and traffic lights; `MeshCollider`s only on `Tree` (trunk + crown); **no collider at all** on road markings. Vehicles carry a single root `BoxCollider` (no `Rigidbody` — they move by transform, and the collider exists only so they can detect each other); see `CityGeneratorColliderUtility` above for what happens at generation time when a vehicle or pedestrian prefab has none.
- Each of the 15 vehicle prefabs carries its own baked `CarAgent` component with distinct tuning (`maxSpeed`, `acceleration`, `braking`, `turnSpeed`, `cornerSpeedFactor`) so mixed traffic doesn't drive identically: heavy vehicles (`Garbage-Truck`, `Truck`, `Truck-Flat`, the delivery vans) are slowest with the widest turns, emergency vehicles (`Ambulance`, `Firetruck`, `PoliceCar`) are tuned for snappy acceleration, and sports/luxury cars (`Hatchback-Sports`, `SedanSportCar`, `Suv-Luxury`) are fastest and hardest-accelerating. `CityGeneratorTrafficBuilder.BuildVehicles` only `AddComponent`s a fresh `CarAgent` (with the script's own defaults) when a prefab doesn't already carry one — **every vehicle prefab must keep its baked `CarAgent`**, or it silently falls back to identical default tuning at generation time. The generator adds a ±6% `maxSpeed` jitter per instance on top.
- `DefaultAssets/Materials/` — the flat-colour URP/Lit palette (14 materials: `Asphalt`, `Sidewalk`, `RoadLine`, `Crosswalk`, `Grass`, `GlassBlue`, `TreeTrunk`/`TreeLeaves`, `MetalDark`, and the emissive `LightRed`/`LightAmber`/`LightGreen`/`LightOff`/`LampWarm`). Created by editor script, not by hand. The fountain is the only geometry that doesn't use this palette — it keeps the materials embedded in its `.glb`.
- `DefaultAssets/Meshes/` — extracted mesh assets backing the ProBuilder-authored floor/prop prefabs.
- `DefaultAssets/Animations/CharacterAnimator.controller` — created via `UnityEditor.Animations.AnimatorController` (editor script), not hand-authored YAML. Base layer: `Locomotion` (1D blend tree on `Speed`: idle→walk→sprint), `Jump`, `Fall`. Shared by all 12 `Characters/` prefabs (each just points its `Animator.m_Controller` at it), rather than each carrying its own copy.
- `DefaultAssets/Models/` — only the FBX/glb models a demo prefab actually references (16 buildings, 15 cars, 12 character FBX — `character-male-a` through `-f`, `character-female-a` through `-f` — the fountain `.glb`), decided by `AssetDatabase.GetDependencies` over the demo prefabs and `CharacterAnimator.controller`, not by inspection. Everything else from the same asset packs stays in `Assets/Models/` in this repo (see Project overview) and is **not** part of the package — this no longer includes any `Characters/` orphans: the 12 characters referenced by demo prefabs moved into the package, and the remaining 14 (10 mobility-aid models, 4 wheelchairs), never referenced by any demo prefab, were removed from the repo entirely rather than kept as orphans. `Buildings/` and `Cars/` still each carry a `Textures/colormap.png` — a texture atlas shared with the orphan models of the same category still in `Assets/Models/`, so it's **copied** into the package (not moved) to avoid breaking those orphans; the same file exists in both places on purpose (this no longer applies to `Characters/`, since no character orphans remain). Each of the 12 character FBX's importer was reconfigured by editor script to `animationType: Generic` with an Avatar created from the model, and `idle`/`walk`/`sprint`/`fall`/`crouch`/`static` set to loop.
- `DefaultAssets/Input/InputSystem_Actions.inputactions` — the only input asset (`generateWrapperCode: 0`; scripts look up the `Player` map and its actions by name through a serialized `InputActionAsset` reference). The project uses the new Input System exclusively (`activeInputHandler: 1`) — `UnityEngine.Input` throws at runtime. The tool takes this asset as a *setting* (`general.inputActions`), never by hardcoded path.
- `Assets/Settings/` — URP pipeline assets (separate PC and Mobile renderer/pipeline configs) and volume profiles. Project configuration, not part of the package; see `docs/technical-review.md` for the recommended values.

### The test suite — `Assets/Tests/` (outside the package)

Added by `specs/05-performance-and-tests.md`. Lives outside `Packages/com.santiandrade.citygenerator/` on purpose, same reasoning as `Assets/Editor/CityGeneratorReleaseWindow.cs`/`CityGeneratorSetDefaultsWindow.cs`: it's a development tool for this repo, not something a user installing the package by git URL needs or expects. Three folders, each its own `.asmdef` referencing `CityGenerator.Runtime`/`CityGenerator.Editor`:

- `Assets/Tests/EditMode/` — `CityGeneratorGrid` (blocks/plazas), `CityGeneratorDistributionUtility` (percentage distribution), `CityGeneratorValidator.ValidateDetailed` (including the SPEC 04 gaps and the SPEC 06 Custom Places checks), `RouteWeight`/`Ring` route weighting, `PedestrianNetwork` (BFS via `FindPath`, `CanCross`, connected components). `Assets/Tests/EditMode/Generation/` runs full seeded generation on 1×3/5×5/10×10 grids, asserting no exceptions and basic invariants (block/building/network-node counts) — this is what confirms the SPEC 05 performance changes never altered placement output for a given seed; `CustomPlaceBuilderTests.cs` (SPEC 06) does the same for a quarter-block and a whole-block Custom Place entry, asserting the reserved slot(s) are excluded from `CityGeneratorBuildingBuilder`'s random distribution and that the entry lands in `obstacles`.
- `Assets/Tests/PlayMode/` — `TrafficLightIntersection`'s phase cycle, `PedestrianNetwork.CanCross` (red-only crossing), `TrafficManager`/`PedestrianManager` registration/deregistration (including re-`SetActive` reactivation), and collider-on-child detection (the SPEC 04 fix, now automated instead of manual QA).
- `Assets/Tests/Performance/` — uses `com.unity.test-framework.performance` (a dependency of this project's `manifest.json`, not of the package's `package.json`, since the tests live outside it): generation time/`GC Alloc` per grid size, and runtime frame cost (`Measure.Frames`) at 60/150/300 combined vehicles+pedestrians. This suite is what caught a real regression during SPEC 05 (an `IndexOutOfRangeException` from `PedestrianNetwork`'s connected-components array falling out of sync with a POI-grown node list) — treat a Performance test failure as a correctness signal, not noise. Baseline and delta numbers for every SPEC 05 change are recorded in `specs/05-performance-and-tests.md`.

No CI integration exists — these run manually from the Unity Test Runner (`Window > General > Test Runner`), same as any other Editor workflow in this project.

### Versioning and releasing the package

- `Packages/com.santiandrade.citygenerator/package.json` carries the SemVer `version`; `CHANGELOG.md` in the same folder follows Keep a Changelog, with a `## [Unreleased]` section always present above the latest release. A git tag `vX.Y.Z` marks each release.
- Unity has **no real "Update" button for a package installed by git URL** — installing fixes the resolved commit in `Packages/packages-lock.json`. Updating means reinstalling the URL with the new tag; this is documented for end users in the root README.
- `Assets/Editor/CityGeneratorReleaseWindow.cs` (`Tools > City Generator > Release`, outside the package, in `Assembly-CSharp-Editor`) automates the repetitive part: bumps `version` in `package.json`, turns `## [Unreleased]` into `## [X.Y.Z] - YYYY-MM-DD` and opens a new empty `## [Unreleased]` above it, then shows (and copies to the clipboard) the `git tag vX.Y.Z && git push origin vX.Y.Z` command. It never runs git itself — the tag is always created by a person, on purpose.

## Working in this project

- There is no CLI build/lint pipeline, and no CI — the project is edited and run through the Unity Editor (or Rider/Visual Studio via the generated `.sln`). The `Unity.*.csproj` files and `.sln` at the root are IDE-generated and regenerated automatically; never hand-edit or commit them (they are gitignored). There is a test suite (`Assets/Tests/`, see below), but it too runs manually from the Unity Test Runner, not from a CLI command.
- **Fixes belong in the tool, not in the scene.** If generated output is wrong, change the builder that produced it and regenerate. Hand-editing `City.unity` fixes exactly one city and is lost on the next generation.
- **The tool must stay portable to any Unity project**: no dependency on this project's prefabs, materials, layers or assets outside the package's own `DefaultAssets/`, and no mutation of the user's assets. Anything project-specific belongs in the demo content, in `CityGeneratorDefaultAssets`, or in `Assets/Editor/` (`CityGeneratorReleaseWindow.cs`, `CityGeneratorSetDefaultsWindow.cs`) — never in the rest of `Packages/com.santiandrade.citygenerator/`.
- New code goes in `Packages/com.santiandrade.citygenerator/Runtime` (namespace `CityGenerator.Runtime`) or `Packages/com.santiandrade.citygenerator/Editor` (namespace `CityGenerator.Editor`) — extend those, don't introduce a new namespace, and remember both are behind `.asmdef`s, so anything new they reference must be added to the asmdef's `references`.
- Structural, hard-to-hand-author assets (AnimatorControllers, ModelImporter reconfiguration, prefab creation) are built via one-off editor scripts run through the Unity MCP tooling (`Unity_RunCommand`), not by writing `.controller`/`.meta`/`.prefab` YAML directly — prefer that same approach. Create prefabs with `PrefabUtility.SaveAsPrefabAsset`, place instances with `PrefabUtility.InstantiatePrefab`, and edit existing prefabs with `PrefabUtility.LoadPrefabContents`/`SaveAsPrefabAsset`.
- Prefer `BoxCollider`s over `MeshCollider`s on new props and floors; leave purely decorative geometry (markings, glass, small details) with no collider.
- Unity here does not pick up new/edited scripts on its own while the Editor is in the background: creating a `.cs` and calling `AssetDatabase.Refresh()` leaves the assembly stale (the type is missing from `AppDomain`, and `Unity_RunCommand` fails to compile against it). Force it with `UnityEditor.Compilation.CompilationPipeline.RequestScriptCompilation()`, then wait — the domain reload makes the MCP briefly report "Unity not detected", and only after it do the new types resolve. Check `Unity_ReadConsole` when a type still fails to appear.
- ProBuilder 6.1.2 is installed for the demo floor/prop geometry. From an editor script, generate shapes with `UnityEngine.ProBuilder.ShapeGenerator.*`, then call `ToMesh()`, `Refresh()` and `UnityEditor.ProBuilder.EditorMeshUtility.Optimize(pb)` — `UnityEditor.ProBuilder.EditorUtility.InitObject` is `internal` in this version. Two gotchas in `Unity_RunCommand` scripts: `EditorUtility` is ambiguous once `UnityEditor.ProBuilder` is imported (qualify as `UnityEditor.EditorUtility`), and `Object.GetInstanceID()` is obsolete in this Unity version (`GetEntityId()`).
- Nothing in C# refers to the scene, the city root or the materials folder by name; material references are serialized by GUID. Editor scripts that need the city root should look it up as `GameObject.Find("City")`.
