# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a Unity project (`City Generator`, Unity `6000.5.8f1`, URP) whose **only reason to exist is to develop, test and distribute the City Generator tool** — an Editor window that procedurally generates a city (roads, sidewalks, markings, buildings, plazas, street furniture, traffic lights, autonomous traffic and pedestrians) into a new or existing scene.

The tool lives in the embedded package `Packages/com.santiandrade.citygenerator/` and that package **is** the deliverable: it is what a user installs into their own Unity project via **Package Manager > Install package from git URL**. This project consumes the tool the same way — as an installed package, not as loose code in `Assets/` — so a portability break shows up here first, not in the user's project. See the root `README.md` (English) / `README.es.md` (Spanish) for the install URL, the update procedure and full user-facing documentation. Everything else in the repo exists to support the package, in one of three roles:

- **Demo content**, inside the package at `Packages/com.santiandrade.citygenerator/DefaultAssets/` — the sample prefabs the tool ships with so it works out of the box, loaded by `CityGeneratorDefaultAssets`. It travels with the package to any project that installs it; only the models actually referenced by a demo prefab live here (see "Demo content" below for how that's decided).
- **Orphan models** (`Assets/Models/`) — FBX/glb library entries from the same asset packs as the demo models that no demo prefab currently uses. Kept in this repo on purpose for future use, but deliberately **not** part of the package, so installing it doesn't drag along unused models.
- **Test scene** (`Assets/Scenes/City.unity`) — a **disposable** scene generated by the tool, kept only to eyeball the output. It is regenerated freely and carries no hand-made work worth preserving. Never treat it as a source of truth, and never hand-edit it to fix something the tool should be doing.

The tool's behaviour is considered **done and correct**: reproduce it, don't redesign it. Its original spec lives in `specs/01-city-generator-tool.md` (Spanish, driven by a `/spec-*` workflow configured by `specs/.spec-config.yml`); read it before touching the tool's generation logic — it records the decisions taken **and explicitly discarded**, several of them found during manual QA. `specs/02-unity-package-distribution.md` is the spec for the package/distribution work described in this file (embedding, demo content movement, README, versioning, release tooling) — it does not touch generation behaviour. `specs/03-pedestrian-network.md` is the spec for the autonomous pedestrian system (see "Pedestrian system" below). `docs/technical-review.md` is the standing technical review (performance, code quality, ECS analysis) with the pending findings.

Historical note: the layout the tool reproduces was originally a hand-built city made of ProBuilder primitives. That hand-made city no longer exists (commit `ff13e28`, "Removed old city"). The numbers extracted from it survive as `CityGeneratorConstants`.

## Structure

### The tool — `Packages/com.santiandrade.citygenerator/` (the installable package)

An embedded Unity package (`package.json`, `name` `com.santiandrade.citygenerator`, `unity` `6000.0`, dependencies `com.unity.inputsystem` and `com.unity.cloud.gltfast`). Two assemblies, each with its own `.asmdef`:

- `Runtime/CityGenerator.Runtime.asmdef` — namespace `CityGenerator.Runtime`, references `Unity.InputSystem`.
- `Editor/CityGenerator.Editor.asmdef` — namespace `CityGenerator.Editor`, `includePlatforms: [Editor]`, references the runtime asmdef and `Unity.InputSystem`. Every type in it is `internal static` except the window and the `Editor/UI/` visual-element classes below (which need instance state to exist at all).

**`CityGeneratorWindow`** — `Tools > City Generator > Open`. Holds the entire configuration in a single `[SerializeField] CityGeneratorSettings settings`, which is why state survives closing/reopening the window within an Editor session; **deliberately not a `ScriptableObject`** (see the spec's discarded decisions). The window is built with **UI Toolkit** (`CreateGUI`, not `OnGUI`): `Editor/UI/CityGeneratorWindow.uxml` is the structural skeleton (banner, scrollable card container, footer) cloned into `rootVisualElement`, styled by `CityGeneratorWindow.uss` plus a theme sheet (`_Dark`/`_Light`, picked by `EditorGUIUtility.isProSkin`) that only redefines `--cg-*` color variables; every section is built in code as a `CityGeneratorCard` (collapsible, open/closed state persisted per-card in `EditorPrefs`, badge summarising its content, turns red when one of its fields fails validation). Bound the standard UI Toolkit way — `rootVisualElement.Bind(serializedWindow)` plus per-field `PropertyField`s constructed straight from a `SerializedProperty` — except three custom controls that manage their own `SerializedProperty` reads/writes: `CityGeneratorGridPreview` (a `Painter2D` top-down miniature of the grid, doubling as the plaza editor — clicking a block toggles it directly against `general.plazaCells`, a `List<Vector2Int>` of block coordinates, so the picture and the generated scene can never disagree; there is no separate plaza count), `CityGeneratorPrefabGrid` (thumbnail grid for `buildingPrefabs`/`vegetation.prefabs`) and `CityGeneratorWeightedPrefabList` (thumbnail + percentage slider + stacked bar + "Normalize to 100%" for `vehicles`/`pedestrians` — deliberately never rebuilds its rows on a plain percentage edit, only on add/remove/normalize, because tearing down the dragged `Slider` mid-drag would drop its pointer capture and abort the gesture). `CityGeneratorValidator.ValidateDetailed` (same checks as the original `Validate`, each issue additionally tagged with the settings path that caused it) is re-run on every edit via `TrackSerializedObjectValue`, driving live required-field/card highlighting and disabling both Build buttons until every issue clears — replacing the old blocking `EditorUtility.DisplayDialog` validation-error flow. Two buttons — "Build City in New Scene" and "Re-Build City in Current Scene" (destroys the `City` root and regenerates it, leaving light/camera/player alone) — drive an `EditorUtility.DisplayProgressBar` through an optional `onProgress` callback threaded (additively — default `null`) through `CityGeneratorContentAssembler.Assemble` → `CityGeneratorSceneBuilder`, and show the result in an in-window panel (with a "Ping Scene" button) instead of a dialog; "Reset to Defaults" stays a plain button, low-key styled. A separate menu entry, `Tools > City Generator > Set Current Selection As Default`, captures whatever is currently assigned in an open window's `settings` and writes it back as the tool's new default — see `CityGeneratorDefaultAssetsWriter` below.

**Pipeline**, in order: `CityGeneratorValidator` (runs first, blocks generation with a dialog + console errors) → `CityGeneratorSceneBuilder` (new scene + directional light + camera + player, saved as the next free `Assets/Scenes/City<N>.unity`) → `CityGeneratorContentAssembler` (the group hierarchy and every builder) → `Grid` → `GroundBuilder` → `BuildingBuilder` → `PlazaBuilder` → `StreetPropsBuilder` → `TrafficBuilder`.

- `CityGeneratorConstants` holds the layout numbers (46 m blocks on a 56 m pitch, `GroundDatumY` 0.18, 22 m building slots, lamp/zebra/traffic-light offsets…). Most constants carry a comment explaining *why* that value — several were tuned against real overlap bugs (lamps clearing the plaza lawn, zebra stripes vs. dashed centreline, corner margin so wide prefabs don't collide across a corner). Change them from there, never inline.
- **Overlap avoidance is the tool's central mechanism, but only for props and vegetation** — buildings and vehicles are deliberately exempt. `CityGeneratorBoundsUtility.GetWorldBounds` combines all child `Renderer` bounds, and `CityGeneratorPlacementEngine` instantiates a candidate, checks its XZ `Rect` against every already-placed object, and `DestroyImmediate`s it if it overlaps. Bounds, not fixed per-category radii, because the prefabs come from the user. `ContentAssembler` threads one growing `obstacles` list through every category in turn — if you add a category, append its result to that list.
- `CityGeneratorPlayerSpawner.FindSpawnPosition` picks where the player instance lands: inside a plaza block when the city has one (searched in random order across plazas), a random block otherwise, checked against the same growing `obstacles` list (minus ground cover, since standing on lawn/sidewalk is the point) so the player never spawns overlapping a building/prop/vehicle. `CityGeneratorSceneBuilder.EnsurePlayerComponents` then `AddComponent`s `CharacterController` and `PlayerController` — with hardcoded default tuning from `CityGeneratorConstants` — to whichever prefab is assigned as Player Prefab, if it doesn't already carry them. This is what lets `DefaultAssets/Prefabs/Characters/` stay 12 clean model+Animator prefabs instead of each needing its own baked movement setup, and equally lets a user-supplied character work as Player Prefab with zero manual setup.
- `CityGeneratorBuildingBuilder.BuildBuildings` picks up to 4 fixed 22 m corner slots per non-plaza block, guaranteeing every assigned building prefab is used at least once. **Which corners are filled is shuffled per block** when `buildingsPerBlock < 4` — a QA-found bug had every block always fill corners `0..buildingsPerBlock-1` in the same order, making partially-built blocks look identical everywhere. Buildings are **not** overlap-checked against each other or against the block edge: an oversized building prefab will visibly clip into its neighbour or spill into the street — accepted as the user's responsibility to size their prefabs to the 22 m slot, same as any other user-supplied prefab.
- Densities mean "fraction of valid candidate points filled", not an absolute count — including `lampDensity` (1 = all 3 candidate points per block side).
- `CityGeneratorContentAssembler` applies `BatchingStatic | OccluderStatic | OccludeeStatic` to every generated group **except `Vehicles`/`Pedestrians`**, so each generated city is batched and ready for a lightmap/occlusion bake with no manual pass. `CarAgent`/`PedestrianAgent` move their instances by transform every frame, which is why both are excluded.
- `CityGeneratorTrafficBuilder.BuildVehicles` calls `EnsureVehicleLayerExists` before spawning anything: if the project has no `Vehicle` layer yet, it creates one itself by writing directly to `ProjectSettings/TagManager.asset` via `SerializedObject`, using the first free slot from `CityGeneratorConstants.FirstUserLayerIndex` (8) up, and logs that it did so. Requiring the user to create this layer by hand was a recurring point of confusion during SPEC 02 verification. Only if every slot 8-31 is already taken does it fall back to warning instead — in that case every instance's `CarAgent.vehicleMask` is left at `0` (Nothing) rather than matching whatever layer the instance happens to share with unrelated scene geometry, so vehicles simply stop detecting each other (they still stop for lights and unsignalled-crossing priority) until a slot frees up. `CarAgent` and the `Vehicle` layer are added **to the scene instances only**, never to the user's prefab asset, and outer-edge exit nodes are skipped when spawning (a car there has nothing ahead and `CarAgent` disables itself). When the layer does exist, `BuildVehicles` sets `CarAgent.vehicleMask` to `1 << instance.layer` per instance via `SerializedObject` — **do not rely on the mask baked into a vehicle prefab's own serialized data**: it only happens to work when `Vehicle` sits at the same layer index the prefab was authored against, and silently makes the forward sensor blind to every other vehicle otherwise (found during SPEC 02 verification: the demo prefabs' baked `vehicleMask` and `m_Layer` both happened to reference index 8, which is why the bug went unnoticed). `CityGeneratorConstants.VehicleDensityWarningThreshold` (0.4 of spawn nodes) is surfaced only as a live `HelpBox` in `CityGeneratorWindow` while editing `vehicleCount` — `BuildVehicles` itself no longer logs a console warning past that threshold, since the inspector already told the user before they clicked generate; measured on a 5×5 grid, 38% of nodes flowed, 76% gridlocked from the first frame.
- `CityGeneratorPedestrianBuilder` builds the pedestrian network and NPCs, mirroring `CityGeneratorTrafficBuilder`: the `PedestrianNetwork` graph (see "Pedestrian system" below) is always built and pruned against the shared `obstacles` list, independent of `includePedestrians`, so its crossings stay wired to the real traffic lights even when no NPCs are spawned; NPC instances are only placed when `includePedestrians` is on. `CityGeneratorDistributionUtility.DistributePercentages` (a generic largest-remainder distributor) is shared between `BuildVehicles` and `BuildPedestrians` rather than duplicated per category. `EnsurePedestrianLayerAndAssignMask` is called whenever vehicles exist (not gated on `includePedestrians`), since `CityGeneratorSceneBuilder` puts the player on the same `Pedestrian` layer and vehicles must detect it either way.
- `general.useCustomSeed` (off by default) + `general.seed` make generation reproducible: `Assemble` uses `new System.Random(seed)` when enabled, unseeded otherwise. Every builder receives that one `System.Random` **by parameter** — none of them touch `UnityEngine.Random`, so seeding it is enough to make placement and prefab choice fully deterministic (`CarAgent`'s runtime driving still uses `UnityEngine.Random`, unrelated to generation). Which blocks are plazas is **not** part of this: `CityGeneratorGrid.BuildBlocks` takes `general.plazaCells` directly and never touches `random` — it used to draw a random subset here (`ChoosePlazaIndices`), which is why the grid preview couldn't reliably match the generated scene; now the preview edits `plazaCells` directly (see `CityGeneratorGridPreview` above), so they can't disagree.
- The generated `Main Camera`'s transform is a **hand-tuned fixed value**, not Unity's defaults: position `(36, 28, -36)`, rotation `Euler(27, -45, 0)`, `fieldOfView` 45.
- No `Global Volume` is generated — removed on purpose (commit `a094fef`) to keep the tool render-pipeline-agnostic.
- `CityGeneratorDefaultAssets.ApplyTo` fills a fresh `CityGeneratorSettings` with the package's own demo prefabs (buildings, vegetation, vehicles and pedestrians with their percentages, ground, plaza prefabs and layout (`plazaCells`), props, player, input actions), loaded from hardcoded `Packages/com.santiandrade.citygenerator/DefaultAssets/...` paths, so the window opens ready for a one-click first generation instead of empty required fields. Since SPEC 02 those paths resolve in any project that installs the package (the demo content ships inside it), so this file is no longer the one non-portable file in the tool — it's ordinary portable code, just tied to the bundled demo assets rather than to generation logic. It cannot run from a field initializer on `CityGeneratorSettings` (Unity forbids `AssetDatabase` calls during `EditorWindow` deserialization); it is invoked from `CityGeneratorWindow.OnEnable()`, gated by a serialized `defaultsInitialized` flag so it runs once per window instance, and again from "Reset to Defaults".
- `CityGeneratorDefaultAssetsWriter.SaveCurrentAsDefault` is the other direction: given an open window's `settings`, it regenerates `CityGeneratorDefaultAssets.cs`'s `ApplyTo` body wholesale (asset lists can change length between calls, e.g. after swapping in new building or vehicle prefabs, which a targeted text edit can't express as cleanly as a full rewrite) and patches the scalar field initializers in `CityGeneratorSettings.cs` in place via `Regex` (safe because every scalar field name — `gridWidth`, `vehicleCount`, `density`, etc. — is unique within that file). Both are plain `File.WriteAllText` calls against the package's own source under `Packages/`, followed by `AssetDatabase.Refresh()`. Kept in its own file rather than folded into `CityGeneratorDefaultAssets` because it overwrites that file's contents — it must never need to regenerate itself. A prefab assigned from outside `DefaultAssets/` still gets written into the new default (the command never blocks on it), but the result only resolves in this project; flagged with a console warning per offending field rather than silently accepted.

### Runtime components — `Packages/com.santiandrade.citygenerator/Runtime/`

These ship with the tool and are what a generated city runs on.

- `PlayerController.cs` — walk/run/jump via the new Input System (`Player` action map: `Move`, `Sprint`, `Jump`). Movement is camera-relative. Drives the Animator's `Speed`, `Grounded`, `Jump`, `VerticalSpeed`. `[RequireComponent(typeof(CharacterController))]`, but neither it nor `CharacterController` are baked into the demo character prefabs — see `CityGeneratorSceneBuilder.EnsurePlayerComponents` below.
- `ThirdPersonCamera.cs` — Mario-64-style orbit camera, reads `Look` from the same map. Only the target-follow *position* is smoothed (`SmoothDamp`); rotation is recomputed every frame as `LookRotation` from the camera's actual (possibly lagging) position to the pivot, so position and aim can never desync — **do not reintroduce separate smoothing on `transform.rotation`**, that was tried and caused visible motion sickness. Pivot offset is `verticalOffset` + `horizontalOffset` (the latter along the orbit's local right axis, i.e. over-the-shoulder), not a single `Vector3`. Has camera-vs-environment `SphereCast` collision.
- `TrafficLight.cs` / `TrafficLightIntersection.cs` — `TrafficLight` swaps lamp materials (`LightRed`/`LightAmber`/`LightGreen`/`LightOff`) to show its state; `TrafficLightIntersection` runs the coroutine alternating green between its `eastWest` and `northSouth` groups with amber and all-red phases, with a per-intersection `startOffset` so neighbours are not in sync.
- `TrafficNetwork.cs` — *generates* the lane graph in `Awake` from the same layout as the geometry (`laneOffset` 2.6; nodes are computed, not serialized). The axes are **two independent arrays**, `axesX` and `axesZ`, so grids need not be square; `SetAxes` + the public `Build()` let the generator set the layout, place all traffic lights, and only then build the graph (`Build` matches lights by scanning the scene, so order matters). `EnsureBuilt` covers accessors called before `Awake`. Per intersection and direction there is an *entry* node (the inner corner of the crossing: where the turn is chosen and where the light applies) and an *exit* node; turning right needs no intermediate node because one direction's entry coincides geometrically with the exit of the direction to its right. Lights are matched **by geometry, not by name**: each entry gets the `TrafficLight` facing it head-on (`Dot(light.forward, direction) < -0.9`), which leaves outer intersections unsignalled. It also calls `Physics.SyncTransforms()` once per frame after the agents have moved, because the project runs with `m_AutoSyncTransforms: 0` and `CarAgent` moves by transform then raycasts in the same frame.
- `CarAgent.cs` — follows the graph picking turns at random (`straightWeight` favours going straight), brakes progressively for red/amber and for the car ahead, and takes corners with `RotateTowards` plus a speed cut, not by interpolating positions. Falls back to `FindFirstObjectByType<TrafficNetwork>()` in `Start` if `network` wasn't injected by the generator, since a scene only ever has one. Ticked by `TrafficManager` rather than through its own `Update` — see below. Four rules are load-bearing:
  1. Once past the stop line a car keeps going even if the light changes, so it never freezes inside a crossing.
  2. At unsignalled crossings priority is an exclusive per-intersection reservation (`TryReserve`/`Release`, with a timeout), because the forward sensor cannot see cross traffic. **That reservation once deadlocked every car for over five minutes and its current shape *is* the fix — do not revert any of its three pieces**: (a) the owner does *not* refresh its timestamp when re-claiming (if it does, a blocked car holds the reservation forever just by asking every frame and the timeout never expires); (b) priority is claimed only within `claimDistance` of the stop line, slowing down beforehand like a give-way, never from far off; (c) `ReleaseReservationWhileBlocked` drops it when its owner is stopped by another car and has not entered the crossing, breaking the "A waits for the priority B holds, B waits for A to move" cycle. `CurrentStopReason`/`StoppedTime`/`DistanceTravelled` exist to diagnose jams.
  3. In the forward sensor (`SphereCastNonAlloc`, filtered by `vehicleMask` — set per-instance by `CityGeneratorTrafficBuilder` to match the layer it actually placed the vehicle on, not a value baked into the prefab) hits are discarded **by identity** (`other == this`), never by distance: a zero-distance hit is both the car's own collider *and* the car already bumper-to-bumper ahead, and filtering by distance made cars fail to see each other and drive inside one another on corners.
  4. Route weighting (`RouteWeight`/`Ring`, with `interiorBias` and `borderPenalty`) exists because without it all traffic circles the perimeter: on a border street, going straight is the only non-turning exit, ~71% likely at every crossing with the raw straight weight. Measured with the weights, traffic settles around 9/9 perimeter/interior.
- `TrafficManager.cs` — ticks every registered `CarAgent` from a single `Update` (`Register`/`Unregister`, called from each car's `Start`/`OnDisable`) instead of each car paying its own Update marshalling cost (technical review, A.7). `CityGeneratorTrafficBuilder.AddManagerComponent` adds it to the `TrafficNetwork` GameObject only when `includeTraffic` is on; a `CarAgent` used outside the generator falls back to finding or auto-creating one, so it still drives standalone. Below `staggerMinAgentCount` (60 by default) every car's forward sensor runs every frame, identical to the old per-car `Update` — **do not lower this without re-verifying the default 80-car demo still behaves the same**. Above it, cars farther than `staggerDistance` from `Camera.main` only run their `SphereCast` 1 of every `staggerFrames` frames, reusing the previous clearance in between.
- `PerformanceBootstrap.cs` — `[RuntimeInitializeOnLoadMethod]` that sets `vSyncCount = 0` and `targetFrameRate = 60`. Ships with the tool rather than as a project setting so generated cities behave the same in another project.

### Pedestrian system

Added by `specs/03-pedestrian-network.md`, structurally mirroring the vehicle traffic system throughout.

- `PedestrianNetwork.cs` — an **undirected** graph (unlike `TrafficNetwork`'s directed one: a pedestrian can walk either way along every edge), rebuilt in `Awake`/`Build()` from the same street axes. Every block gets an 8-node ring (4 corners + 4 side midpoints) sitting in the gap between the building slot edge and street furniture; every interior intersection additionally gets, per arm, a curb → crossing → curb chain linking two ring corners across the street, with the crossing node matched **by geometry** (nearest `TrafficLightIntersection`, same convention as `TrafficNetwork`'s light matching) so `CanCross` can read the real light state via `TrafficNetwork.AxisState`/`IsAxisGreen` (`TrafficLightIntersection.EastWestState`/`NorthSouthState`). `CanCross` only allows stepping onto the road on **Red**, not just "not green" — Amber still has cars moving through. `FindPath` is a zero-allocation BFS into caller-supplied buffers (shortest by hop count, since every edge is unweighted). A grid with `gridWidth == 1` or `gridHeight == 1` has no interior intersections, so every block's ring is isolated — surfaced as a non-blocking `HelpBox` in `CityGeneratorWindow`, same convention as the vehicle density warning.
- Three levels of obstacle pruning, from cheapest/coarsest to most thorough, matching the vehicle system's own generation-time-only check but going further: (1) `CityGeneratorPedestrianBuilder.PruneNodesAgainstObstacles` at generation time, against the same shared `obstacles` list every other category uses; (2) `PedestrianNetwork.PrunePlacedObstacles`, a `Physics.CheckSphere`-based auto-repair pass that runs every `Awake` (so it also catches a building moved/added by hand after generation); (3) the same method exposed as `[ContextMenu("Prune Placed Obstacles")]` / `Tools > City Generator > Rebuild Pedestrian Network` for an explicit re-bake without entering Play. Level 2/3 can't detect a user prefab with **no `Collider` anywhere in its hierarchy** — it still gets avoided at generation time via level 1.
- `PedestrianAgent.cs` — walks the graph destination to destination, moving by transform (no `CharacterController`/`Rigidbody`, mirroring `CarAgent`), driving the same `Speed`/`Grounded` Animator parameters `PlayerController` uses so it shares `CharacterAnimator.controller`'s Locomotion blend tree unmodified. Waits at a curb (`WaitingToCross` state) until `CanCross` clears. `PlanNewDestination` rolls several random candidate destinations and tries them **farthest-first**, not just the single farthest one — a grid-corner block with only one link to the rest of the network would otherwise almost always draw an unreachable "farthest" candidate and idle forever.
- `PedestrianManager.cs` — ticks every registered `PedestrianAgent` from one central `Update` (`Register`/`Unregister`), same convention as `TrafficManager`/`CarAgent`, with the same far-from-camera decision-logic staggering above `staggerMinAgentCount`. On top of that it rebuilds a coarse spatial grid every frame and applies a small local separation nudge between nearby agents, plus a stronger player-avoidance nudge — the only peer-interaction mechanic implemented so far (a `PedestrianState.Interacting` value exists on the enum but is never entered, reserved for a future spec). `PedestrianAgent` has **no jam/gridlock mechanics of its own** — crowding only ever shows as this separation nudge, never a stuck agent — so `CityGeneratorConstants.PedestrianCountWarningThreshold` (0.7 of ring nodes) is much higher than the vehicle one (0.4).
- Vehicles brake for pedestrians (and for the player) via `CarAgent.pedestrianMask` and a second, independent forward `SphereCastNonAlloc` (`PedestrianAheadClearance`) feeding the same `StopReason.VehicleAhead` braking branch — no dedicated state. `CityGeneratorPedestrianBuilder.EnsurePedestrianLayerAndAssignMask` creates the `Pedestrian` layer the same fail-closed way `EnsureVehicleLayerExists` creates `Vehicle` (first free slot from `FirstUserLayerIndex`, warns and leaves the mask at `0` if none is free) and sets `pedestrianMask` per vehicle instance, exactly like `vehicleMask`. `CityGeneratorSceneBuilder` puts the **player** on this same `Pedestrian` layer too, so vehicles brake for the player regardless of whether `includePedestrians` is on.
- Each generated pedestrian instance gets a non-trigger `BoxCollider` sized from its own renderer bounds (`CityGeneratorPedestrianBuilder.AddCollider`, never added to the prefab asset) — not a trigger, unlike vehicles, so the player's `CharacterController` physically collides with NPCs; `PedestrianAgent` itself never gets pushed back since it moves by setting `transform.position` directly. The 12 `DefaultAssets/Prefabs/Characters/` prefabs double as the default pedestrian list (~8.33% each), same prefabs also selectable as Player Prefab.
- `PlazaSettings`-driven `PointOfInterest` nodes: `RegisterPointsOfInterest` wires a bench-radial + short centerpiece-loop into every plaza block's ring after `Build()`, so pedestrians occasionally walk to and linger at a bench/fountain (longer idle duration than a random street stop) instead of only ever looping the sidewalk ring.

### Demo content — `Packages/com.santiandrade.citygenerator/DefaultAssets/`

Ships inside the package (moved there by SPEC 02 so it's portable to any project that installs it), loaded by `CityGeneratorDefaultAssets` from hardcoded `DefaultAssets/...` paths. Unity treats package content as read-only in the consuming project — to edit a demo prefab, copy it into your own `Assets/` first.

- `DefaultAssets/Prefabs/` — by category: `Buildings/` (16 modelled prefabs — `Building-A` through `Building-M` plus `Building-Skyscraper-A` through `-E` — root scale 10, pivot at base, own collider; widest footprint ~13.9 m, clearing the 22 m slot), `Characters/` (12 selectable Player Prefab candidates, doubling as the default pedestrian list — `Character-Male-A` through `-F`, `Character-Female-A` through `-F` — each a clean model+Animator prefab with no movement component baked in; the default Player Prefab is `Character-Male-D`), `Floors/` (`RoadBase`, `RoadSidewalk`, `RoadDash`, `RoadZebra`, `Lawn` — ProBuilder-authored slabs), `Props/` (`Bench`, `Bin`, `Lamp`, `TrafficLight`, and `Fountain`, the only imported-model prop, built on `DefaultAssets/Models/Props/Fountain by Poly.glb` via glTFast), `Vegetation/Tree.prefab`, `Vehicles/` (15 prefabs: `Ambulance`, `Delivery-Flat`, `DeliveryCar`, `Firetruck`, `Garbage-Truck`, `Hatchback-Sports`, `PoliceCar`, `Sedan`, `SedanSportCar`, `Suv`, `Suv-Luxury`, `TaxiCar`, `Truck`, `Truck-Flat`, `Van`).
- Colliders are deliberately simple: `BoxCollider`s on floors, benches, lamps and traffic lights; `MeshCollider`s only on `Tree` (trunk + crown); **no collider at all** on road markings. Vehicles carry a single root `BoxCollider` (no `Rigidbody` — they move by transform, and the collider exists only so they can detect each other).
- Each of the 15 vehicle prefabs carries its own baked `CarAgent` component with distinct tuning (`maxSpeed`, `acceleration`, `braking`, `turnSpeed`, `cornerSpeedFactor`) so mixed traffic doesn't drive identically: heavy vehicles (`Garbage-Truck`, `Truck`, `Truck-Flat`, the delivery vans) are slowest with the widest turns, emergency vehicles (`Ambulance`, `Firetruck`, `PoliceCar`) are tuned for snappy acceleration, and sports/luxury cars (`Hatchback-Sports`, `SedanSportCar`, `Suv-Luxury`) are fastest and hardest-accelerating. `CityGeneratorTrafficBuilder.BuildVehicles` only `AddComponent`s a fresh `CarAgent` (with the script's own defaults) when a prefab doesn't already carry one — **every vehicle prefab must keep its baked `CarAgent`**, or it silently falls back to identical default tuning at generation time. The generator adds a ±6% `maxSpeed` jitter per instance on top.
- `DefaultAssets/Materials/` — the flat-colour URP/Lit palette (14 materials: `Asphalt`, `Sidewalk`, `RoadLine`, `Crosswalk`, `Grass`, `GlassBlue`, `TreeTrunk`/`TreeLeaves`, `MetalDark`, and the emissive `LightRed`/`LightAmber`/`LightGreen`/`LightOff`/`LampWarm`). Created by editor script, not by hand. The fountain is the only geometry that doesn't use this palette — it keeps the materials embedded in its `.glb`.
- `DefaultAssets/Meshes/` — extracted mesh assets backing the ProBuilder-authored floor/prop prefabs.
- `DefaultAssets/Animations/CharacterAnimator.controller` — created via `UnityEditor.Animations.AnimatorController` (editor script), not hand-authored YAML. Base layer: `Locomotion` (1D blend tree on `Speed`: idle→walk→sprint), `Jump`, `Fall`. Shared by all 12 `Characters/` prefabs (each just points its `Animator.m_Controller` at it), rather than each carrying its own copy.
- `DefaultAssets/Models/` — only the FBX/glb models a demo prefab actually references (16 buildings, 15 cars, 12 character FBX — `character-male-a` through `-f`, `character-female-a` through `-f` — the fountain `.glb`), decided by `AssetDatabase.GetDependencies` over the demo prefabs and `CharacterAnimator.controller`, not by inspection. Everything else from the same asset packs stays in `Assets/Models/` in this repo (see Project overview) and is **not** part of the package — this no longer includes any `Characters/` orphans: the 12 characters referenced by demo prefabs moved into the package, and the remaining 14 (10 mobility-aid models, 4 wheelchairs), never referenced by any demo prefab, were removed from the repo entirely rather than kept as orphans. `Buildings/` and `Cars/` still each carry a `Textures/colormap.png` — a texture atlas shared with the orphan models of the same category still in `Assets/Models/`, so it's **copied** into the package (not moved) to avoid breaking those orphans; the same file exists in both places on purpose (this no longer applies to `Characters/`, since no character orphans remain). Each of the 12 character FBX's importer was reconfigured by editor script to `animationType: Generic` with an Avatar created from the model, and `idle`/`walk`/`sprint`/`fall`/`crouch`/`static` set to loop.
- `DefaultAssets/Input/InputSystem_Actions.inputactions` — the only input asset (`generateWrapperCode: 0`; scripts look up the `Player` map and its actions by name through a serialized `InputActionAsset` reference). The project uses the new Input System exclusively (`activeInputHandler: 1`) — `UnityEngine.Input` throws at runtime. The tool takes this asset as a *setting* (`general.inputActions`), never by hardcoded path.
- `Assets/Settings/` — URP pipeline assets (separate PC and Mobile renderer/pipeline configs) and volume profiles. Project configuration, not part of the package; see `docs/technical-review.md` for the recommended values.

### Versioning and releasing the package

- `Packages/com.santiandrade.citygenerator/package.json` carries the SemVer `version`; `CHANGELOG.md` in the same folder follows Keep a Changelog, with a `## [Unreleased]` section always present above the latest release. A git tag `vX.Y.Z` marks each release.
- Unity has **no real "Update" button for a package installed by git URL** — installing fixes the resolved commit in `Packages/packages-lock.json`. Updating means reinstalling the URL with the new tag; this is documented for end users in the root README.
- `Assets/Editor/CityGeneratorReleaseWindow.cs` (`Tools > City Generator > Release`, outside the package, in `Assembly-CSharp-Editor`) automates the repetitive part: bumps `version` in `package.json`, turns `## [Unreleased]` into `## [X.Y.Z] - YYYY-MM-DD` and opens a new empty `## [Unreleased]` above it, then shows (and copies to the clipboard) the `git tag vX.Y.Z && git push origin vX.Y.Z` command. It never runs git itself — the tag is always created by a person, on purpose.

### The test scene — `Assets/Scenes/City.unity`

Currently a 3×3 city generated by the tool with default settings, including 90 pedestrian NPCs (`pedestrianCount` default) plus a `Player` instance placed on the shared `Pedestrian` layer, both at the scene root next to the `City` root's group empties (now including `Pedestrians` and `PedestrianNetwork` alongside the pre-existing `Vehicles`/`TrafficNetwork`). Static flags are set on every generated group except `Vehicles`/`Pedestrians`. Lightmaps and occlusion culling are **not** baked.

The ProBuilder-authored floor/prop prefabs keep their `ProBuilderMesh` component, so each instance stores its regenerated mesh as a scene-local override — the scene holds ~227 embedded `pb_Mesh*` assets. That is expected, and the reason the scene file is ~5 MB. See `docs/technical-review.md` for the standing proposal to remove ProBuilder from those prefabs.

Build Settings list this scene as the only enabled one. It is disposable: regenerate it rather than repairing it.

## Working in this project

- There is no CLI build/test/lint pipeline — the project is edited and run through the Unity Editor (or Rider/Visual Studio via the generated `.sln`). The `Unity.*.csproj` files and `.sln` at the root are IDE-generated and regenerated automatically; never hand-edit or commit them (they are gitignored).
- **Fixes belong in the tool, not in the scene.** If generated output is wrong, change the builder that produced it and regenerate. Hand-editing `City.unity` fixes exactly one city and is lost on the next generation.
- **The tool must stay portable to any Unity project**: no dependency on this project's prefabs, materials, layers or assets outside the package's own `DefaultAssets/`, and no mutation of the user's assets. Anything project-specific belongs in the demo content, in `CityGeneratorDefaultAssets`, or in `Assets/Editor/CityGeneratorReleaseWindow.cs` — never in the rest of `Packages/com.santiandrade.citygenerator/`.
- New code goes in `Packages/com.santiandrade.citygenerator/Runtime` (namespace `CityGenerator.Runtime`) or `Packages/com.santiandrade.citygenerator/Editor` (namespace `CityGenerator.Editor`) — extend those, don't introduce a new namespace, and remember both are behind `.asmdef`s, so anything new they reference must be added to the asmdef's `references`.
- Structural, hard-to-hand-author assets (AnimatorControllers, ModelImporter reconfiguration, prefab creation) are built via one-off editor scripts run through the Unity MCP tooling (`Unity_RunCommand`), not by writing `.controller`/`.meta`/`.prefab` YAML directly — prefer that same approach. Create prefabs with `PrefabUtility.SaveAsPrefabAsset`, place instances with `PrefabUtility.InstantiatePrefab`, and edit existing prefabs with `PrefabUtility.LoadPrefabContents`/`SaveAsPrefabAsset`.
- Prefer `BoxCollider`s over `MeshCollider`s on new props and floors; leave purely decorative geometry (markings, glass, small details) with no collider.
- Unity here does not pick up new/edited scripts on its own while the Editor is in the background: creating a `.cs` and calling `AssetDatabase.Refresh()` leaves the assembly stale (the type is missing from `AppDomain`, and `Unity_RunCommand` fails to compile against it). Force it with `UnityEditor.Compilation.CompilationPipeline.RequestScriptCompilation()`, then wait — the domain reload makes the MCP briefly report "Unity not detected", and only after it do the new types resolve. Check `Unity_ReadConsole` when a type still fails to appear.
- ProBuilder 6.1.2 is installed for the demo floor/prop geometry. From an editor script, generate shapes with `UnityEngine.ProBuilder.ShapeGenerator.*`, then call `ToMesh()`, `Refresh()` and `UnityEditor.ProBuilder.EditorMeshUtility.Optimize(pb)` — `UnityEditor.ProBuilder.EditorUtility.InitObject` is `internal` in this version. Two gotchas in `Unity_RunCommand` scripts: `EditorUtility` is ambiguous once `UnityEditor.ProBuilder` is imported (qualify as `UnityEditor.EditorUtility`), and `Object.GetInstanceID()` is obsolete in this Unity version (`GetEntityId()`).
- Nothing in C# refers to the scene, the city root or the materials folder by name; material references are serialized by GUID. Editor scripts that need the city root should look it up as `GameObject.Find("City")`.
