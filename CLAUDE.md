# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a Unity project (`Test AI`) using Unity Editor version `6000.5.8f1` and the Universal Render Pipeline (URP). It started from Unity's default 3D template and a library of FBX model assets under `Assets/Models`. It now has a single scene, `Assets/Scenes/City.unity`, holding a ProBuilder greybox city with working traffic, plus the playable third-person character walking around it.

There is no git repository initialized in this directory yet.

## Structure

- `Assets/Scenes/City.unity` — **the project's only scene** (it was named `City3` while being built, and the earlier `SampleScene` has been deleted). Roots: `City3` (the city; the GameObject still carries the old name), a `Player` instance of `Assets/Prefabs/Player.prefab`, `Main Camera` (has `ThirdPersonCamera`), `Directional Light`, and `Global Volume`. There is no `Plane` ground any more — the character stands on the city's own road and sidewalk geometry, which is what carries the colliders.
- **Build Settings still list the deleted `Assets/Scenes/SampleScene.unity`** and not `City.unity`, so a player build (or any `SceneManager.LoadScene`) would fail. Fix that before building.
- `Assets/Prefabs/Player.prefab` — the playable character. Built on `character-male-d.fbx`, with `CharacterController` (radius 0.2, height 0.72, center (0, 0.36, 0) — sized to the model's actual bounds, not Unity's 2 m default), `Animator` (uses `PlayerAnimator.controller` and the FBX's own Avatar), and `TestAI.PlayerController`.
- `Assets/Scripts/PlayerController.cs` — walk/run/jump via the new Input System (`InputSystem_Actions.inputactions`, `Player` action map: `Move`, `Sprint`, `Jump`). Movement direction is relative to the camera. Drives the Animator's `Speed`, `Grounded`, `Jump`, `VerticalSpeed` parameters.
- `Assets/Scripts/ThirdPersonCamera.cs` — Mario-64-style orbit camera. Reads `Look` from the same action map. Only the target-follow *position* is smoothed (`SmoothDamp`); rotation is recomputed every frame as `LookRotation` from the camera's actual (possibly lagging) position to the pivot, so camera position and where it looks can never desync — do not reintroduce separate smoothing on `transform.rotation`, that was tried and caused visible motion sickness. Pivot offset from the target is configurable via `verticalOffset` and `horizontalOffset` (the latter applied along the orbit's local right axis, i.e. an over-the-shoulder offset), not a single `Vector3` offset. Has camera-vs-environment `SphereCast` collision.

### The city (the `City3` root in `City.unity`)

- Built entirely from ProBuilder primitives via `Unity_RunCommand` editor scripts (no FBX props). Layout is a 56 m grid: street axes at x/z ∈ {-84, -28, 28, 84}, nine 46 m blocks centred on {-56, 0, 56}, city extent ±90. Grouped as `Roads`, `Sidewalks`, `RoadMarkings`, `Buildings`, `TrafficLights`, `StreetLights`, `Plaza`, `Trees`, `Props`, `Vehicles`, `TrafficNetwork`. Block tops sit at y = 0.18 (sidewalk thickness), which is the ground datum every prop is placed on. The centre block is a plaza (lawns, fountain, benches). ~1000 `ProBuilderMesh` objects; only structural geometry (roads, sidewalks, building bodies) has `MeshCollider`s — markings, windows and small details do not.
- `Assets/Scripts/TrafficLight.cs` / `Assets/Scripts/TrafficLightIntersection.cs` — the traffic lights. `TrafficLight` swaps lamp materials (`LightRed`/`LightAmber`/`LightGreen`/`LightOff`) to show its state; `TrafficLightIntersection` runs the coroutine that alternates green between its `eastWest` and `northSouth` groups with amber and all-red phases. The four inner intersections each have 4 lights, wired up by editor script through `SerializedObject` (the fields are private `[SerializeField]`), with a `startOffset` per intersection so neighbours are not in sync.
- `Assets/Scripts/TrafficNetwork.cs` / `Assets/Scripts/CarAgent.cs` — the traffic. `TrafficNetwork` (on `City3/TrafficNetwork`) *generates* the lane graph in `Awake` from the same layout as the geometry (`axes`, `laneOffset` 2.6 — the 128 nodes are computed, not serialized). Per intersection and direction there is an *entry* node (the inner corner of the crossing: where the turn is chosen and where the light applies) and an *exit* node; turning right needs no intermediate node because one direction's entry coincides geometrically with the exit of the direction to its right. Lights are matched by geometry, not by name: each entry gets the `TrafficLight` facing it head-on (`Dot(light.forward, direction) < -0.9`), which leaves the 12 outer intersections unsignalled. `CarAgent` follows the graph picking turns at random (`straightWeight` favours going straight), brakes progressively for red/amber and for the car ahead, and takes corners with `RotateTowards` plus a speed cut, not by interpolating positions. Two rules matter: once past the stop line a car keeps going even if the light changes (so it never freezes inside a crossing), and at unsignalled crossings priority is an exclusive per-intersection reservation (`TryReserve`/`Release`, with a timeout) because the forward sensor cannot see cross traffic.
- That reservation once deadlocked every car into a standstill queue for over five minutes, and its current shape *is* the fix — do not revert any of the three pieces: (1) the owner does **not** refresh its timestamp when re-claiming the reservation (if it does, a car blocked next to the crossing holds it forever just by asking every frame, and the timeout never expires); (2) priority is claimed only within `claimDistance` of the stop line, slowing down beforehand like a give-way, never from far off — reserving before you can actually cross blocks everyone else; (3) `ReleaseReservationWhileBlocked` drops it when its owner is stopped by another car and has not entered the crossing yet, which is what breaks the "A waits for the priority B holds, B waits for A to move" cycle. `CurrentStopReason`/`StoppedTime`/`DistanceTravelled` exist to diagnose jams.
- Route weighting (`RouteWeight`/`Ring`, with `interiorBias` and `borderPenalty`) exists because without it all traffic ends up circling the perimeter: on a border street, going straight is the only non-turning exit, and with the raw straight weight that was ~71% likely at every crossing. The weights cancel that bias towards the interior; measured, traffic settles around 9/9 between perimeter and interior.
- Layer `Vehicle` (slot 8) — used by the cars; `CarAgent`'s forward sensor (`SphereCastNonAlloc`) queries only that layer. In that sensor, hits are discarded **by identity** (`other == this`), never by distance: a zero-distance hit is both the car's own collider and the car already bumper-to-bumper ahead, and filtering by distance made cars fail to see each other and drive inside one another on corners. Cars carry a single `BoxCollider` on the root rather than their pieces' `MeshCollider`s: they move by transform with no `Rigidbody`, and the collider exists only so they can detect each other.
- The `Vehicles` group no longer holds ProBuilder greybox cars — traffic is 18 instances of four modelled prefabs (`Assets/Prefabs/SedanSportCar.prefab`, `TaxiCar.prefab`, `DeliveryCar.prefab`, `PoliceCar.prefab`), mixed across the grid rather than clustered by type: 7 `Taxi_*`, 4 `Police_*`, 5 `Delivery_*`, 2 `Sedan_*`. Each prefab already had its own `BoxCollider` sized to its mesh; layer `Vehicle`, `CarAgent` and `vehicleMask` were added on top by editor script (`PrefabUtility.LoadPrefabContents`/`SaveAsPrefabAsset`, not hand-edited YAML) — reuse that pattern for further vehicle prefabs. `CarAgent.network` is left unassigned on the prefabs; `Start()` falls back to `FindFirstObjectByType<TrafficNetwork>()`, which is fine since the scene only ever has one.
- Each type has distinct `CarAgent` tuning so the mixed traffic doesn't all drive identically (prefab defaults; each scene instance additionally has a ±6% random jitter on `maxSpeed` for per-car variety): `Delivery` is the slowest and worst-accelerating (`maxSpeed` 6.5, `acceleration` 3, `braking` 9, `turnSpeed` 160°/s, `cornerSpeedFactor` 0.32 — reads as a heavy truck, sluggish into corners); `Police` sits at a patrol pace with the snappiest acceleration for its speed (`maxSpeed` 9, `acceleration` 7.5, `braking` 15, `turnSpeed` 230°/s, `cornerSpeedFactor` 0.45 — the original default tuning); `Taxi` is a bit faster than `Police` but accelerates worse (`maxSpeed` 10.2, `acceleration` 4.5, `braking` 13, `turnSpeed` 215°/s, `cornerSpeedFactor` 0.42); `Sedan` is the fastest and hardest-accelerating of all (`maxSpeed` 12.8, `acceleration` 9.5, `braking` 17, `turnSpeed` 260°/s, `cornerSpeedFactor` 0.5).
- `Assets/Materials/City/` — the flat-colour URP/Lit palette for the city (asphalt, sidewalk, road lines, facades, glass, foliage, car bodies, plus the emissive `LightRed`/`LightAmber`/`LightGreen`/`LampWarm` lamp materials). Created by editor script, not by hand.

### Shared assets

- `Assets/Animations/PlayerAnimator.controller` — created via `UnityEditor.Animations.AnimatorController` (editor script), not hand-authored YAML. Base layer: `Locomotion` (1D blend tree on `Speed`, blending `idle`→`walk`→`sprint`), `Jump`, `Fall`, with trigger/bool-driven transitions between them.
- `Assets/Models/Characters/character-male-d.fbx` — the model backing `Player`. Its importer was reconfigured (via editor script, not by hand-editing the `.meta`) to `animationType: Generic` with an Avatar created from the model itself (was `avatarSetup: 0` / no Avatar originally), and `idle`/`walk`/`sprint`/`fall`/`crouch`/`static` clips set to loop (the FBX's default `clipAnimations` import with `loopTime: false`). The FBX contains 32 animation takes total (combat, wheelchair, emotes, etc.) beyond the ones currently wired into the controller — reuse the same reimport pattern if more are needed.
- Other `Assets/Models/Characters/*.fbx` (other character variants) and `Assets/Models/Pets/*.fbx` — same Generic/no-Avatar import state as `character-male-d.fbx` originally had; not yet reimported or referenced by any prefab/script.
- `Assets/Settings/` — URP pipeline assets (separate PC and Mobile renderer/pipeline configs) and the default volume profile.
- `Assets/InputSystem_Actions.inputactions` — the project's only input asset (`generateWrapperCode: 0`, so there's no generated C# class; scripts look up the `Player` action map and actions by name via a serialized `InputActionAsset` reference). Project uses the new Input System exclusively (`activeInputHandler: 1` in ProjectSettings) — `UnityEngine.Input` will throw at runtime.
- `Assets/TutorialInfo/` and `Assets/Readme.asset` — Unity's default template Readme asset/editor, not project-specific.
- `Packages/manifest.json` — package dependencies (URP, Input System, Timeline, Visual Scripting, Unity AI Assistant, etc.). No Cinemachine — the camera is hand-rolled by design.
- The many `Unity.*.csproj` files and `.sln` at the root are IDE-generated project files (regenerated by Unity/Rider automatically); do not hand-edit them.

## Working in this project

- There is no CLI build/test/lint pipeline set up — this project is edited and run through the Unity Editor (or Rider/Visual Studio via the generated `.sln`).
- When adding scripts, place runtime code in `Assets/Scripts` and follow standard Unity C# conventions (MonoBehaviour components, `.meta` files are auto-generated by the Editor — don't create or edit them manually).
- Structural, hard-to-hand-author assets (AnimatorControllers, ModelImporter reconfiguration, prefab creation, the whole city) were built via one-off editor scripts run through the Unity MCP tooling (`Unity_RunCommand`), not by writing `.controller`/`.meta` YAML directly — prefer that same approach for similar changes.
- Nothing in C# refers to the scene, the city root, or the materials folder by name (material references are serialized by GUID), so the `City3` → `City` renames needed no code changes. Watch for it anyway when writing new editor scripts: the ones used to build the city looked the root up with `GameObject.Find("City3")`.
- FBX characters/pets other than `character-male-d` still have `animationType: Generic` with no Avatar and un-looped clips; before animating any of them, reimport following the same pattern used for `character-male-d.fbx`.
- Unity here does not pick up new/edited scripts on its own while the Editor is in the background: creating a `.cs` and then calling `AssetDatabase.Refresh()` leaves `Assembly-CSharp` stale (the type is missing from `AppDomain`, and `Unity_RunCommand` fails to compile against it). Force it with `UnityEditor.Compilation.CompilationPipeline.RequestScriptCompilation()`, then wait — the domain reload makes the MCP briefly report "Unity not detected", and only after it the new types resolve. Check `Unity_ReadConsole` for compile errors when a type still fails to appear.
- ProBuilder 6.1.2 is installed and is the intended way to build level geometry. From an editor script, generate shapes with `UnityEngine.ProBuilder.ShapeGenerator.*`, then call `ToMesh()`, `Refresh()` and `UnityEditor.ProBuilder.EditorMeshUtility.Optimize(pb)` so the mesh is cached in the scene — `UnityEditor.ProBuilder.EditorUtility.InitObject` is `internal` in this version and cannot be used. Watch two gotchas in `Unity_RunCommand` scripts: `EditorUtility` is ambiguous once `UnityEditor.ProBuilder` is imported (qualify it as `UnityEditor.EditorUtility`), and `Object.GetInstanceID()` is obsolete in this Unity version (`GetEntityId()`).
- The `TestAI` namespace (`PlayerController`, `ThirdPersonCamera`, `TrafficLight`, `TrafficLightIntersection`, `TrafficNetwork`, `CarAgent`) is the established convention; extend it rather than introducing a new one.
