# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a Unity project (`City Generator`, Unity `6000.5.8f1`, URP) whose **only reason to exist is to develop, test and distribute the City Generator tool** — an Editor window that procedurally generates a city (roads, sidewalks, markings, buildings, plazas, street furniture, traffic lights and autonomous traffic) into a new or existing scene.

The tool lives in the embedded package `Packages/com.santiandrade.citygenerator/` and that package **is** the deliverable: it is what a user installs into their own Unity project via **Package Manager > Install package from git URL**. This project consumes the tool the same way — as an installed package, not as loose code in `Assets/` — so a portability break shows up here first, not in the user's project. See the root `README.md` (English) / `README.es.md` (Spanish) for the install URL, the update procedure and full user-facing documentation. Everything else in the repo exists to support the package, in one of three roles:

- **Demo content**, inside the package at `Packages/com.santiandrade.citygenerator/DefaultAssets/` — the sample prefabs the tool ships with so it works out of the box, loaded by `CityGeneratorDefaultAssets`. It travels with the package to any project that installs it; only the models actually referenced by a demo prefab live here (see "Demo content" below for how that's decided).
- **Orphan models** (`Assets/Models/`) — FBX/glb library entries from the same asset packs as the demo models that no demo prefab currently uses. Kept in this repo on purpose for future use, but deliberately **not** part of the package, so installing it doesn't drag along unused models.
- **Test scene** (`Assets/Scenes/City.unity`) — a **disposable** scene generated by the tool, kept only to eyeball the output. It is regenerated freely and carries no hand-made work worth preserving. Never treat it as a source of truth, and never hand-edit it to fix something the tool should be doing.

The tool's behaviour is considered **done and correct**: reproduce it, don't redesign it. Its original spec lives in `specs/01-city-generator-tool.md` (Spanish, driven by a `/spec-*` workflow configured by `specs/.spec-config.yml`); read it before touching the tool's generation logic — it records the decisions taken **and explicitly discarded**, several of them found during manual QA. `specs/02-unity-package-distribution.md` is the spec for the package/distribution work described in this file (embedding, demo content movement, README, versioning, release tooling) — it does not touch generation behaviour. `docs/technical-review.md` is the standing technical review (performance, code quality, ECS analysis) with the pending findings.

Historical note: the layout the tool reproduces was originally a hand-built city made of ProBuilder primitives. That hand-made city no longer exists (commit `ff13e28`, "Removed old city"). The numbers extracted from it survive as `CityGeneratorConstants`.

## Structure

### The tool — `Packages/com.santiandrade.citygenerator/` (the installable package)

An embedded Unity package (`package.json`, `name` `com.santiandrade.citygenerator`, `unity` `6000.0`, dependencies `com.unity.inputsystem` and `com.unity.cloud.gltfast`). Two assemblies, each with its own `.asmdef`:

- `Runtime/CityGenerator.Runtime.asmdef` — namespace `CityGenerator.Runtime`, references `Unity.InputSystem`.
- `Editor/CityGenerator.Editor.asmdef` — namespace `CityGenerator.Editor`, `includePlatforms: [Editor]`, references the runtime asmdef and `Unity.InputSystem`. Every type in it is `internal static` except the window.

**`CityGeneratorWindow`** — `Tools > City Generator > Open`. Holds the entire configuration in a single `[SerializeField] CityGeneratorSettings settings`, which is why state survives closing/reopening the window within an Editor session; **deliberately not a `ScriptableObject`** (see the spec's discarded decisions). Draws `ToolThumbnail.png` as a header. Three buttons: "Build City in New Scene", "Re-Build City in Current Scene" (destroys the `City` root and regenerates it, leaving light/camera/player alone) and "Reset to Defaults". Two UI quirks are load-bearing and commented in place: `labelWidth` is scaled from `position.width` because the auto width clips the long labels, and required fields draw their red asterisk as a `Rect` overlay inside the label column because a trailing `GUILayout` control gets pushed off-screen on a narrow window. The asterisk is **conditional**: `DrawRequiredField`'s `isRequired` parameter hides it for fields only required under another setting (e.g. `lawnPrefab` only when `plazaCount > 0`), so it disappears once that condition stops applying.

**Pipeline**, in order: `CityGeneratorValidator` (runs first, blocks generation with a dialog + console errors) → `CityGeneratorSceneBuilder` (new scene + directional light + camera + player, saved as the next free `Assets/Scenes/City<N>.unity`) → `CityGeneratorContentAssembler` (the group hierarchy and every builder) → `Grid` → `GroundBuilder` → `BuildingBuilder` → `PlazaBuilder` → `StreetPropsBuilder` → `TrafficBuilder`.

- `CityGeneratorConstants` holds the layout numbers (46 m blocks on a 56 m pitch, `GroundDatumY` 0.18, 22 m building slots, lamp/zebra/traffic-light offsets…). Most constants carry a comment explaining *why* that value — several were tuned against real overlap bugs (lamps clearing the plaza lawn, zebra stripes vs. dashed centreline, corner margin so wide prefabs don't collide across a corner). Change them from there, never inline.
- **Overlap avoidance is the tool's central mechanism, but only for props and vegetation** — buildings and vehicles are deliberately exempt. `CityGeneratorBoundsUtility.GetWorldBounds` combines all child `Renderer` bounds, and `CityGeneratorPlacementEngine` instantiates a candidate, checks its XZ `Rect` against every already-placed object, and `DestroyImmediate`s it if it overlaps. Bounds, not fixed per-category radii, because the prefabs come from the user. `ContentAssembler` threads one growing `obstacles` list through every category in turn — if you add a category, append its result to that list.
- `CityGeneratorBuildingBuilder.BuildBuildings` picks up to 4 fixed 22 m corner slots per non-plaza block, guaranteeing every assigned building prefab is used at least once. **Which corners are filled is shuffled per block** when `buildingsPerBlock < 4` — a QA-found bug had every block always fill corners `0..buildingsPerBlock-1` in the same order, making partially-built blocks look identical everywhere. Buildings are **not** overlap-checked against each other or against the block edge: an oversized building prefab will visibly clip into its neighbour or spill into the street — accepted as the user's responsibility to size their prefabs to the 22 m slot, same as any other user-supplied prefab.
- Densities mean "fraction of valid candidate points filled", not an absolute count — including `lampDensity` (1 = all 3 candidate points per block side).
- `CityGeneratorContentAssembler` applies `BatchingStatic | OccluderStatic | OccludeeStatic` to every generated group **except `Vehicles`**, so each generated city is batched and ready for a lightmap/occlusion bake with no manual pass. `CarAgent` moves vehicles by transform every frame, which is why they are excluded.
- `CityGeneratorTrafficBuilder.BuildVehicles` calls `EnsureVehicleLayerExists` before spawning anything: if the project has no `Vehicle` layer yet, it creates one itself by writing directly to `ProjectSettings/TagManager.asset` via `SerializedObject`, using the first free slot from `CityGeneratorConstants.FirstUserLayerIndex` (8) up, and logs that it did so. Requiring the user to create this layer by hand was a recurring point of confusion during SPEC 02 verification. Only if every slot 8-31 is already taken does it fall back to warning instead — in that case every instance's `CarAgent.vehicleMask` is left at `0` (Nothing) rather than matching whatever layer the instance happens to share with unrelated scene geometry, so vehicles simply stop detecting each other (they still stop for lights and unsignalled-crossing priority) until a slot frees up. `CarAgent` and the `Vehicle` layer are added **to the scene instances only**, never to the user's prefab asset, and outer-edge exit nodes are skipped when spawning (a car there has nothing ahead and `CarAgent` disables itself). When the layer does exist, `BuildVehicles` sets `CarAgent.vehicleMask` to `1 << instance.layer` per instance via `SerializedObject` — **do not rely on the mask baked into a vehicle prefab's own serialized data**: it only happens to work when `Vehicle` sits at the same layer index the prefab was authored against, and silently makes the forward sensor blind to every other vehicle otherwise (found during SPEC 02 verification: the demo prefabs' baked `vehicleMask` and `m_Layer` both happened to reference index 8, which is why the bug went unnoticed). `CityGeneratorConstants.VehicleDensityWarningThreshold` (0.4 of spawn nodes) is surfaced only as a live `HelpBox` in `CityGeneratorWindow` while editing `vehicleCount` — `BuildVehicles` itself no longer logs a console warning past that threshold, since the inspector already told the user before they clicked generate; measured on a 5×5 grid, 38% of nodes flowed, 76% gridlocked from the first frame.
- `general.useCustomSeed` (off by default) + `general.seed` make generation reproducible: `Assemble` uses `new System.Random(seed)` when enabled, unseeded otherwise. Every builder receives that one `System.Random` **by parameter** — none of them touch `UnityEngine.Random`, so seeding it is enough to make placement and prefab choice fully deterministic (`CarAgent`'s runtime driving still uses `UnityEngine.Random`, unrelated to generation).
- The generated `Main Camera`'s transform is a **hand-tuned fixed value**, not Unity's defaults: position `(36, 28, -36)`, rotation `Euler(27, -45, 0)`, `fieldOfView` 45.
- No `Global Volume` is generated — removed on purpose (commit `a094fef`) to keep the tool render-pipeline-agnostic.
- `CityGeneratorDefaultAssets.ApplyTo` fills a fresh `CityGeneratorSettings` with the package's own demo prefabs (all 20 fields — buildings, vegetation, vehicles with their percentages, ground, plaza, props, player, input actions), loaded from hardcoded `Packages/com.santiandrade.citygenerator/DefaultAssets/...` paths, so the window opens ready for a one-click first generation instead of empty required fields. Since SPEC 02 those paths resolve in any project that installs the package (the demo content ships inside it), so this file is no longer the one non-portable file in the tool — it's ordinary portable code, just tied to the bundled demo assets rather than to generation logic. It cannot run from a field initializer on `CityGeneratorSettings` (Unity forbids `AssetDatabase` calls during `EditorWindow` deserialization); it is invoked from `CityGeneratorWindow.OnEnable()`, gated by a serialized `defaultsInitialized` flag so it runs once per window instance, and again from "Reset to Defaults".

### Runtime components — `Packages/com.santiandrade.citygenerator/Runtime/`

These ship with the tool and are what a generated city runs on.

- `PlayerController.cs` — walk/run/jump via the new Input System (`Player` action map: `Move`, `Sprint`, `Jump`). Movement is camera-relative. Drives the Animator's `Speed`, `Grounded`, `Jump`, `VerticalSpeed`.
- `ThirdPersonCamera.cs` — Mario-64-style orbit camera, reads `Look` from the same map. Only the target-follow *position* is smoothed (`SmoothDamp`); rotation is recomputed every frame as `LookRotation` from the camera's actual (possibly lagging) position to the pivot, so position and aim can never desync — **do not reintroduce separate smoothing on `transform.rotation`**, that was tried and caused visible motion sickness. Pivot offset is `verticalOffset` + `horizontalOffset` (the latter along the orbit's local right axis, i.e. over-the-shoulder), not a single `Vector3`. Has camera-vs-environment `SphereCast` collision.
- `TrafficLight.cs` / `TrafficLightIntersection.cs` — `TrafficLight` swaps lamp materials (`LightRed`/`LightAmber`/`LightGreen`/`LightOff`) to show its state; `TrafficLightIntersection` runs the coroutine alternating green between its `eastWest` and `northSouth` groups with amber and all-red phases, with a per-intersection `startOffset` so neighbours are not in sync.
- `TrafficNetwork.cs` — *generates* the lane graph in `Awake` from the same layout as the geometry (`laneOffset` 2.6; nodes are computed, not serialized). The axes are **two independent arrays**, `axesX` and `axesZ`, so grids need not be square; `SetAxes` + the public `Build()` let the generator set the layout, place all traffic lights, and only then build the graph (`Build` matches lights by scanning the scene, so order matters). `EnsureBuilt` covers accessors called before `Awake`. Per intersection and direction there is an *entry* node (the inner corner of the crossing: where the turn is chosen and where the light applies) and an *exit* node; turning right needs no intermediate node because one direction's entry coincides geometrically with the exit of the direction to its right. Lights are matched **by geometry, not by name**: each entry gets the `TrafficLight` facing it head-on (`Dot(light.forward, direction) < -0.9`), which leaves outer intersections unsignalled. It also calls `Physics.SyncTransforms()` once per frame after the agents have moved, because the project runs with `m_AutoSyncTransforms: 0` and `CarAgent` moves by transform then raycasts in the same frame.
- `CarAgent.cs` — follows the graph picking turns at random (`straightWeight` favours going straight), brakes progressively for red/amber and for the car ahead, and takes corners with `RotateTowards` plus a speed cut, not by interpolating positions. Falls back to `FindFirstObjectByType<TrafficNetwork>()` in `Start` if `network` wasn't injected by the generator, since a scene only ever has one. Ticked by `TrafficManager` rather than through its own `Update` — see below. Four rules are load-bearing:
  1. Once past the stop line a car keeps going even if the light changes, so it never freezes inside a crossing.
  2. At unsignalled crossings priority is an exclusive per-intersection reservation (`TryReserve`/`Release`, with a timeout), because the forward sensor cannot see cross traffic. **That reservation once deadlocked every car for over five minutes and its current shape *is* the fix — do not revert any of its three pieces**: (a) the owner does *not* refresh its timestamp when re-claiming (if it does, a blocked car holds the reservation forever just by asking every frame and the timeout never expires); (b) priority is claimed only within `claimDistance` of the stop line, slowing down beforehand like a give-way, never from far off; (c) `ReleaseReservationWhileBlocked` drops it when its owner is stopped by another car and has not entered the crossing, breaking the "A waits for the priority B holds, B waits for A to move" cycle. `CurrentStopReason`/`StoppedTime`/`DistanceTravelled` exist to diagnose jams.
  3. In the forward sensor (`SphereCastNonAlloc`, filtered by `vehicleMask` — set per-instance by `CityGeneratorTrafficBuilder` to match the layer it actually placed the vehicle on, not a value baked into the prefab) hits are discarded **by identity** (`other == this`), never by distance: a zero-distance hit is both the car's own collider *and* the car already bumper-to-bumper ahead, and filtering by distance made cars fail to see each other and drive inside one another on corners.
  4. Route weighting (`RouteWeight`/`Ring`, with `interiorBias` and `borderPenalty`) exists because without it all traffic circles the perimeter: on a border street, going straight is the only non-turning exit, ~71% likely at every crossing with the raw straight weight. Measured with the weights, traffic settles around 9/9 perimeter/interior.
- `TrafficManager.cs` — ticks every registered `CarAgent` from a single `Update` (`Register`/`Unregister`, called from each car's `Start`/`OnDisable`) instead of each car paying its own Update marshalling cost (technical review, A.7). `CityGeneratorTrafficBuilder.AddManagerComponent` adds it to the `TrafficNetwork` GameObject only when `includeTraffic` is on; a `CarAgent` used outside the generator falls back to finding or auto-creating one, so it still drives standalone. Below `staggerMinAgentCount` (60 by default) every car's forward sensor runs every frame, identical to the old per-car `Update` — **do not lower this without re-verifying the default 30-car demo still behaves the same**. Above it, cars farther than `staggerDistance` from `Camera.main` only run their `SphereCast` 1 of every `staggerFrames` frames, reusing the previous clearance in between.
- `PerformanceBootstrap.cs` — `[RuntimeInitializeOnLoadMethod]` that sets `vSyncCount = 0` and `targetFrameRate = 60`. Ships with the tool rather than as a project setting so generated cities behave the same in another project.

### Demo content — `Packages/com.santiandrade.citygenerator/DefaultAssets/`

Ships inside the package (moved there by SPEC 02 so it's portable to any project that installs it), loaded by `CityGeneratorDefaultAssets` from hardcoded `DefaultAssets/...` paths. Unity treats package content as read-only in the consuming project — to edit a demo prefab, copy it into your own `Assets/` first.

- `DefaultAssets/Prefabs/` — the 22 sample prefabs, by category: `Buildings/` (6 modelled prefabs, root scale 10, pivot at base, own collider; widest footprint ~13.9 m, clearing the 22 m slot), `Characters/Player.prefab`, `Floors/` (`RoadBase`, `RoadSidewalk`, `RoadDash`, `RoadZebra`, `Lawn` — ProBuilder-authored slabs), `Props/` (`Bench`, `Bin`, `Lamp`, `TrafficLight`, and `Fountain`, the only imported-model prop, built on `DefaultAssets/Models/Props/Fountain by Poly.glb` via glTFast), `Vegetation/Tree.prefab`, `Vehicles/` (`DeliveryCar`, `PoliceCar`, `SedanSportCar`, `TaxiCar`).
- Colliders are deliberately simple: `BoxCollider`s on floors, benches, lamps and traffic lights; `MeshCollider`s only on `Tree` (trunk + crown); **no collider at all** on road markings. Vehicles carry a single root `BoxCollider` (no `Rigidbody` — they move by transform, and the collider exists only so they can detect each other).
- Each vehicle prefab has distinct `CarAgent` tuning so mixed traffic doesn't drive identically: `Delivery` slowest/heaviest (`maxSpeed` 6.5, `acceleration` 3, `cornerSpeedFactor` 0.32), `Police` patrol pace with snappy acceleration (9 / 7.5 / 0.45), `Taxi` slightly faster but worse acceleration (10.2 / 4.5 / 0.42), `Sedan` fastest and hardest-accelerating (12.8 / 9.5 / 0.5). The generator adds a ±6% `maxSpeed` jitter per instance.
- `DefaultAssets/Materials/` — the flat-colour URP/Lit palette (14 materials: `Asphalt`, `Sidewalk`, `RoadLine`, `Crosswalk`, `Grass`, `GlassBlue`, `TreeTrunk`/`TreeLeaves`, `MetalDark`, and the emissive `LightRed`/`LightAmber`/`LightGreen`/`LightOff`/`LampWarm`). Created by editor script, not by hand. The fountain is the only geometry that doesn't use this palette — it keeps the materials embedded in its `.glb`.
- `DefaultAssets/Meshes/` — extracted mesh assets backing the ProBuilder-authored floor/prop prefabs.
- `DefaultAssets/Animations/PlayerAnimator.controller` — created via `UnityEditor.Animations.AnimatorController` (editor script), not hand-authored YAML. Base layer: `Locomotion` (1D blend tree on `Speed`: idle→walk→sprint), `Jump`, `Fall`.
- `DefaultAssets/Models/` — only the FBX/glb models a demo prefab actually references (6 buildings, 4 cars, `character-male-d.fbx`, the fountain `.glb`), decided by `AssetDatabase.GetDependencies` over the 22 prefabs and `PlayerAnimator.controller`, not by inspection. Everything else from the same asset packs stays in `Assets/Models/` in this repo (see Project overview) and is **not** part of the package. `Buildings/`, `Cars/` and `Characters/` each carry a `Textures/colormap.png` — a texture atlas shared with the orphan models of the same category still in `Assets/Models/`, so it's **copied** into the package (not moved) to avoid breaking those orphans; the same file exists in both places on purpose. `character-male-d.fbx` is the one backing `Player`: its importer was reconfigured by editor script to `animationType: Generic` with an Avatar created from the model, and `idle`/`walk`/`sprint`/`fall`/`crouch`/`static` set to loop.
- `DefaultAssets/Input/InputSystem_Actions.inputactions` — the only input asset (`generateWrapperCode: 0`; scripts look up the `Player` map and its actions by name through a serialized `InputActionAsset` reference). The project uses the new Input System exclusively (`activeInputHandler: 1`) — `UnityEngine.Input` throws at runtime. The tool takes this asset as a *setting* (`general.inputActions`), never by hardcoded path.
- `Assets/Settings/` — URP pipeline assets (separate PC and Mobile renderer/pipeline configs) and volume profiles. Project configuration, not part of the package; see `docs/technical-review.md` for the recommended values.

### Versioning and releasing the package

- `Packages/com.santiandrade.citygenerator/package.json` carries the SemVer `version`; `CHANGELOG.md` in the same folder follows Keep a Changelog, with a `## [Unreleased]` section always present above the latest release. A git tag `vX.Y.Z` marks each release.
- Unity has **no real "Update" button for a package installed by git URL** — installing fixes the resolved commit in `Packages/packages-lock.json`. Updating means reinstalling the URL with the new tag; this is documented for end users in the root README.
- `Assets/Editor/CityGeneratorReleaseWindow.cs` (`Tools > City Generator > Release`, outside the package, in `Assembly-CSharp-Editor`) automates the repetitive part: bumps `version` in `package.json`, turns `## [Unreleased]` into `## [X.Y.Z] - YYYY-MM-DD` and opens a new empty `## [Unreleased]` above it, then shows (and copies to the clipboard) the `git tag vX.Y.Z && git push origin vX.Y.Z` command. It never runs git itself — the tag is always created by a person, on purpose.

### The test scene — `Assets/Scenes/City.unity`

Currently a 3×3 city generated by the tool: 398 prefab instances and 27 plain GameObjects (the `City` root, its 11 group empties, 8 `Block_r_c`, 1 `Plaza_1_1`, 4 `Intersection_r_c`, camera and light), plus a `Player` instance at the scene root. Static flags are set on every generated group. Lightmaps and occlusion culling are **not** baked.

The ProBuilder-authored floor/prop prefabs keep their `ProBuilderMesh` component, so each instance stores its regenerated mesh as a scene-local override — the scene holds ~227 embedded `pb_Mesh*` assets. That is expected, and the reason the scene file is ~5 MB. See `docs/technical-review.md` for the standing proposal to remove ProBuilder from those prefabs.

Build Settings list this scene as the only enabled one. It is disposable: regenerate it rather than repairing it.

## Working in this project

- There is no CLI build/test/lint pipeline — the project is edited and run through the Unity Editor (or Rider/Visual Studio via the generated `.sln`). The `Unity.*.csproj` files and `.sln` at the root are IDE-generated and regenerated automatically; never hand-edit or commit them (they are gitignored).
- **Fixes belong in the tool, not in the scene.** If generated output is wrong, change the builder that produced it and regenerate. Hand-editing `City.unity` fixes exactly one city and is lost on the next generation.
- **The tool must stay portable to any Unity project**: no dependency on this project's prefabs, materials, layers or assets outside the package's own `DefaultAssets/`, and no mutation of the user's assets. Anything project-specific belongs in the demo content, in `CityGeneratorDefaultAssets`, or in `Assets/Editor/CityGeneratorReleaseWindow.cs` — never in the rest of `Packages/com.santiandrade.citygenerator/`.
- New code goes in `Packages/com.santiandrade.citygenerator/Runtime` (namespace `CityGenerator.Runtime`) or `Packages/com.santiandrade.citygenerator/Editor` (namespace `CityGenerator.Editor`) — extend those, don't introduce a new namespace, and remember both are behind `.asmdef`s, so anything new they reference must be added to the asmdef's `references`.
- Structural, hard-to-hand-author assets (AnimatorControllers, ModelImporter reconfiguration, prefab creation) are built via one-off editor scripts run through the Unity MCP tooling (`Unity_RunCommand`), not by writing `.controller`/`.meta`/`.prefab` YAML directly — prefer that same approach. Create prefabs with `PrefabUtility.SaveAsPrefabAsset`, place instances with `PrefabUtility.InstantiatePrefab`, and edit existing prefabs with `PrefabUtility.LoadPrefabContents`/`SaveAsPrefabAsset`.
- Prefer `BoxCollider`s over `MeshCollider`s on new props and floors; leave purely decorative geometry (markings, glass, small details) with no collider.
- Unity here does not pick up new/edited scripts on its own while the Editor is in the background: creating a `.cs` and calling `AssetDatabase.Refresh()` leaves the assembly stale (the type is missing from `AppDomain`, and `Unity_RunCommand` fails to compile against it). Force it with `UnityEditor.Compilation.CompilationPipeline.RequestScriptCompilation()`, then wait — the domain reload makes the MCP briefly report "Unity not detected", and only after it do the new types resolve. Check `Unity_ReadConsole` when a type still fails to appear.
- ProBuilder 6.1.2 is installed for the demo floor/prop geometry. From an editor script, generate shapes with `UnityEngine.ProBuilder.ShapeGenerator.*`, then call `ToMesh()`, `Refresh()` and `UnityEditor.ProBuilder.EditorMeshUtility.Optimize(pb)` — `UnityEditor.ProBuilder.EditorUtility.InitObject` is `internal` in this version. Two gotchas in `Unity_RunCommand` scripts: `EditorUtility` is ambiguous once `UnityEditor.ProBuilder` is imported (qualify as `UnityEditor.EditorUtility`), and `Object.GetInstanceID()` is obsolete in this Unity version (`GetEntityId()`).
- Nothing in C# refers to the scene, the city root or the materials folder by name; material references are serialized by GUID. Editor scripts that need the city root should look it up as `GameObject.Find("City")`.
